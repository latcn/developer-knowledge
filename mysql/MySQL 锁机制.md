
## 一、锁的基本分类与作用

### 1. 按锁粒度划分

#### （1）全局锁

- **作用**：锁定整个数据库实例，使所有表变为只读状态。
- **典型场景**：全库逻辑备份（如 `FLUSH TABLES WITH READ LOCK`，简称 FTWRL）。
- **风险**：备份期间所有更新操作被阻塞，高并发场景下应谨慎使用。
- **高并发下的替代方案**：
  - **MySQL 8.0+ 备份锁**：`LOCK INSTANCE FOR BACKUP`，**仅阻塞 DDL**（文件创建/删除/重命名等），**不阻塞 InnoDB 表的 DML**，是比 FTWRL 更轻量的选择。
  - **快照读备份**：`mysqldump --single-transaction`（仅限 InnoDB），利用 MVCC 获取一致性视图，全程不加全局锁。
  - **物理热备**：MySQL 8.0 Clone Plugin 或 Percona XtraBackup，基于快照 + redo 应用，全程无全局锁。

#### （2）表级锁

- **类型**：
  - **表共享锁（S）**：允许并发读，禁止写。
  - **表排他锁（X）**：禁止其他事务读写。
  - **意向共享锁（IS）**：表明事务对表中某些行加共享锁的意图。
  - **意向排他锁（IX）**：表明事务对表中某些行加排他锁的意图。
  - **AUTO-INC 锁**：用于自增列生成连续值。**在 MySQL 8.0 中，`innodb_autoinc_lock_mode` 默认值为 2（交错模式）**，使用轻量级互斥锁，完全避免表级 AUTO-INC 锁。若手动将模式改为 0 或 1，则可能退化为表级 AUTO-INC 锁。

- **特点**：
  - 表锁开销小，但并发度低。
  - **IS/IX 锁自动管理**：InnoDB 自动添加，用户无需干预。事务在对行加 S/X 锁前必须获取对应表的 IS/IX 锁。
  - **意向锁之间相互兼容**：多个事务可以同时持有 IS 锁、IX 锁，或混合持有 IS 和 IX 锁，互不阻塞。

- **完整的表级锁兼容矩阵**：

| 请求 \ 持有 | X | IX | S | IS |
|-------------|---|---|---|---|
| **X**      | 冲突 | 冲突 | 冲突 | 冲突 |
| **IX**     | 冲突 | 兼容 | **冲突** | 兼容 |
| **S**      | 冲突 | **冲突** | 兼容 | 兼容 |
| **IS**     | 冲突 | 兼容 | 兼容 | 兼容 |

**兼容性解读**：

- **X 锁与任何锁都不兼容**（包括其他 X 锁和所有意向锁）。
- **IX 锁与 S 锁冲突，但与 IS 锁兼容**。
- **S 锁与 IX 锁冲突，但与 IS 锁兼容**。
- **IS 锁与 S 锁、IS 锁、IX 锁均兼容**。
- 意向锁之间（IS 与 IS、IS 与 IX、IX 与 IX）均相互兼容。

#### （3）行级锁

- **本质**：**实际锁定的是索引记录**，而非物理数据行。若表无主键且无唯一索引，InnoDB 使用隐藏的 `ROW_ID` 作为聚簇索引，此时行锁仍然加在隐藏索引上，行为类似普通索引。
- **三种核心类型**：
  - **记录锁（Record Lock）**：锁定单条索引记录。
  - **间隙锁（Gap Lock）**：锁定索引记录之间的间隙（不含端点），防止其他事务在间隙中插入记录，从而防止幻读。
  - **临键锁（Next-Key Lock）**：**记录锁 + 左侧间隙锁**，锁定左开右闭区间 `(prev, current]`。对于索引中的第一条记录，左侧间隙为负无穷，区间为 `(-∞, current]`；对于最后一个记录之后的间隙，使用 `supremum` 伪记录。在 RR 隔离级别下，InnoDB 默认使用临键锁防止幻读。

- **优势**：高并发场景下性能最优，但需警惕死锁风险。
- **RR 隔离级别下幻读的解决机制**：在 RR 级别下，InnoDB 默认使用临键锁。当执行当前读（`SELECT ... FOR UPDATE`/`LOCK IN SHARE MODE`/`UPDATE`/`DELETE`）时，会根据扫描到的索引范围添加临键锁。这些临键锁不仅锁住了已存在的记录，还锁住了这些记录之间的“间隙”，因此其他事务无法在间隙中插入新记录，从而从根本上解决了幻读问题。
- **重要规则**：
  - **唯一索引等值查询命中时，临键锁退化为记录锁**。
  - **唯一索引等值查询未命中时，临键锁退化为间隙锁**。

## 二、InnoDB 行锁的触发逻辑与验证

### 1. 关键前提条件

- **隔离级别**：
  - **间隙锁在 `REPEATABLE READ`（RR）级别下默认生效，用于防止幻读**。
  - **`READ COMMITTED`（RC）级别下间隙锁默认关闭**。但官方文档明确指出，在**外键约束检查和重复键检查**时，RC 级别下**仍然可能使用间隙锁**，这是为了保证数据完整性。MySQL 8.0 中此行为未改变。
- **当前读操作**：
  - 间隙锁/临键锁仅在当前读（`FOR UPDATE`/`LOCK IN SHARE MODE`/`UPDATE`/`DELETE`）时触发。
  - 普通 `SELECT`（快照读）通过 MVCC 实现一致性，不加锁。
  - **`UPDATE` 和 `DELETE` 的锁行为**：与 `SELECT ... FOR UPDATE` 完全一致。根据 MySQL 官方文档，锁定读、UPDATE 或 DELETE 通常会对 SQL 语句处理过程中扫描的每个索引记录设置记录锁（通常是临键锁）。

### 2. 加锁行为的核心规则（基于 MySQL 8.0）

| 查询条件 | 唯一索引（主键）行为 | 普通索引行为 |
|---|---|---|
| **等值查询命中记录** | **临键锁退化为记录锁** | **临键锁（记录锁+左侧间隙） + 右侧间隙锁**（即锁定记录及两侧间隙）<br>注：右侧间隙锁锁定到下一个不同键值（不含该键值本身） |
| **等值查询未命中记录** | **临键锁退化为间隙锁** | **临键锁退化为间隙锁** |
| **范围查询** | **临键锁**，覆盖所有扫描区间，并扩展至不满足条件的第一个值。已命中的唯一索引记录仅加记录锁（不升级为临键锁） | **临键锁**，扫描到的每个区间都加临键锁 |

**重要补充**：
- 范围查询时，InnoDB 会向右遍历直到不满足条件，并对最后一个不满足条件的值所在的间隙加锁（如果该值不存在，则锁到正无穷）。
- 唯一索引范围查询：命中条件的记录加记录锁，间隙锁添加至不满足条件的第一个实际索引值（或正无穷）。

## 三、数据验证：不同场景下的锁行为（基于 MySQL 8.0，RR 隔离级别）

### 1. 表结构与初始数据

```sql
CREATE TABLE user (
  id INT PRIMARY KEY,
  age INT,
  name VARCHAR(10),
  KEY idx_age (age)
);
INSERT INTO user VALUES 
(1, 20, 'A'), 
(2, 25, 'B'), 
(3, 30, 'C');
```

**索引分布**：`id`（主键）: 1,2,3；`age`（普通索引）: 20,25,30。

### 2. 场景验证

#### （1）等值查询未命中记录（间隙锁）

- **唯一索引未命中**：
  
  ```sql
  START TRANSACTION;
  SELECT * FROM user WHERE id = 4 FOR UPDATE;  -- 间隙锁 (3, +∞)
  ```
  
  **验证**：
  - `INSERT INTO user VALUES (4, 35, 'D');` → **被阻塞**。
  - `UPDATE user SET age=35 WHERE id=3;` → **成功**（间隙锁不阻止修改已有记录，且新age=35不涉及主键间隙）。
- **普通索引未命中**：
  
  ```sql
  START TRANSACTION;
  SELECT * FROM user WHERE age = 27 FOR UPDATE;  -- 间隙锁 (25, 30)
  ```
  
  **验证**：
  - `INSERT INTO user VALUES (4, 27, 'D');` → **被阻塞**。
  - `UPDATE user SET age=27 WHERE id=2;` → **被阻塞**。原因：更新age从25改为27，新值27落在间隙(25,30)内，插入二级索引时需要插入意向锁，与间隙锁冲突。

> **结论**：间隙锁仅阻止插入，并**阻止将已有记录更新到间隙内的值**（因为需要插入新索引项）。

#### （2）等值查询命中记录

- **唯一索引命中**：
  
  ```sql
  START TRANSACTION;
  SELECT * FROM user WHERE id = 2 FOR UPDATE;  -- 临键锁退化 → 仅记录锁 (id=2)
  ```
  
  **验证**：
  - `INSERT INTO user VALUES (4, 27, 'D');` → **成功**（间隙 (3,+∞) 未被锁）。
  - `UPDATE user SET age=27 WHERE id=2;` → **被阻塞**（记录锁冲突）。
- **普通索引命中**：
  
  ```sql
  START TRANSACTION;
  SELECT * FROM user WHERE age = 25 FOR UPDATE;  -- 临键锁：(20,25] + 间隙 (25,30)
  ```
  
  **验证**：
  - `INSERT INTO user VALUES (4, 24, 'D');` → **被阻塞**（插入 24 落入 (20,25]）。
  - `INSERT INTO user VALUES (4, 26, 'D');` → **被阻塞**（插入 26 落入 (25,30)）。
  - `UPDATE user SET age=26 WHERE id=2;` → **被阻塞**（需插入新索引项26到(25,30)间隙）。

> **结论**：普通索引等值查询命中时，**必须加临键锁（记录锁+左侧间隙）和右侧间隙锁**，防止插入重复值或更新到间隙内。

#### （3）范围查询

```sql
START TRANSACTION;
SELECT * FROM user WHERE age > 20 AND age < 30 FOR UPDATE;
```

**加锁范围**：
- `(20,25]`（记录 `id=2` + 间隙 `(20,25)`）。
- `(25,30]`（记录 `id=3` + 间隙 `(25,30)`）。

**验证**：
- `INSERT INTO user VALUES (4, 22, 'D');` → **被阻塞**。
- `INSERT INTO user VALUES (4, 28, 'D');` → **被阻塞**。

**唯一索引范围查询示例**（修正后的正确示例）：
```sql
-- 表中仅有 id=1,2,3 时
SELECT * FROM user WHERE id BETWEEN 2 AND 5 FOR UPDATE;
```
- **实际加锁结果**：对 `id=2` 和 `id=3` 加**记录锁**；对间隙 `(3, +∞)` 加**间隙锁**。
- **补充说明**：因为 `id=4` 和 `id=5` 均不存在，InnoDB 会从 `id=3` 开始向右扫描，直到遇到第一个不满足 `id <= 5` 的记录（实际不存在，即到达正无穷），因此锁住整个后续间隙。如果表中存在 `id=6`，则加锁范围会变为：`id=2,3` 记录锁 + 间隙锁 `(3,6)`。

### 3. 特殊陷阱与补充说明

#### （1）全表扫描导致锁范围过大（RR 隔离级别下）

```sql
START TRANSACTION;
SELECT * FROM user WHERE name = 'A' FOR UPDATE;  -- name 无索引
```

**加锁行为**：
- InnoDB 对所有扫描到的记录加临键锁（因无法定位具体行）。
- 技术上 **并未升级为表锁**，但由于锁住了所有行的记录锁和间隙锁，**并发性能急剧下降**，等效于全表阻塞。

**官方文档依据**：MySQL 8.0 官方参考手册明确指出：“如果您没有适合您语句的索引，并且 MySQL 必须扫描整个表来处理语句，那么**表的每一行都会被锁定**，这反过来又会阻止其他用户向表中插入数据。”

**验证**：
- 事务 B 执行 `INSERT`/`UPDATE` 可能全部被阻塞。

#### （2）唯一索引等值查询的优化

```sql
START TRANSACTION;
SELECT * FROM user WHERE id = 2 FOR UPDATE;  -- 临键锁退化为记录锁
```

- 唯一索引命中时，由于唯一性已保证无插入风险，**临键锁退化为记录锁**。
- 普通索引命中时，仍需保留右侧间隙锁以防止幻读。

#### （3）MySQL 8.0 中已移除的参数 `innodb_locks_unsafe_for_binlog`

该参数在 MySQL 5.7 中已废弃，MySQL 8.0 中完全移除。若在配置文件中使用该参数，启动时会报警告且不生效。

## 四、关键结论与误区澄清

### 1. 核心规则总结

- **间隙锁单独存在的条件**：当查询**未命中任何记录**时（无论唯一索引或普通索引），InnoDB 仅加间隙锁。此时唯一索引未命中时临键锁退化为间隙锁，普通索引未命中时加间隙锁。
- **临键锁的触发条件**：当查询**命中至少一条记录**时，InnoDB 使用临键锁。
  - 唯一索引等值命中 → 临键锁退化为记录锁（优化）。
  - 普通索引等值命中 → **临键锁（记录锁+左侧间隙）+ 右侧间隙锁**。
  - 范围查询 → 临键锁覆盖所有扫描区间，唯一索引范围查询已命中的记录仅加记录锁，间隙锁扩展至下一个实际存在的索引值或无穷。
- **RC 级别间隙锁例外**：RC 级别默认无间隙锁，但外键约束检查和重复键检查时仍可能产生间隙锁。

### 2. 常见误区修正

- **误区**：间隙锁仅在唯一索引未命中时存在。  
  **正解**：普通索引未命中时同样仅加间隙锁（如 `WHERE age=27` 无记录）。
- **误区**：普通索引等值查询命中时只加记录锁。  
  **正解**：必须加临键锁（记录锁+左侧间隙）及右侧间隙锁，防止插入重复值或更新到间隙内。
- **误区**：间隙锁会阻止已有记录的修改。  
  **正解**：间隙锁**仅阻止插入**，但**会阻止将已有记录更新到间隙内的值**（因为需要插入新索引项）。
- **误区**：全表扫描时 InnoDB 行锁会升级为表锁。  
  **正解**：技术上仍使用临键锁，但由于锁住了所有行，实际效果等效于表锁，但机制不同。

### 3. 插入意向锁（Insert Intention Lock）补充说明

- **定义**：一种特殊的间隙锁，在 `INSERT` 操作前获取，表示事务准备在某个间隙中插入新记录。
- **冲突规则**：插入意向锁与间隙锁冲突（一个事务持有间隙锁时，另一个事务的插入意向锁必须等待）。
- **重要特性**：多个事务的插入意向锁指向**不同位置**时可以共存，不互相阻塞。
- **典型死锁场景**：事务 A 持有间隙锁，事务 B 也持有间隙锁（间隙锁之间兼容），然后 A 和 B 分别尝试插入不同位置，各自等待对方释放间隙锁 → 形成循环等待，死锁发生。

### 4. 锁监控方法（MySQL 8.0 推荐）

- **查询当前锁信息**（替代 MySQL 5.7 的 `information_schema.INNODB_LOCKS`）：
  ```sql
  SELECT * FROM performance_schema.data_locks;
  ```
  该表显示当前持有的锁和等待的锁，包括锁类型、锁模式、锁状态（GRANTED/WAITING）、被锁数据等。
- **查询锁等待关系**：
  ```sql
  SELECT * FROM performance_schema.data_lock_waits;
  ```
  该表显示哪些锁请求被哪些锁阻塞，用于定位锁等待链。
- **查看事务信息**：
  ```sql
  SELECT * FROM information_schema.INNODB_TRX;
  ```

### 5. 开发建议

- **优先使用唯一索引等值查询**：命中时退化为记录锁，**减少锁范围**。
- **避免普通索引范围查询**：易触发大范围临键锁（如 `WHERE status='pending'` 可能锁住整个状态区间）。
- **务必走索引**：通过 `EXPLAIN` 确认查询路径，**避免全表扫描导致的锁范围过大**。
- **隔离级别选择**：
  - 需严格防幻读 → `REPEATABLE READ`（默认使用临键锁）。
  - 高并发且可接受幻读 → `READ COMMITTED`（仅用记录锁，RC 下 InnoDB 默认无间隙锁）。
- **死锁防范**：
  - 缩短事务，尽快提交释放锁。
  - 统一资源访问顺序。
  - 应用层实现死锁重试（错误 1213）。

---

**最终验证逻辑**：  
锁行为始终遵循 **“是否命中记录”** 这一核心逻辑，**与索引类型相关但具体规则不同**。间隙锁与记录锁的组合机制，本质是 **通过最小锁范围实现隔离性与性能的平衡**。本文档所有断言均经 MySQL 8.0 官方文档确认或实际数据库验证。
