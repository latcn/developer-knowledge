## 第一章 架构总览：从“存取”推导出分层大厦

**根本问题**：大量数据需要**可靠、高效**地存取，允许多人并发，数据量可远超内存，且系统随时可能断电或崩溃。  
**硬约束**：磁盘 I/O 慢于内存数个数量级，顺序访问远快于随机访问，硬件资源有限，并发控制必须保证数据正确。

从这些约束出发，分层架构是必然选择：

1. **连接层**：管理客户端连接、认证、线程复用（线程池避免频繁创建销毁线程）。
2. **服务层**：SQL 解析、优化器、执行器、视图、存储过程、内置函数等。
3. **引擎层**：插件式存储引擎，以 InnoDB 为主，通过 handler API 与上层交互。
4. **存储层**：文件系统、磁盘、OS 缓存。

**类比**：图书馆前台（连接层）接收读者请求，转给参考馆员（服务层），馆员翻译成书架编号，库房管理员（引擎层）去书库（存储层）取书。更换管理员不影响前台和馆员。

**查询执行路径**：连接认证→解析器生成解析树→预处理器解析表名列名、检查权限→优化器基于统计信息生成执行计划→执行器通过存储引擎 API 逐行获取数据→返回结果。

**为什么优化器与执行器分开**：优化是 NP-hard，需编译式处理；执行需流式、可暂停，能分批返回结果。

**本章精要**：分层架构不是设计出来的，而是在磁盘慢、并发高、需求多变等硬约束下，通过职责分离“不得不”形成的自然结构。

## 第二章 核心数据结构与算法

### 2.1 InnoDB 页结构：精心设计的“集装箱”

磁盘 I/O 最小单位是**页**（默认 16KB）。一个数据页内部包含：

- **File Header（38 字节）**：校验和、页号、前后页指针（构成双向链表）、LSN。
- **Page Header（56 字节）**：记录数、槽数量、最近插入位置、页方向等，用于空间管理与一致性检查。
- **Infimum / Supremum**：虚拟最小/最大记录，充当边界哨兵。
- **User Records**：实际行数据，按主键顺序以单向链表排列。
- **Page Directory**：将记录稀疏分组，每组最后一条记录的偏移量存入“槽”，实现页内二分查找。
- **File Trailer（8 字节）**：尾部校验和与 LSN，用于页完整性检查。

**类比**：一页纸有侧边索引标签（页目录），查找时先看标签二分定位，再在组内顺序寻找，时间复杂度远优于遍历。

#### 2.1.1 Doublewrite Buffer：防止部分写入的“复写纸”

**根本问题**：操作系统或硬件可能在任何时刻断电，导致 InnoDB 正在写入的 16KB 数据页仅部分写入磁盘（Partial Page Write）。虽然页的 File Trailer 含有校验和能发现错误，但仅依靠 redo log 无法恢复——因为 redo log 记录的是基于完整页的物理偏移修改，如果页本身已损坏，重放 redo 也无济于事。

**第一性推导**：必须有一个安全机制，既能保护写入中的页，又不增加太多性能开销。解决方案是：在写入真正数据文件之前，**先把页连续写到一个独立的、顺序的磁盘区域**（Doublewrite Buffer），然后再随机写入实际位置。因为顺序写入是原子的或可恢复的，即使实际位置发生部分写入，也可以从 Doublewrite 区域拿回完整的副本重写，确保页的原子性。

**实现**：
1. InnoDB 在系统表空间（或独立文件 `#ib_16384_*` 中）预留 2MB 的连续区域作为 Doublewrite Buffer（128 个页）。
2. 当需要刷新脏页时，先将一批页**顺序**写入 Doublewrite Buffer，再**随机**写入各自的表空间位置。
3. 如果崩溃恢复时检测到某个页的校验和不匹配，就从 Doublewrite Buffer 中找到该页的完好副本，覆盖损坏的页。

**费曼类比**：就像写一份重要文件时，先用复写纸在另一张纸上留个底，再正式填写。如果填写时笔没水了（部分写入），可以从复写纸上把完整的字迹描回去。

**与 redo log 的分工**：
- **Doublewrite**：保证单个页写入的原子性，防止“破碎页”。
- **Redo log**：保证事务修改的持久性，恢复未刷盘的改动。
- 两者缺一不可：Doublewrite 让页本身是完好的，redo 才能正确应用修改。

对于支持原子写（Atomic Write）的存储（如部分 NVMe SSD），可安全关闭 Doublewrite（`innodb_doublewrite=OFF`），以获得更高性能。

### 2.2 B+Tree 与索引原理

**为什么是 B+Tree**：二叉树/红黑树深度大导致多次随机 I/O；B-Tree 非叶存数据，范围扫描效率低；B+Tree 只在叶子存数据，叶子形成双向链表，范围查询可直接顺序扫描链表，极大减少随机 I/O。

**聚簇索引**：叶子节点存放整行数据，按主键顺序组织。主键大小直接影响所有二级索引大小。

**二级索引与回表**：二级索引叶子存储“索引列 + 主键值”，若查询需要其他列，则必须根据主键回聚簇索引查整行，即**回表**。**覆盖索引**指查询列全部包含在二级索引中，无需回表。

**联合索引与最左前缀**：联合索引 `(A,B,C)` 先按 A 排序，A 相同按 B，B 相同按 C。推导出：
- 条件缺前导列则无法使用索引排序特性。
- 范围条件后的列无法用于索引缩小扫描范围（ICP 可下推部分过滤，但不会减少扫描行数）。

**索引第一性**：索引的目的是减少扫描数据量，其顺序决定比较次数和扫描区间大小。

### 2.3 缓冲池与变更缓冲

- **缓冲池**：内存缓存数据页，使用改进 LRU（分 Young/Old 区），防止全表扫描冲刷热数据。自适应哈希索引自动为频繁点查建立哈希索引。
- **变更缓冲（Change Buffer）**：对非唯一二级索引的插入、更新、删除，若目标索引页不在缓冲池，暂存修改，待被读取或后台合并时再写入，减少随机读 I/O。

### 2.4 页分裂机制完全解析

**为什么需要分裂**：当向已满页插入新记录时，必须分裂成两页以保持主键顺序。

**分裂过程（插入 25，页 A 满）**：
1. 分配新页 B。
2. 数据迁移策略（分裂点根据记录大小动态决定，大约一半）：
   - **自增主键（右分裂优化）**：A 不动，新记录直接插入新页 B，B 初始只有一条，后续插入继续追加到 B 直至 B 满。**无数据移动**。
   - **非自增/随机插入**：将原页 A 大约后一半记录移到 B，使两页各有约 50% 空闲，然后插入 25 到对应页。**移动一半目的是给旧页留空间，避免后续插入落在旧页范围时立即再次分裂。**
3. 调整链表指针：`A → B → 原下一页 C`。
4. 更新父节点索引项，可能触发递归分裂。
5. 插入新记录。

**澄清**：
- *为什么随机插入要移动一半，而不是只把 25 放新页？* 只放新页则旧页仍满，后续若插入落在旧页范围（如 8）会立即再分裂。移动一半可减少连续分裂。
- *分裂后 A 半满会一直空着吗？* 自增下不存在此问题；随机插入下后续数据会填充；若长期低填充率（低于 `MERGE_THRESHOLD`，默认 50%），InnoDB 后台页合并机制会合并相邻页回收空间。

**自增主键优势**：总是往最右侧追加，分裂无需移动旧数据，空间利用率高，碎片少。

### 2.5 事务、隔离级别与 MVCC

**根本矛盾**：多个用户同时读写，既要保证正确性，又要尽量提高并发。

#### 2.5.1 ACID 与隔离级别

- **原子性（Atomicity）**：事务要么全做，要么全不做，通过 undo log 回滚实现。
- **一致性（Consistency）**：业务与数据库约束共同保证。
- **隔离性（Isolation）**：并发事务相互影响的程度。SQL 标准定义了四种隔离级别（由低到高）：
  - **读未提交（Read Uncommitted）**：可以读到未提交数据（脏读），几乎不用。
  - **读已提交（Read Committed，RC）**：只能读到已提交数据，但同一事务内两次相同快照读可能得到不同结果（不可重复读）。
  - **可重复读（Repeatable Read，RR）**：同一事务内多次快照读结果一致；InnoDB 通过 Next-Key Lock 也在加锁读中消除了幻读。
  - **可串行化（Serializable）**：事务完全串行执行，并发度最低。
- **持久性（Durability）**：提交的事务不会丢失，通过 redo log 和 WAL 保证。

#### 2.5.2 MVCC 实现原理

**第一性推导**：读写锁会导致读写互相阻塞，高并发下性能极差。MVCC 的思想是：写操作创建数据的新版本，读操作根据事务开始时的快照读取旧版本，从而实现无锁快照读。

InnoDB 的 MVCC 基于三个隐藏列和 undo 版本链：

- 每行记录含有：
  - `DB_TRX_ID`：最近修改该行的事务 ID。
  - `DB_ROLL_PTR`：回滚指针，指向 undo log 中该行的上一个版本。
  - `DB_ROW_ID`（表无主键时）：内部主键。
- 更新一行时，先将当前值写入 undo log（记录旧版本），再修改数据页上的值，并更新 `DB_TRX_ID` 和 `DB_ROLL_PTR`，形成一条从新到旧的版本链。

**快照读的可见性判断**：事务**执行第一个快照读时**会生成一个 **ReadView**，包含：
- `m_ids`：当前系统中活跃（未提交）的事务 ID 列表。
- `min_trx_id`：活跃事务中最小的事务 ID。
- `max_trx_id`：系统下一个待分配的事务 ID（即已分配最大 ID + 1）。

对于某行数据的版本，判断规则：
1. 若 `DB_TRX_ID == 当前事务 ID`：说明是自己修改的，**总是可见**。
2. 若 `DB_TRX_ID < min_trx_id`：说明修改该版本的事务在 ReadView 创建前已提交，**可见**。
3. 若 `DB_TRX_ID >= max_trx_id`：说明修改该版本的事务在 ReadView 创建后才开始，**不可见**。
4. 若 `min_trx_id <= DB_TRX_ID < max_trx_id`：需判断 `DB_TRX_ID` 是否在 `m_ids` 中。若在，则未提交，不可见；若不在，则已提交，可见。

若当前版本不可见，则通过 `DB_ROLL_PTR` 沿版本链找上一个版本继续判断，直到找到可见版本为止。

**RC 与 RR 的实现差异**：
- **RC**：每次快照读都生成一个新的 ReadView，因此能看到其他事务已提交的修改（不可重复读）。
- **RR**：在事务的第一个快照读时生成一个 ReadView，整个事务期间复用，因此始终看到相同的数据快照，实现可重复读。

**Purge 线程**：当旧版本不再被任何活跃事务的 ReadView 需要时，InnoDB 的后台 Purge 线程会异步清理这些 undo 记录，回收空间。

### 2.6 日志系统与数据关系

**根本矛盾**：内存快但易失，磁盘慢但持久。通过 WAL（Write-Ahead Logging）将随机写转为顺序写。

#### 一次 UPDATE 的完整旅程：`UPDATE users SET age = 30 WHERE id = 100`（原 age=25）

1. 查找并锁定 `id=100` 的记录。
2. **写 undo log**：记录“如何回滚到 age=25”。undo 页修改受 redo 保护。
3. **修改缓冲池数据页**：age→30，更新 `DB_TRX_ID`（当前事务ID）和 `DB_ROLL_PTR`（指向新 undo 记录）。页变脏。
4. **写 redo log**：物理记录“页 Y 偏移 Z 写入 30”，追加顺序写。
5. **写 binlog**：逻辑记录 `UPDATE users SET age=30 WHERE id=100`（行格式下为前后镜像），追加顺序写。
6. **两阶段提交**：redo prepare → 写 binlog → redo commit，保证一致。
7. 后台刷脏页时，Doublewrite Buffer 保证页的原子写入，随后完成随机写。

**顺序写体现在**：redo log 和 binlog 的追加写是纯顺序 I/O，数据页的随机写被推后。

#### 三种日志与索引叶子数据的关系

- **聚簇索引叶子节点**：存储行的**当前最新版本**（含隐藏列 `DB_TRX_ID`、`DB_ROLL_PTR`）。
- **undo log**：保存历史版本，形成版本链。MVCC 读旧版本即沿 `DB_ROLL_PTR` 回溯。为回滚和 MVCC 服务。
- **redo log**：物理日志，保护所有对数据页（包括索引页和 undo 页）的修改。崩溃恢复时重放已提交但未刷盘的脏页。是**叶子数据的“保险丝”**。
- **binlog**：服务层逻辑日志，描述 SQL 或行变化，用于复制和 PITR。是**叶子数据变化的“翻译官”和传播者**。

**一句话**：叶子数据是当前状态，undo 提供回到过去，redo 保证不丢失，binlog 传播变化。

## 第三章 主要功能深层解析（完整扩展版）

### 3.1 查询处理流程：一条 SQL 的完整生命周期

#### 3.1.1 连接与线程管理
- 每连接一线程，线程池限制并发数。
- `max_connections` 打满时，`extra_max_connections`（8.0.28+）可保留管理通道。

#### 3.1.2 查询缓存（8.0 已移除）
- 失效粒度粗、锁竞争严重、命中条件苛刻，高并发下成为瓶颈。

#### 3.1.3 解析器
- 词法分析→Token，语法分析→解析树。

#### 3.1.4 预处理器
- 表/列名解析、权限检查、类型兼容性初步判断。

#### 3.1.5 优化器（CBO）
- 利用统计信息（表行数、索引基数、直方图）和代价模型（I/O、CPU、内存）选择代价最小的执行计划。
- **Join 算法**：
  - **Nested-Loop Join**：被驱动表有索引，每次索引查找 O(log N)。
  - **Hash Join**：构建表建哈希，探测表逐行探测，复杂度 O(M+N)。自 8.0.18 引入，并在 8.0.20 完全替代 Block Nested-Loop Join。当哈希表超过 `join_buffer_size` 时会溢出到磁盘。
- **子查询优化**：物化、半连接转换（Semi-Join）；无法优化时外层每行执行一次子查询（`DEPENDENT SUBQUERY`），性能极差，应用 JOIN 重写。
- 执行计划可缓存（Plan Cache），对 Prepare Statement 有益。

#### 3.1.6 执行器
- 根据执行计划调用存储引擎 handler API，流式返回结果。
- 若需排序或分组且无法用索引，使用临时表（`Using temporary`）。

### 3.2 现代关键特性（8.0+）

#### 3.2.1 公用表表达式（CTE）与递归 CTE
- CTE：命名临时结果集，可多次引用，提高可读性。
- 递归 CTE：遍历层次结构数据（组织树、BOM），通过 `UNION ALL` 递归直到空集，受 `cte_max_recursion_depth` 限制。

#### 3.2.2 窗口函数
- 不折叠行，在窗口上计算排名、累计、滑动平均等，支持 `PARTITION BY`、`ORDER BY` 和窗口范围帧。

#### 3.2.3 原子 DDL
- DDL 操作包装为事务，基于新数据字典，要么完全成功要么回滚，防止元数据不一致。

#### 3.2.4 不可见索引
- 删除索引前设为不可见以安全测试，`optimizer_switch` 可让优化器忽略。

#### 3.2.5 降序索引
- 索引可指定 `DESC`，支持 `ORDER BY col1 ASC, col2 DESC` 直接使用索引避免 filesort。

#### 3.2.6 `CROSS JOIN LATERAL`：让派生表“看得见”左边

**根本问题**：传统派生表不能引用同一 `FROM` 子句中前面的表列，导致某些逐行驱动的查询难以表述。

**原理**：`LATERAL` 关键字允许右侧派生表引用左侧表的列，左侧每一行都会触发一次右侧子查询，结果横向拼接。类似相关子查询，但可以返回**多行**。

**类比**：拿着部门清单，每看到一个部门就去员工表查该部门薪资前 3 名，而不是先全表关联再过滤。

**示例**（每个部门薪资前 3 名）：
```sql
SELECT d.name, e.emp_name, e.salary
FROM departments d
CROSS JOIN LATERAL (
  SELECT emp_name, salary
  FROM employees
  WHERE department_id = d.id
  ORDER BY salary DESC
  LIMIT 3
) e;
```

**适用场景**：分组 Top-N 查询；生成关联数据序列；订单最近的 N 条物流记录。

**性能与注意**：当左侧行数少且右侧能有效利用索引时性能极高；否则可能退化 N 次扫描；`LEFT JOIN LATERAL ... ON TRUE` 可保留左侧行即使右侧无结果。

### 3.3 其他功能的深层解析

#### 3.3.1 视图（View）
- 可简化复杂查询，执行时采用 MERGE（展开合并）或 TEMPTABLE（物化）。
- 多层视图嵌套可能导致优化器难以优化，建议复杂查询直接写 SQL 并审查计划。
- MySQL 原生无物化视图，需自行模拟。

#### 3.3.2 存储过程、函数与触发器
- 可减少网络交互，但调试困难、移植性差、隐式性能杀手。
- 复制时可能引入不一致（STATEMENT 格式下非确定性逻辑）。
- **第一性建议**：数据库专注存取，业务逻辑尽量放在应用层。若必须使用，保持简单、有日志、团队周知。

#### 3.3.3 分区表
- 支持 RANGE、LIST、HASH、KEY 分区，主要收益：分区剪裁、快速数据删除。
- **严格限制**：所有唯一索引（含主键）必须包含分区键；查询不带分区键会扫所有分区；分区数过多会导致元数据开销大；不支持外键。
- 最适合按时间归档的流水型数据，不推荐用于复杂 OLTP。

#### 3.3.4 全文索引
- 基于倒排索引的文本搜索，适合轻量级场景，专业搜索建议用 Elasticsearch。

### 3.4 复制架构与数据一致性（完整版）

**根本需求**：数据冗余（HA）、读写分离、异地容灾、数据分发。

#### 3.4.1 异步复制
- 主库写 binlog → Binlog Dump 线程发送 → 从库 I/O 线程写 relay log → SQL 线程重放。
- 天然存在延迟，主库宕机可能丢数据。

#### 3.4.2 半同步复制
- 插件已内置，可直接 `INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';`（从库类似用 `rpl_semi_sync_replica`）。
- 主库等待至少一个从库确认收到 binlog 再返回客户端。
- `rpl_semi_sync_source_wait_point = AFTER_SYNC`（默认，最安全）：先写 binlog 等待确认再引擎提交。
- 超时后退化为异步，恢复后自动升回半同步。

#### 3.4.3 并行复制
- 解决从库单线程回放慢导致延迟。
- 5.6：基于 Schema 的并行。
- 5.7：基于 Logical Clock，同组提交事务可并行。
- 8.0：在 `replica_parallel_type = LOGICAL_CLOCK` 下，通过 `binlog_transaction_dependency_tracking = WRITESET` 实现基于写集合的依赖跟踪，无冲突事务均可并行，大幅提升吞吐。
- 配置：`replica_parallel_workers = N`，主库 `binlog_transaction_dependency_tracking = WRITESET`。

#### 3.4.4 组复制（MGR）
- 基于 Paxos 的多主集群，事务需多数派共识才提交。
- 单主模式：只有主写，自动切换；多主模式：所有节点可写，冲突检测回滚。
- 自带流控、自动故障检测，要求网络低延迟。
- InnoDB Cluster 封装 MGR + MySQL Shell + Router，提供完整高可用方案。

#### 3.4.5 一致性边界与陷阱
- 读写分离下从库可能读到过期数据；大事务导致延迟突增；DDL 串行阻塞复制；过滤规则可能引起不一致。

#### 3.4.6 Binlog 格式
- STATEMENT：日志小但可能导致不一致；ROW：强一致推荐，日志量大；MIXED：折中。
- 推荐 ROW + GTID，`binlog_row_image=MINIMAL` 减小日志量。

**本章一句话精要**：查询处理、现代特性、复制功能都是“用空间/时间/复杂度换性能、可用性或表达能力”的权衡艺术。理解每项功能的代价模型和一致性边界，才能在生产中做出正确选择。

## 第四章 锁体系全解：从记录锁到死锁处理

### 4.1 核心原则：“扫描过就可能被锁”
InnoDB 行锁加在**索引记录**上。为防其他事务修改，必须先锁定扫描到的记录再判断条件，因此锁范围等于索引扫描范围，可能远超最终结果集。
- **全表扫描 + 加锁语句**：RC 下 `SELECT ... FOR UPDATE` 锁所有行；RR 下不仅锁所有行还锁所有间隙，**效果等同锁表**。

### 4.2 锁类型详解（均在索引上）

#### 4.2.1 记录锁（Record Lock）
锁定单条索引记录，防修改。
```sql
SELECT * FROM t WHERE id=5 FOR UPDATE;  -- 锁 id=5 的记录
```

#### 4.2.2 间隙锁（Gap Lock）
锁定记录间**间隙**，防插入。**RR 特有**，间隙锁之间不互斥。
```sql
-- 现有 id=5,10
SELECT * FROM t WHERE id=8 FOR UPDATE;  -- 锁 (5,10) 间隙
```

#### 4.2.3 临键锁（Next-Key Lock）
记录锁+前间隙锁，左开右闭区间 `(gap, record]`。RR 默认行锁。
- 唯一索引等值命中会**降级为记录锁**。
- 非唯一索引等值查询会锁住命中记录临键锁和下一间隙锁，范围比预期大。

#### 4.2.4 插入意向锁（Insert Intention Lock）
特殊间隙锁，表明欲插入。与间隙锁冲突，多个插入意向锁若不冲突位置可共存。
```sql
-- A: SELECT ... FOR UPDATE 锁住间隙
-- B: INSERT 被阻塞，等待插入意向锁
```

#### 4.2.5 自增锁（AUTO-INC Lock）
为自增列生成连续值。三种模式（`innodb_autoinc_lock_mode`）：
- 0（传统）：表级锁，语句结束释放。
- 1（连续）：简单插入用互斥量，批量插入用表锁。
- **2（交错，MySQL 8.0 默认）**：完全交错生成，性能最高，但 binlog 为 ROW 格式才安全。

#### 4.2.6 意向锁（Intention Lock）
表级，分 IS/IX，行锁前获取，用于快速检测表级锁冲突。

#### 4.2.7 表锁与元数据锁（MDL）
- 显式 `LOCK TABLES` 不推荐；MDL 保护表结构，DDL 需排他 MDL，阻塞所有读写。

#### 锁兼容矩阵（简化，假设请求锁为 X 锁）
| 已有 \ 请求 | Record X | Record S | Gap | Next-Key X | Insert Intention |
|-----------|----------|----------|-----|------------|------------------|
| Record X  | 冲突 | 冲突 | 兼容 | 冲突 | 兼容 |
| Record S  | 冲突 | 兼容 | 兼容 | 冲突 | 兼容 |
| Gap       | 兼容 | 兼容 | 兼容 | 兼容 | **冲突** |
| Next-Key X| 冲突 | 冲突 | 兼容 | 冲突 | **冲突** |
| Insert Intention | 兼容 | 兼容 | **冲突** | **冲突** | 兼容（不同位置） |

### 4.3 死锁经典案例与解决

**案例：间隙锁不互斥导致死锁**
```sql
-- 现有 id=10,20
-- 会话A: SELECT * FROM t WHERE id=15 FOR UPDATE; -- 锁 (10,20) 间隙
-- 会话B: SELECT * FROM t WHERE id=17 FOR UPDATE; -- 也锁 (10,20) 间隙（兼容）
-- A: INSERT INTO t VALUES (14); -- 等 B 释放间隙锁
-- B: INSERT INTO t VALUES (16); -- 等 A 释放间隙锁 → 死锁
```

**根因**：间隙锁之间兼容，但插入意向锁与间隙锁冲突，形成互相等待。

**解决方案**：
1. **降为 RC 隔离级别**：RC 无间隙锁，彻底消除此类死锁。
2. **使用唯一索引锁定已有记录**：减少间隙锁产生。
3. **改写业务**：`INSERT ... ON DUPLICATE KEY UPDATE` 或先插后处理。
4. **缩短事务**：尽快提交。
5. **应用层死锁重试**（错误 1213）：必备兜底。

**锁监控工具**：
```sql
SELECT * FROM performance_schema.data_locks;  -- 所有锁信息
SELECT * FROM sys.innodb_lock_waits;        -- 锁等待链
SHOW ENGINE INNODB STATUS\G;               -- 最近死锁详情
```

## 第五章 生产常见问题与排查决策树

### 5.1 性能抖动
- 统计信息不准 → `ANALYZE TABLE`。
- 锁阻塞 → `sys.innodb_lock_waits`。
- 脏页刷盘 → 检查 `Innodb_buffer_pool_pages_dirty`，调大 redo log 容量（8.0.30+ 可用 `innodb_redo_log_capacity` 动态调整）。
- 缓冲池预热不足 → 刚重启后抖动。

**排查决策树**：
```
开始 → CPU高 iowait高?
  → CPU用户态高: 大量计算SQL或锁自旋, 查processlist
  → iowait高: 检查磁盘吞吐与脏页比例, 必要时调整redo/磁盘
同时查慢查询和执行计划，对比预估与实际行数，确认锁等待。
```

### 5.2 锁等待/死锁
诊断：`sys.innodb_lock_waits`，`data_locks`。解决：调序、降 RC、加索引、拆事务。

### 5.3 主从延迟
- I/O 线程慢：网络/主库 binlog 产生速度。
- SQL 线程慢：大事务/DDL，开并行复制。
- 监控：`pt-heartbeat`。

### 5.4 连接风暴 / OOM
- 连接池、超时、`max_connections` 调优。
- 缓冲池不超过物理内存 70-80%，限制 `tmp_table_size`。

**排查心法**：将现象映射到 I/O、锁、内存、网络底层机制，逐层确认。

## 第六章 性能调优方法论

**调优五层逻辑**：避免（缓存/归档）→ 减少（索引覆盖/只取所需列）→ 并行（并行复制/并发）→ 缓存（缓冲池）→ 简化（拆分大事务/复杂 SQL）。

### 6.1 SQL 与索引调优
- 读懂 `EXPLAIN`：`type` 从 ALL 到 const，关注 `rows`、`Extra`（`Using filesort`/`temporary` 需优化）。
- **`EXPLAIN ANALYZE`**（8.0.18+）：实际执行查询并返回每步真实时间与行数，可直接对比估算与实际差异。
- 利用覆盖索引、最左前缀，通过**函数索引**（如 `INDEX((YEAR(order_date)))`）优化对列表达式的查询。

### 6.2 参数调优
- 内存：`innodb_buffer_pool_size`（70-80%物理内存）。
- I/O：`innodb_io_capacity`（SSD 可设 2000+）、`innodb_flush_method=O_DIRECT`。
- redo log：8.0.30+ 用 `innodb_redo_log_capacity` 动态调整。
- 复制：`replica_parallel_workers`。

**闭环**：基线→压测→定位瓶颈→调整→验证。

### 6.3 操作系统与硬件
- 文件系统 xfs/ext4 + `noatime`，SWAP 禁用或 `vm.swappiness=1`。
- SSD 调度器现代内核自动设为 `none` 或 `mq-deadline`。

## 第七章 最佳实践与反模式（Checklist）

### 7.1 建表规约
- 必须有主键，短且自增。
- 字段尽量 `NOT NULL`，字符集 `utf8mb4`，排序规则推荐 `utf8mb4_0900_ai_ci`。
- 大字段分离，控制行宽。
- 分区表仅在按分区键查询和数据管理需求明确时使用。

### 7.2 索引规约
- 最左前缀铁律，高选择性列优先。
- 对列表达式优先使用**函数索引**，而非在 WHERE 中直接计算。
- 避免冗余索引（`(A,B)` 可覆盖 `(A)`）。
- 长字段用前缀索引，监控无用索引（`sys.schema_unused_indexes`）。

### 7.3 SQL 编写规约
- 禁止 `SELECT *`，避免 WHERE 列函数/计算（配合函数索引使用）。
- 关联查询被驱动表关联列必须索引。
- 大偏移分页用延迟关联或基于主键的条件优化。
- 大事务拆分，缩短锁持有。

### 7.4 安全与权限
- 最小权限，应用账号不授予 DDL，严格 `sql_mode`。

### 7.5 备份恢复
- **物理热备**：`xtrabackup` 或官方 **Clone Plugin**（8.0.17+，在线物理克隆，极速创建从库）。
- 逻辑备份：`mysqldump`/`mysqlpump`。
- 定期恢复演练，配合 binlog 实现 PITR。

### 7.6 升级与云环境
- 升级前用 MySQL Shell `util.checkForServerUpgrade()` 检查。
- 云上关注 IOPS 限制、备份窗口，监控 Prometheus + `mysqld_exporter`。
