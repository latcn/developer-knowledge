### 0. 第一性原理基础

Java 每次版本演进遵循三个底层约束：

1. 二进制兼容：旧 class 文件能在新 JVM 上运行（除删除的 API）
2. 性能可预测：新特性不能以损害常规代码性能为代价
3. 线程模型与操作系统映射：传统线程是 OS 线程的 1:1 包装；虚拟线程旨在打破此映射，实现 M:N 调度

理解这三点，就能推理出大部分新特性可能出现的生产问题及解决方案。

### 2. 生产问题分类与解决方案

#### 2.1 虚拟线程（Virtual Thread）核心生产问题

这是最值得重点讲解的特性，也是生产问题高发区。

##### 2.1.1 问题分类

| 类别 | 具体问题 | 症状 | 根因 |
|------|----------|------|------|
| **线程局部滥用** | `ThreadLocal` 数量爆炸 | 内存泄漏 | 虚拟线程极多，每个线程的 `ThreadLocal` 存活时间长于任务 |
| **池化思维** | 使用固定线程池包装虚拟线程 | 吞吐量不升反降 | 虚拟线程创建成本极低，池化反而增加调度开销 |
| **同步块阻塞** | `synchronized` 代码块中执行网络 I/O | 载体线程被固定（pinned） | `synchronized` 持有监视器时无法卸载 |
| **本地方法调用** | 虚拟线程执行本地方法 | 载体线程被固定 | 本地栈帧存在时无法安全卸载 |
| **不支持 `Thread.stop()` / `suspend()`** | 调用抛出异常 | 老框架出错 | 虚拟线程不实现这些破坏性方法 |
| **使用 `ThreadGroup`** | 创建虚拟线程到旧 `ThreadGroup` | `UnsupportedOperationException` | 虚拟线程没有 `ThreadGroup` |

##### 2.1.2 挂载与卸载机制

JEP 491 官方文档阐述了虚拟线程的调度模型：

- **挂载（Mount）**：JVM 调度器将虚拟线程分配到**平台线程**（即**载体线程**）上执行，此时虚拟线程的栈帧从堆内存拷贝到载体线程的栈上
- **卸载（Unmount）**：虚拟线程在执行阻塞操作（如 `socket.read()`、`LockSupport.park()`）时，JVM 保存虚拟线程的执行状态到堆中的虚拟线程栈，清空载体线程的栈，使载体线程可执行其他虚拟线程
- 当阻塞操作完成时，虚拟线程重新排队等待调度器再次将其**挂载**到某个载体线程上继续执行

**优点**：一个载体线程可以**时分复用**成千上万个虚拟线程，极大提升硬件利用率。

**卸载失败的情况**：虚拟线程在 `synchronized` 块内阻塞、本地方法调用等，此时无法安全卸载，导致载体线程被固定（pinning）。

##### 2.1.3 `synchronized` pinning 的根本原因

` synchronized` 代码块中，JVM 将**载体线程**记录为监视器的持有者，而不是虚拟线程本身。当虚拟线程在此类代码块中阻塞时，JVM 无法安全地卸载它，因为载体线程的栈上已存在 `synchronized` 相关的锁记录，强行卸载会破坏监视器的状态一致性。

Java 22 及更早版本中，当虚拟线程在 `synchronized` 代码块中阻塞时，载体线程会被固定，无法承载其他虚拟线程。

##### 2.1.4 解决方案与最佳实践

**Java 21-23（pinning 存在）：**

1. **用 `ScopedValue` 替代 `ThreadLocal`**（Java 21 预览 / 25 正式）：作用域限定，任务结束后自动清理

   ```java
   // Java 21 预览（需 --enable-preview） / Java 25 正式
   private static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();
   ScopedValue.where(REQUEST_ID, "req-123").run(() -> handleRequest());
   ```

2. **不要使用线程池**：直接使用 `Executors.newVirtualThreadPerTaskExecutor()`

3. **规避 `synchronized` pinning**：

   ```java
   // Java 21-23：使用 ReentrantLock 替代 synchronized
   private final Lock lock = new ReentrantLock();
   lock.lock();
   try {
       httpClient.send(...);
   } finally {
       lock.unlock();
   }
   ```

   **重要说明**：`synchronized` 替换为 `ReentrantLock` 能解决大多数问题，但不能解决本地方法调用场景下的 pinning。完整解决方案依赖 JEP 491（Java 24+）。

4. **检测 Pinning**：

   ```bash
   # 检测并打印完整堆栈
   -Djdk.tracePinnedThreads=full
   ```

5. **设置全局未捕获异常处理器**：

   ```java
   Thread.setDefaultUncaughtExceptionHandler((t, e) -> log.error("Virtual thread died", e));
   ```

**Java 24+（pinning 根本解决，JEP 491）：**

JEP 491（Synchronize Virtual Threads without Pinning）在 **Java 24** 中正式交付，从根本上解决了 pinning 问题。其核心方案是将 `synchronized` 的锁记录从载体线程栈移到堆上（类似 `ReentrantLock` 的实现），使虚拟线程在 `synchronized` 块内也能安全卸载。升级到 Java 24 或更高版本后，无需对现有代码做任何修改，虚拟线程即可在 `synchronized` 环境中正常卸载。

##### 2.1.5 虚拟线程 vs 传统线程池对比

| 维度 | 虚拟线程 | 传统线程池（平台线程） |
|------|----------|------------------------|
| **创建成本** | 极低（内存 ~ 几百字节初始栈） | 高（默认 1MB 栈 + OS 资源） |
| **最大并发数** | 百万级（受限于堆内存） | 数千（受限于 OS 线程数） |
| **阻塞操作** | 阻塞时自动卸载，不浪费 CPU | 阻塞时 OS 线程仍占用内存和上下文 |
| **编程模型** | 同步、命令式（像普通线程一样写） | 通常需要异步回调、CompletableFuture |
| **池化必要性** | **无需池化**，直接创建即可 | **必须池化**，否则创建开销巨大 |
| **适合场景** | I/O 密集型、高并发、任务短且多 | CPU 密集型、需要精确控制线程数 |
| **pinning 问题（Java 21-23）** | 存在，`synchronized` 和本地方法导致固定 | 无 |
| **pinning 问题（Java 24+）** | **已根本解决（JEP 491）** | 无 |

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `jdk.virtualThreadScheduler.parallelism` | `availableProcessors()` | 平台线程数，控制并发度 |

##### 2.1.7 生产监控

#### 2.2 结构化并发（预览特性，Java 21）

**重要提示**：结构化并发在 Java 21 中是预览特性（JEP 453），需 `--enable-preview` 启用。API 在未来版本中可能变化，**不建议在当前生产环境中使用**。

**问题类型**：
- 忘记在 `finally` 中关闭 `StructuredTaskScope`，导致子线程泄漏
- 混用虚拟线程和平台线程作用域时，关闭顺序错误死锁

**解决方案**：
使用 **try-with-resources** 模式。

```java
// Java 21 预览特性，需要 --enable-preview
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String> user = scope.fork(() -> fetchUser());
    Subtask<Integer> order = scope.fork(() -> fetchOrder());
    scope.join();
    scope.throwIfFailed();
    return new Response(user.get(), order.get());
}
```

#### 2.3 外部函数与内存 API

**重要提示**：FFM API 在 Java 21 中是预览特性（JEP 442），正式版本在 Java 22（JEP 454）发布。

**生产级安全写法（Java 22+ 正式）**：

```java
// Java 22+ 正式版本：使用 Arena 管理内存
try (Arena arena = Arena.openConfined()) {
    MemorySegment cString = arena.allocateUtf8String("hello");
    puts.invokeExact(cString);
}
```

**Java 21 中的限制**：
- FFM API 是预览特性，需添加 `--enable-preview` 和 `--add-modules jdk.foreign`

#### 2.4 向量 API（孵化状态，Java 21）

**重要提示**：向量 API 在 Java 21 中是第六次孵化状态（JEP 448），不是正式特性。由于 Valhalla 项目尚未稳定，API 设计仍可能变化。

**生产环境建议**：向量 API 仍是孵化状态，不建议在生产关键路径中使用。Java 21.0.3 中存在已知的向量化退化 Bug（AVX-512 指令退化到标量循环），请升级到更高版本或等待 Valhalla 稳定。
