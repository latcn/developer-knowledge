## 第零章：Redis 的设计本质与第一性原理

### 0.1 设计目的
Redis 的核心目的是提供**亚毫秒级延迟的内存数据存储**，通过丰富的数据结构和原子操作，支撑高并发、低延迟的缓存、会话存储、计数器、消息队列等场景。

### 0.2 解决的根本问题
1. **速度不匹配**：传统磁盘数据库 I/O 瓶颈 → 全内存操作，读写延迟约 0.1ms。
2. **数据结构多样性**：键值存储无法高效支持排行榜、消息队列、去重集合 → 原生支持 String、Hash、List、Set、Sorted Set、Stream、Bitmap、HyperLogLog、Geo。
3. **扩展性与高可用**：单机内存有限，需分布式方案 → 主从复制、哨兵、集群。

### 0.3 适用场景
- 高速缓存（页面缓存、热点数据）
- 实时计数器（点赞、播放量）
- 分布式会话管理
- 排行榜 / 延时队列（Sorted Set）
- 分布式锁（Redlock / SET NX）
- 消息队列（Stream / Pub/Sub）
- 地理位置服务（Geo）

### 0.4 核心设计矛盾与原则映射
| 矛盾 | 对应原则 |
| :--- | :--- |
| 可靠性 vs 性能 | 原则1（持久化）、原则2（复制） |
| 顺序性 vs 并行度 | 原则4（集群分区） |
| 一致性 vs 可用性 | 原则2（异步/同步复制） |
| 内存容量 vs 成本 | 原则3（内存优化） |

### 0.5 原则规划与推理草稿
基于用户需求（Redis、关注全维度），规划以下7个原则域：
1. [D2 数据容错] → 持久化（RDB/AOF）
2. [X4 冗余复制] → 主从复制 + 哨兵/集群
3. [X13 成本优化] → 内存优化（淘汰策略、压缩）
4. [X5 分区扩展] → Redis Cluster 水平扩展
5. [X1 一致性模型] → 异步/同步复制、事务、Lua
6. [X10 可观测性] → 慢日志、监控、Trace
7. [X9 安全防御] → 密码、TLS、ACL

**推理草稿**：放弃 N2（通信容错）因为 Redis 网络模型已经高效；长事务不适用 Redis（建议用 Lua 原子性替代）。

## 原则 1：数据持久化与容错（D2）

### 1.1 第一性原理
- **物理/数学约束**：内存数据断电丢失，磁盘写入慢但持久。
- **推导**：必须将内存数据异步/同步写入磁盘，但写入频率影响性能。

### 1.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| RDB 快照 | 定期 fork 子进程 dump 内存 | 恢复快，文件紧凑 | 丢失两次快照间数据，fork 可能阻塞 |
| AOF 追加日志 | 每条写命令追加到文件 | 最多丢失 1 秒数据 | 文件大，恢复慢 |
| 混合持久化（4.0+） | RDB + AOF 重写 | 快速恢复 + 低丢失 | 实现复杂 |

### 1.3 可靠性等级参考
| 等级 | 持久化方案 | 丢失风险 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 高可靠 | AOF + `appendfsync always` | 几乎为零 | 金融、交易 |
| 一般 | AOF everysec | 最多 1 秒 | 通用缓存 |
| 高性能 | RDB + 关闭 AOF | 分钟级 | 纯缓存，可丢失 |
| 混合 | RDB + AOF rewrite | 秒级 | 生产推荐 |

### 1.4 通用实现案例
- **RDB**：`save 900 1`、`save 300 10`、`save 60 10000`
- **AOF**：`appendonly yes`、`appendfsync everysec`
- **混合**：`aof-use-rdb-preamble yes`

### 1.5 生产问题与解决
- **fork 阻塞**：大实例 RDB 导致响应延迟 → 调整 `repl-diskless-sync`、使用 SSD、控制内存 <20GB。
- **AOF 文件过大**：`bgrewriteaof` 自动/手动重写。
- **断电丢失**：AOF everysec + 从库复制。

### 1.6 边界条件与风险
- **极值风险**：`appendfsync always` 写入性能下降 90% 以上。
- **RDB fork 时 COW**：内存可能翻倍，需预留 50% 空闲内存。
- **AOF 重写时磁盘满**：导致 Redis 不可写 → 监控磁盘。

### 1.7 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `save` | RDB 触发条件 | 按写入频率调整 | 需重启 | `INFO persistence` |
| `appendonly` | 开启 AOF | yes | 在线 | 同上 |
| `appendfsync` | AOF 刷盘策略 | everysec 推荐 | 在线 | 压测对比 |
| `aof-use-rdb-preamble` | 混合持久化 | yes | 需重启 | 检查 AOF 文件头 |

### 1.7.1 参数联动清单
- **场景**：AOF + RDB 同时开启
- **风险**：重写时 CPU/IO 双重压力 → 调整 `auto-aof-rewrite-percentage` 和 `auto-aof-rewrite-min-size`。

### 1.8 已知反模式
- 只用 RDB 且 `save ""`（不触发） → 数据永久丢失风险。
- 同时开启 AOF 和 RDB 但未配置重写阈值 → 磁盘爆满。

## 原则 2：冗余复制与高可用（X4）

### 2.1 第一性原理
- **物理/数学约束**：单节点必然故障。
- **推导**：主从复制 + 自动故障转移。

### 2.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 主从异步复制 | 主写本地，从异步拉取 | 高吞吐 | 主故障可能丢数据 |
| 主从同步复制（WAIT） | 等待从确认 | 强一致 | 写延迟增加 |
| 哨兵 | 监控 + 自动切换 | 高可用 | 需额外哨兵节点 |
| 集群 | 分片 + 复制 | 水平扩展 + 高可用 | 实现复杂 |

### 2.3 高可用等级参考
| 等级 | 架构 | RPO/RTO | 适用场景 |
| :--- | :--- | :--- | :--- |
| 基础 | 单机 | 高 | 开发测试 |
| 标准 | 主从 + 哨兵 | 秒级切换，可能丢数据 | 一般业务 |
| 强一致 | 主从 + WAIT 1 | 零丢失 | 金融 |
| 集群 | Redis Cluster | 秒级，分片故障影响子集 | 大规模 |

### 2.4 通用实现案例
- **主从**：`replicaof <masterip> <masterport>`
- **哨兵**：`sentinel monitor mymaster 127.0.0.1 6379 2`
- **集群**：`cluster-enabled yes`

### 2.5 生产问题与解决
- **复制延迟**：网络或从库性能差 → 增加带宽、优化从库。
- **脑裂**：哨兵误切换 → 配置 `sentinel down-after-milliseconds` 和 `failover-timeout` 合理。
- **全量复制风暴**：多从库同时重连 → 使用 `repl-diskless-sync`。

### 2.6 边界条件与风险
- **异步复制丢失**：主故障时未同步命令丢失 → 业务接受或使用 WAIT。
- **哨兵多数派要求**：奇数个哨兵。
- **集群部分故障**：`cluster-require-full-coverage` 设为 no 允许部分槽可用。

### 2.7 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `replicaof` | 主从关系 | 从库配置 | 需重启 | `INFO replication` |
| `repl-backlog-size` | 增量复制缓冲区 | 1MB-256MB | 在线 | 观察复制偏移 |
| `min-replicas-to-write` | 最少从库确认 | 1-2 | 在线 | 模拟从库故障 |
| `cluster-enabled` | 开启集群 | yes | 需重启 | `CLUSTER INFO` |

### 2.7.1 参数联动清单
- **场景**：WAIT 同步复制
- **涉及参数**：`min-replicas-to-write` 和 `min-replicas-max-lag`
- **风险**：从库数不足时写入被拒绝。

### 2.8 已知反模式
- 所有从库在同一机架 → 机架断电全挂。
- 哨兵部署在同一物理机 → 同时故障。

## 原则 3：内存与成本优化（X13）

### 3.1 第一性原理
- **物理/数学约束**：内存昂贵，数据量超过物理内存则 swap 或 OOM。
- **推导**：淘汰策略、内存压缩、合理数据结构。

### 3.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 淘汰策略（LRU/LFU/TTL） | `maxmemory-policy` | 控制内存上限 | 可能丢失数据 |
| 内存压缩 | ziplist/listpack/intset | 节省 30-50% 内存 | 访问速度略降 |
| 合理数据结构 | Hash 替代 String 批量 | 节省内存 | 开发复杂度 |
| 内存碎片整理 | `activedefrag` | 回收碎片 | CPU 开销 |

### 3.3 通用实现案例
- **maxmemory**：`maxmemory 2gb`
- **策略**：`maxmemory-policy allkeys-lru`
- **碎片整理**：`activedefrag yes`

### 3.4 生产问题与解决
- **内存碎片过高**：`INFO memory` 看 `mem_fragmentation_ratio` >1.5 → 重启或 `activedefrag`。
- **OOM**：`maxmemory` 设置低于物理内存 70%，留 buffer。
- **bigkey 内存爆炸**：`redis-cli --bigkeys` 扫描，拆分。

### 3.5 边界条件与风险
- **极值风险**：`maxmemory-policy noeviction` 导致写入失败。
- **LFU 初期冷启动**：所有 key 频繁被淘汰 → 预热。
- **listpack 阈值不当**：过小则频繁转换编码。

### 3.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `maxmemory` | 内存上限 | 物理内存 50-70% | 在线 | `INFO memory` |
| `maxmemory-policy` | 淘汰算法 | allkeys-lru | 在线 | 模拟写入 |
| `hash-max-listpack-entries` | Hash 编码阈值 | 512 | 在线 | `DEBUG OBJECT` |
| `activedefrag` | 碎片整理 | yes | 在线 | 观察碎片率 |

### 3.6.1 参数联动清单
- **场景**：同时使用 RDB/AOF 和 maxmemory
- **风险**：持久化可能额外占用内存 → 预留 20% 余量。

### 3.7 已知反模式
- 不设 `maxmemory` → 内存耗尽 OOM。
- `maxmemory-policy volatile-lru` 但未设过期时间 → 永不淘汰。

## 原则 4：水平扩展（Redis Cluster）（X5）

### 4.1 第一性原理
- **物理/数学约束**：单机内存/吞吐上限。
- **推导**：哈希槽分片，槽迁移平滑扩容。

### 4.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 客户端分片 | 应用层计算槽位 | 简单 | 无高可用，重平衡复杂 |
| 代理分片（Twemproxy） | 中间层路由 | 透明 | 增加跳数 |
| Redis Cluster | 官方分片 + 复制 | 高可用 + 线性扩展 | 限制多键操作 |

### 4.3 通用实现案例
- **Cluster 模式**：`cluster-enabled yes`，`cluster-config-file nodes.conf`

### 4.4 生产问题与解决
- **槽迁移期间性能下降**：限制迁移速度 `cluster-node-timeout`，业务低峰期操作。
- **跨槽操作不支持**：使用 `{hash_tag}` 强制同槽。
- **集群脑裂**：`cluster-require-full-coverage no` 避免整体不可用。

### 4.5 边界条件与风险
- **最小节点数**：至少 3 主 3 从。
- **槽迁移时主从切换风险**：迁移完成前禁用自动故障转移。
- **客户端重定向**：智能客户端需支持 MOVED/ASK。

### 4.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `cluster-enabled` | 开启集群 | yes | 需重启 | `CLUSTER NODES` |
| `cluster-node-timeout` | 节点超时 | 15000 | 在线 | 模拟网络分区 |
| `cluster-migration-barrier` | 从库迁移阈值 | 1 | 在线 | 观察主从分布 |

### 4.6.1 参数联动清单
- **场景**：集群扩容
- **涉及参数**：新增节点后需执行 `CLUSTER MEET` 和 `CLUSTER ADDSLOTS`。

### 4.7 已知反模式
- 使用 Cluster 但客户端不支持协议 → 大量 MOVED 重定向。
- 单机运行多个 Cluster 节点 → 端口冲突，资源争抢。

## 原则 5：一致性模型与事务（X1）

### 5.1 第一性原理
- **物理/数学约束**：异步复制导致主从不一致，网络分区可能导致脑裂。
- **推导**：选择合适的一致性等级。

### 5.2 消息语义与 CAP 关联
| 语义 | 典型实现 | CAP 倾向 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 最终一致 | 默认异步复制 | AP | 缓存 |
| 强一致 | WAIT 1 + 同步复制 | CP | 金融锁 |
| 顺序原子 | Lua 脚本 / MULTI | 单线程顺序 | 复杂操作 |

### 5.3 解决手段与代价
- **异步复制**：高性能，可能丢失。
- **WAIT 命令**：阻塞等待从库确认，延迟增加。
- **Lua 脚本**：原子执行，减少网络往返。
- **MULTI/EXEC**：事务，但不支持回滚。

### 5.4 通用实现案例
- **WAIT**：`WAIT <numreplicas> <timeout>`
- **Lua**：`EVAL "redis.call('SET',KEYS[1],ARGV[1])" 1 key value`
- **乐观锁**：`WATCH` + `MULTI` + `EXEC`

### 5.5 生产问题与解决
- **WATCH 失败重试**：高并发下频繁重试 → 使用 Lua 替代。
- **Lua 长时间阻塞**：`lua-time-limit` 默认 5 秒，超时记录但不 kill。
- **事务中命令错误**：Redis 不回滚，需业务补偿。

### 5.6 边界条件与风险
- **WAIT 超时**：返回确认数少于要求数，可能丢失。
- **Lua 脚本主从一致性**：脚本必须确定性。
- **长事务**：不推荐，应使用 Lua 原子执行。

### 5.7 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `lua-time-limit` | Lua 最大执行时间 | 5000ms | 在线 | 模拟长脚本 |
| `min-replicas-max-lag` | WAIT 从库延迟阈值 | 10s | 在线 | 压测 |

### 5.8 已知反模式
- 使用 `MULTI` 实现乐观锁但未处理重试逻辑。
- Lua 脚本包含非确定性命令（如 `RANDOMKEY`）导致主从不一致。

---

- **选择依据**：一致性 vs 可用性。
- **关联域**：X2（分布式事务不适用）。
- **预期检查项**：C1,C2,C3,C4,C5,C8,C11,C15。

## 原则 6：可观测性（X10）

### 6.1 第一性原理
- **物理/数学约束**：分布式系统故障定位难。
- **推导**：指标、日志、慢查询、追踪。

### 6.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 慢日志 | `slowlog-log-slower-than` | 发现慢命令 | 额外内存 |
| INFO 命令 | 实时统计 | 监控基础 | 解析复杂 |
| Prometheus Exporter | 导出指标 | 标准化监控 | 额外进程 |
| 延迟监控 | `--latency` | 网络/内核延迟 | 运行时影响 |

### 6.3 通用实现案例
- **慢日志**：`CONFIG SET slowlog-log-slower-than 10000`
- **Redis Exporter**：`github.com/oliver006/redis_exporter`
- **延迟检查**：`redis-cli --latency -h host -p port`

### 6.4 生产问题与解决
- **慢日志过多**：调高阈值，关注命令优化。
- **指标爆炸**：限制 exporter 采集的 key 模式。
- **内存碎片导致延迟**：`activedefrag` 或重启。

### 6.5 边界条件与风险
- **INFO 输出大**：大量 key 时 INFO 可能阻塞。
- **Exporter 拉取频率过高**：增加 Redis 负担，建议 15-30s。

### 6.6 健康检查最佳实践
**K8s 配置**：
```yaml
livenessProbe:
  tcpSocket:
    port: 6379
  initialDelaySeconds: 30
  periodSeconds: 10
readinessProbe:
  exec:
    command:
    - sh
    - -c
    - redis-cli -h 127.0.0.1 PING
  initialDelaySeconds: 5
  periodSeconds: 5
```

### 6.7 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `slowlog-log-slower-than` | 慢日志阈值 | 10000 微秒 | 在线 | `SLOWLOG GET` |
| `slowlog-max-len` | 慢日志条数 | 128 | 在线 | 同上 |
| `latency-monitor-threshold` | 延迟监控阈值 | 0（关闭）或 100ms | 在线 | `LATENCY LATEST` |

### 6.8 已知反模式
- 生产环境开启 `latency-monitor-threshold` 过低 → 大量事件。
- 不监控内存碎片率 → 长期高碎片导致 OOM。

## 原则 7：安全防御（X9）

### 7.1 第一性原理
- **物理/数学约束**：敏感数据需防泄露、篡改、未授权访问。
- **推导**：认证、授权、加密、审计。

### 7.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 密码认证 | `requirepass` | 基础防护 | 明文传输风险 |
| ACL（6.0+） | 用户+命令+key 权限 | 细粒度权限 | 配置复杂 |
| TLS 加密 | `tls-port` | 防窃听 | CPU 开销 10-20% |
| 命令重命名 | `rename-command` | 屏蔽危险命令 | 运维不便 |

### 7.3 通用实现案例
- **ACL**：`ACL SETUSER alice on >password +@all -@dangerous`
- **TLS**：`tls-port 6379`、`tls-cert-file`、`tls-key-file`

### 7.4 生产问题与解决
- **密码爆破**：使用 ACL + 复杂密码，限制连接频率。
- **TLS 性能下降**：启用 `tls-session-caching`，硬件加速。
- **ACL 规则过多**：使用 `ACL LOAD` 动态加载，避免重启。

### 7.5 边界条件与风险
- **requirepass 明文传输**：必须配合 TLS。
- **rename-command 与 ACL 冲突**：优先使用 ACL。
- **默认用户 default**：无密码，需禁用或设强密码。

### 7.6 性能量化说明
- TLS 开销：Intel Xeon, AES-GCM-128, 1KB 消息，无加速时约 15% CPU 增加。
- 优化：启用 `tls-session-caching`，使用 QAT 加速卡。

### 7.7 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `requirepass` | 全局密码 | 强密码 | 在线 | `AUTH` 测试 |
| `aclfile` | ACL 文件路径 | 文件模式 | 需重启 | `ACL LIST` |
| `tls-port` | TLS 端口 | 启用加密 | 需重启 | `openssl s_client` |

### 7.8 已知反模式
- 仅设 `requirepass` 不启用 TLS → 密码明文传输。
- ACL 授权过大（如 `+@all`） → 违背最小权限。
