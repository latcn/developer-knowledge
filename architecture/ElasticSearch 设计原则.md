## 第零章：Elasticsearch 的设计本质与第一性原理

### 0.1 设计目的
Elasticsearch 的核心目的是在分布式环境中提供**近实时的全文搜索**、结构化聚合分析和海量数据存储，解决传统数据库在规模化和搜索能力上的瓶颈。

### 0.2 解决的根本问题
1. **全文搜索性能**：传统数据库的 `LIKE` 查询无法规模化，倒排索引提供毫秒级检索。
2. **水平扩展**：数据分片机制使单集群可支持 PB 级数据，通过增加节点线性提升吞吐。
3. **高可用**：主副分片副本跨节点/可用区分布，自动故障转移，保证服务连续性。
4. **分析聚合**：分布式聚合框架对海量数据进行实时统计（sum、avg、cardinality 等）。
5. **多模态**：支持文本、数值、地理位置、向量等多种数据类型。

### 0.3 适用场景
- 日志与可观测性（ELK/EFK 栈）
- 全文搜索（网站、App 内搜索）
- 安全分析与 SIEM
- 指标监控与告警
- 向量检索（生成式 AI 应用）

### 0.4 核心设计矛盾与原则映射

| 矛盾 | 对应原则 |
| :--- | :--- |
| 数据可靠性 vs 写入性能 | 原则1（副本数）、原则2（同步/异步复制） |
| 强一致性 vs 查询可用性 | 原则2（读偏好、同步复制） |
| 扩展性 vs 资源开销 | 原则4（分片设计）、原则7（热温冷架构） |
| 实时性 vs 分段合并开销 | 原则3（refresh、flush 策略） |
| 原子性 vs 高并发 | 原则9（乐观锁、批量部分失败） |

## 原则1：分片副本冗余与故障自动转移

> **主归属**：X4（冗余复制） | **关联域**：X8（故障检测）

### 1.1 第一性原理
- **物理/数学约束**：在分布式系统中，节点故障是常态。若数据只存一份，任何节点宕机都将导致服务不可用或数据永久丢失。副本机制通过将同一分片的完整拷贝存储在不同节点上，实现数据冗余，这是高可用的物理基础。
- **推导**：通过为每个主分片创建至少1个副本分片，并将其分配在不同节点或不同可用区，结合节点间心跳检测机制和Raft共识选举（ES 7.x+），实现节点故障时的自动故障检测和副本自动提升为新的主分片。

### 1.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **主分片+副本分片** | 每个主分片至少1个副本，分配在不同节点 | 数据冗余、单节点故障不丢数据 | 存储成本翻倍 |
| **心跳检测** | 节点间定期发送Ping（默认间隔1秒，超时30秒），Master监控Data节点健康 | 快速感知节点故障 | 网络开销 |
| **副本自动晋升** | Data节点故障时，其主分片的副本分片自动提升为新的主分片 | 快速故障转移，恢复写入能力 | 短暂的集群状态变化（集群变Yellow） |
| **Master选举（Raft）** | ES 7.x+使用Raft协议自动选举，投票配置需多数（>50%） | 自动选主，避免脑裂 | 至少需3个Master候选节点 |
| **手动故障转移（计划维护）** | 先通过API排除节点，等待分片迁移，再安全停止 | 零中断地维护节点 | 操作需谨慎，等待分片迁移完成 |

### 1.3 通用实现案例（Elasticsearch 7.x/8.x）
- **索引副本配置**：默认`number_of_replicas=1`，可在创建索引时通过Settings API设置或事后动态调整。例如：
  ```
  PUT /my_index
  {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 1
    }
  }
  ```
  生产环境建议副本数≥1，单节点集群因无其他节点存放副本，副本数必须设为0。
- **多可用区部署**：生产环境至少使用2个可用区（AZ），关键系统建议3个AZ，并将副本合理分布到各AZ。节点数不少于AZ数，否则跨可用区部署会失败。双AZ部署时至少配置1个副本，保证一个AZ故障后另一AZ仍可提供服务。
- **Master选举与投票配置**：生产集群推荐至少3个专用Master候选节点，且节点数为奇数。高可用集群要求至少3个Master候选节点，以保证一个节点故障时仍能选出新Master。ES 7.x+版本使用Raft协议自动选举，无需手动配置`discovery.zen.minimum_master_nodes`（该参数已在7.x中被弃用）。**不同版本选举机制存在差异，建议查阅对应版本官方文档确认。**
- **跨集群复制（CCR）**：CCR实现秒级数据同步，适用于跨地域容灾场景。主集群故障时，业务流量可切换到Follower集群恢复服务，无需等待快照恢复。这是商业特性（Platinum版），部分云服务商已集成。
- **手动维护操作**：计划性节点维护（如升级）时应先排除节点避免分片丢失：
  ```
  PUT _cluster/settings
  {
    "persistent": {
      "cluster.routing.allocation.exclude._name": "old-node-name"
    }
  }
  ```
  等待分片迁移完成后，再停止并处理该节点。

### 1.4 生产问题与解决
- **问题1：节点故障后集群状态变Yellow**
  - **根因**：副本分片数量不足，部分分片的副本尚未分配到健康节点。
  - **解决方案**：集群本身会自动在健康节点上创建新副本恢复Green状态。若长时间未恢复，可手动触发分片重分配：
    ```
    POST _cluster/reroute?retry_failed=true
    ```
- **问题2：2节点集群误导致脑裂**
  - **根因**：两节点（偶数）且都设为Master候选节点，当一个节点故障时无法满足“超过半数”的选举条件，集群不可用。
  - **解决方案**：生产环境禁用两节点集群；2节点集群方案是仅将其中一个节点设为Master候选节点。
- **问题3：副本数过高导致写入性能大幅下降**
  - **根因**：每个主分片的数据需同步到所有副本，副本数过高会显著增加写入延迟。
  - **解决方案**：合理规划副本数，通常设为1即可满足高可用要求。曾有实践将副本数设为2导致写入性能下降60%。写入时可通过`wait_for_active_shards`控制同步确认数，平衡一致性与性能。

### 1.5 边界条件与风险
- **极值风险**：
  - 3节点集群中2个Master候选节点同时故障 → 集群无法选举Master，服务不可用，需待故障节点恢复后才可用。
  - 单节点全部故障且无快照备份 → 数据永久丢失，需恢复快照或接受数据丢失。
- **环境风险**：
  - 跨地域高延迟（>100ms）时，Raft选举可能超时失败 → 建议每个地域部署独立集群，通过CCR实现单向同步，而非单集群跨地域部署。
  - 多可用区部署时主节点分布不均可能导致50%停机风险，可通过调整节点分布或采用3可用区降低风险。
- **异常风险**：
  - 网络分区（脑裂）时，7.x+版本使用Raft协议自动隔离少数派分区，不会产生两个Master。
  - 手动`allocate_stale_primary`操作若使用不当可能导致数据丢失，`accept_data_loss`参数仅在必要时使用。

### 1.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 副本数 | 冗余容错能力 | 生产≥1，开发/测试可按需减少 | 模拟节点故障，检查数据完整性 | **在线生效** |
| 跨可用区副本分布 | 可用区级别容灾 | 至少2个AZ，副本合理分布 | 模拟一个AZ故障，检查服务连续性 | 静态配置 |
| Master候选节点数 | 选举可用性 | ≥3且为奇数，建议专用Master节点 | 逐一停用Master节点，检查选举是否成功 | 需重启 |
| 心跳间隔/超时 | 故障检测速度 | `discovery.zen.fd.ping_interval`=1秒，`ping_timeout`=30秒 | 网络延迟注入，观察故障检测延迟 | 需重启 |
| 跨集群复制（CCR） | 跨地域容灾 | 主集群高性能，Follower集群仅读，版本≥6.7 | 模拟主集群故障，切换流量到Follower | 需配置 |

> **时效性提示**：各版本参数行为可能存在差异（如ES 7.x+已弃用`discovery.zen.minimum_master_nodes`），**生产部署前请务必查阅对应版本官方文档，并通过压测验证。**

### 1.6.1 参数联动检查清单
- **场景**：多可用区部署时的高可用配置。
- **涉及参数**：`number_of_replicas`、跨可用区节点分布、`cluster.routing.allocation.awareness.attributes`。
- **配置原则**：
  - 节点数 ≥ 可用区数，每个可用区节点数尽量均衡。
  - `number_of_replicas` ≥ 可用区数 - 1（2 AZ时≥1，3 AZ时≥2）。
  - 使用分片分配感知，确保副本分布在不同可用区：
    ```
    cluster.routing.allocation.awareness.attributes: zone_id
    node.attr.zone_id: zone1
    ```
  - 也可采用强制感知（`force.zone_id.values`），防止副本分配到同一可用区。
- **未同步调整的风险**：可用区故障时可能因副本不足导致数据丢失或写入不可用。
- **验证方法**：ChaosBlade注入网络丢包模拟AZ故障，检查集群自动重分配情况和业务是否中断。

### 1.7 已知反模式检查
- **类别**：Master节点配置
  - **反模式**：Master候选节点数为偶数（2、4、6） → 选举可能无法形成多数派。
  - **规避**：Master候选节点数必须为奇数，至少3个。
- **类别**：副本数配置
  - **反模式**：生产环境副本数=0 → 单点故障会直接丢数据，必须≥1。
  - **规避**：创建索引模板强制设置`number_of_replicas`≥1；单节点开发环境可通过Template设为0。
- **类别**：单节点/双节点集群
  - **反模式**：2节点集群且两个节点均设为Master候选 → 一个节点故障时选举失败，集群不可用，不推荐生产使用。
  - **规避**：按规范配置至少3个专用Master候选节点；2节点集群仅适用于非生产环境。
- **类别**：手动故障转移
  - **反模式**：直接`kill`节点进程而不先排除并迁移分片 → 可能导致部分分片长时间未分配，影响业务。
  - **规避**：计划维护应严格遵守"排除节点 → 等待迁移 → 停止"的操作流程。

## 原则2：读写一致性模型与乐观锁并发控制

> **主归属**：X1（一致性模型） | **关联域**：X3（并发控制）、X4（冗余复制）

### 2.1 第一性原理
- **物理/数学约束**：分布式系统面临 CAP 权衡。Elasticsearch 默认优先保证写入可用性（AP），通过主副分片异步复制实现最终一致。但用户可通过参数调优，在特定场景下获得强一致性（CP）。
- **推导**：写入操作首先在主分片执行，成功后同步或异步复制到副本；读取操作默认在主副之间轮询（负载均衡），可指定优先读主分片获取最新数据。文档更新使用 `_seq_no` 和 `_primary_term` 实现乐观锁，避免并发覆盖。

### 2.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **主分片优先读取** | `?preference=_primary` 强制读主分片 | 读取最新写入，避免脏读 | 增加主分片负载 |
| **wait_for_active_shards** | 写入时等待至少 N 个副本确认 | 保证数据在多数副本上持久化 | 写入延迟增加（等待副本响应） |
| **同步复制（sync）** | 主分片成功后，同步等待副本确认 | 强一致，写入后查询即见 | 写入时延线性增加（副本数越多越慢） |
| **异步复制（async）** | 主分片成功后立即返回，后台异步复制 | 写入低延迟，高吞吐 | 主分片故障可能丢失最近写入 |
| **乐观锁** | 基于 `if_seq_no` 和 `if_primary_term` 更新 | 避免覆盖其他并发更新 | 冲突需要重试，增加客户端复杂性 |
| **读取一致性级别** | 可选 `QUORUM`（多数副本）、`ONE`（任一）、`ALL` | 平衡实时性与可用性 | `QUORUM` 可能因副本不足而失败 |

### 2.3 通用实现案例（Elasticsearch 7.x/8.x）
- **强制读主分片**：
  ```
  GET /my_index/_search?preference=_primary
  ```
- **设置写等待副本数**：
  ```
  PUT /my_index
  {
    "settings": {
      "index.write.wait_for_active_shards": "2"   // 至少 2 个副本确认
    }
  }
  ```
  单节点时该值只能设为 0 或 1。
- **同步复制**：默认 `index.replication.type=sync`（ES 6 之后默认同步，无需配置）。异步复制需显式设为 `async`，但 ES 官方不推荐，因为可能导致数据丢失。
- **乐观锁更新示例**：
  ```
  POST /my_index/_doc/1?if_seq_no=5&if_primary_term=2
  {
    "field": "new value"
  }
  ```
  若文档当前 `_seq_no` ≠ 5，则返回 409 Conflict。
- **批量操作的原子性**：`_bulk` API 每个子操作独立，一个失败不影响其他，但整体返回的 HTTP 状态码仍为 200。需检查响应体中的 `errors` 字段。
  ```
  POST /_bulk
  { "index": { "_index": "test", "_id": "1" } }
  { "field1": "value1" }
  { "index": { "_index": "test", "_id": "2" } }
  { "field2": "value2" }
  ```

### 2.4 生产问题与解决
- **问题1：索引后查询不到最新文档**
  - **根因**：默认 1 秒刷新频率（`refresh_interval=1s`）或副本异步复制延迟。
  - **解决方案**：紧急情况可强制刷新 `POST /my_index/_refresh`；业务要求强一致则使用 `?refresh=wait_for` 参数等待自动刷新。
- **问题2：高并发更新出现大量 409 冲突**
  - **根因**：乐观锁冲突，多客户端同时更新同一文档。
  - **解决方案**：重试策略（指数退避）；使用脚本更新（部分场景可减少冲突）；或重新设计数据模型，避免热点文档。
- **问题3：wait_for_active_shards 导致写入不可用**
  - **根因**：副本数配置过大，当节点数不足时写入一直阻塞。
  - **解决方案**：设置 `wait_for_active_shards` ≤ 当前可用的副本数，或动态降低该值。

### 2.5 边界条件与风险
- **极值风险**：异步复制下主分片写入成功后立即故障，尚未复制到副本的数据永久丢失 → 对数据零丢失的场景禁用 `async`。
- **环境风险**：跨机房部署延迟高时，`wait_for_active_shards` 会显著增加延迟 → 可设置更低值或使用本地读偏好。
- **异常风险**：乐观锁无限重试可能导致请求积压 → 设置最大重试次数（如 5 次）和超时。

### 2.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| `index.write.wait_for_active_shards` | 写入强一致程度 | 生产建议 `1`（默认）或 `2`（金融级） | 模拟节点故障，观察写入成功条件 | **在线生效** |
| `index.replication.type` | 同步/异步复制 | 默认 `sync`，禁止生产用 `async` | 压测写入，对比延迟与数据丢失情况 | **需重启**（索引级别） |
| `refresh_interval` | 数据可见性延迟 | 默认 1s，可调大（如 30s）提升写入吞吐 | 观测索引延迟与搜索实时性 | **在线生效** |
| `_seq_no` 冲突重试 | 乐观锁处理 | 客户端重试 3-5 次，指数退避 | 高并发压测，监控 409 率 | SDK 配置 |
| 批量并发控制 | 避免资源耗尽 | 每个请求 ≤ 5k 文档或 ≤15MB | 监控线程池队列 | 在线调优 |

> **时效性提示**：不同 ES 版本默认行为和参数名可能变化（如 `replication.type` 在 8.x 已废弃），**请查阅对应版本官方文档**。

### 2.6.1 参数联动检查清单
- **场景**：金融交易数据要求强一致。
- **涉及参数**：`wait_for_active_shards`、`replication.type`、`refresh_interval`、`preference`。
- **配置原则**：
  - 副本数 ≥2，`wait_for_active_shards` = 副本数。
  - `replication.type=sync`。
  - `refresh_interval` = 1s（或禁用自动 refresh，显式控制）。
  - 查询时强制 `preference=_primary`。
- **未同步调整的风险**：可能读取到旧数据或写入后立即故障导致丢失。
- **验证方法**：模拟主分片故障，检查未确认的写入是否丢失。

### 2.7 已知反模式检查
- **类别**：异步复制滥用
  - **反模式**：为追求性能在生产开启 `async` → 存在数据丢失风险。
  - **规避**：仅对可容忍丢失的日志类数据使用 `async`，核心业务必须 `sync`。
- **类别**：乐观锁无重试
  - **反模式**：客户端不处理 409，导致并发更新静默失败 → 业务数据不一致。
  - **规避**：SDK 封装自动重试逻辑。
- **类别**：wait_for_active_shards 过高
  - **反模式**：设为大于实际副本数，写入请求永久等待 → 服务不可用。
  - **规避**：动态检查集群副本状态，使用系统默认值（1）足够。

## 原则3：高并发索引与搜索的性能优化

> **主归属**：N2（通信容错） | **关联域**：C1（计算资源）、X13（成本优化）

### 3.1 第一性原理
- **物理/数学约束**：索引写入涉及分词、倒排表构建、segment 合并，搜索涉及倒排表遍历、评分计算、聚合，均消耗 CPU、内存和 IO。SSD 随机读性能远优于 HDD。
- **推导**：通过批量写入、优化映射（禁用不必要的倒排索引）、使用合适的合并策略（tiered 合并）、分片大小控制、查询缓存、硬件加速（SSD）来平衡实时性和吞吐。

### 3.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **批量写入** | `_bulk` 聚合多个请求 | 网络包减少，IO 合并，写入吞吐提升 5-10 倍 | 单个请求延迟增加，失败需重试整批 |
| **调整 refresh_interval** | 增大刷新间隔（如 30s）减少 segment 数量 | 降低 IO 和 CPU，提升写入性能 | 搜索可见性延迟增大 |
| **禁用无用的文本索引** | 对不搜索的字段设置 `"index": false` | 节省存储和 CPU | 无法对该字段进行全文检索 |
| **使用 index 排序** | 按照自定义顺序预先排序 segment | 提升范围查询性能 | 构建索引耗时增加 |
| **查询缓存** | Node Query Cache / Request Cache | 重复查询结果直接返回 | 内存占用，适用于高命中率查询 |
| **异步搜索** | `?wait_for_completion=false`，返回 task ID | 避免长时间查询阻塞 | 需要额外轮询任务结果 |

### 3.3 通用实现案例（Elasticsearch 7.x/8.x）
- **批量写入**：每个 bulk 请求建议 5-15MB，5k-10k 文档，根据集群性能调整。使用 `_bulk` API 时设置 `refresh=wait_for` 或 `refresh=false`。
- **增大 refresh_interval**：
  ```
  PUT /my_index/_settings
  {
    "index.refresh_interval": "30s"
  }
  ```
  写入完成后可设回 `1s`。
- **禁用倒排索引**：
  ```
  "mappings": {
    "properties": {
      "not_searchable_field": {
        "type": "text",
        "index": false
      }
    }
  }
  ```
- **索引排序**（按时间排序）：
  ```
  PUT /my_index
  {
    "settings": {
      "index.sort.field": "timestamp",
      "index.sort.order": "desc"
    }
  }
  ```
- **查询缓存**：`index.requests.cache.enable: true`，适用于聚合等昂贵查询，按节点内存比例（`indices.requests.cache.size: "1%"`）。
- **异步搜索**（7.7+）：
  ```
  POST /my_index/_async_search?size=0&wait_for_completion_timeout=1s
  ```

### 3.4 生产问题与解决
- **问题1：写入被拒绝（EsRejectedExecutionException）**
  - **根因**：bulk 队列满（默认 200），或并发过高。
  - **解决方案**：增加队列 `thread_pool.write.queue_size=500`；降低批量大小；增加节点。
- **问题2：查询缓慢，CPU 飙升**
  - **根因**：复杂的聚合（脚本、cardinality）或未使用缓存。
  - **解决方案**：启用查询缓存；优化 mapping（`eager_global_ordinals`）；将高频聚合字段转为 `keyword` 类型。
- **问题3：segment 过多导致搜索性能下降**
  - **根因**：refresh_interval 过小，产生大量小 segment。
  - **解决方案**：调大 refresh_interval；强制 merge（`POST /my_index/_forcemerge?max_num_segments=1`），但注意 merge 过程消耗 IO。

### 3.5 边界条件与风险
- **极值风险**：批量请求过大（>100MB）导致集群内存溢出 → 限制单批大小。
- **环境风险**：HDD 磁盘随机 IO 差，严重影响写入和搜索 → 生产环境必须使用 SSD。
- **异常风险**：merge 过程占用大量磁盘 IO，导致写入抖动 → 在业务低峰期执行，并限制 merge 速度（`index.merge.scheduler.max_thread_count=1`）。

### 3.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| `index.refresh_interval` | 数据可见延迟与性能平衡 | 日志场景 30-60s；搜索场景 1s | 压测写入 TPS，监控 segment 数 | **在线生效** |
| `index.merge.policy` | segment 合并策略 | `tiered` 默认，`floor_segment` 避免过小 | 监控磁盘 IO 和 merge 队列 | 需重启 |
| `indices.queries.cache.size` | 查询缓存内存 | 通常 1-5% 堆内存 | 缓存命中率监控 | 动态 |
| `thread_pool.write.queue_size` | 批量队列容量 | 默认 200，可调至 500-1000 | 监控 reject 计数 | 需重启 |
| 批量请求大小 | 网络与 IO 平衡 | 5-15MB，5000-10000 文档 | 压测找出最优区间 | 客户端配置 |

> **时效性提示**：不同版本线程池参数不同（如 8.x 改用 autoscaled），**请查阅对应版本官方文档**。

### 3.6.1 参数联动清单（写入优化）
- **场景**：日志写入吞吐优先，可容忍 30s 搜索延迟。
- **涉及参数**：`refresh_interval`、`translog.durability`、`translog.sync_interval`。
- **配置原则**：
  - `refresh_interval=30s`。
  - `translog.durability=async`，`translog.sync_interval=5s`（降低 translog 磁盘压力）。
  - `index.number_of_replicas=0`（写入完成后再增加，配合 flink 双写机制）。
- **未同步调整的风险**：节点故障可能丢失最后几秒数据。
- **验证方法**：写入后不强制 refresh，检查搜索可见性延迟是否符合预期。

### 3.7 已知反模式检查
- **类别**：频繁强制 merge
  - **反模式**：每次索引后执行 `_forcemerge` → 消耗大量 IO，影响写入。
  - **规避**：仅当 segment 数量超过阈值（如 100）时在低峰期执行。
- **类别**：禁用索引时不分片
  - **反模式**：单个索引分片数过少（<节点数），无法充分利用资源 → 扩展受限。
  - **规避**：分片数 = 节点数 × 1.5-3。
- **类别**：查询使用 `*` 匹配所有字段
  - **反模式**：未指定字段，搜索所有 `index:true` 字段 → 性能差。
  - **规避**：使用 `copy_to` 汇总字段，或明确 field 列表。

## 原则4：水平扩展与负载均衡

> **主归属**：X5（分区扩展） | **关联域**：X6（负载均衡）

### 4.1 第一性原理
- **物理/数学约束**：单节点处理能力有限，通过分片（shard）将数据水平切分到多个节点，实现线性扩展。分片数量一旦设定，不能轻易更改（只能 split 或 shrink），需合理规划。
- **推导**：提前预估数据量规划分片数（每个分片 20-40GB 为佳），采用节点角色分离（master、data、ingest、coordinate），并使用协调节点负载均衡请求。

### 4.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **分片数量规划** | 索引拆分到多个主分片（默认 1，推荐 5-10/节点） | 并行查询和写入，扩展性线性 | 分片过多 → 元数据膨胀，查询开销大 |
| **节点角色分离** | master、data、ingest、coordinate 各司其职 | 避免职责干扰，提升稳定性 | 需要更多节点，管理复杂 |
| **协调节点** | 接收请求，分发到分片，聚合结果 | 分担查询聚合压力 | 无状态，可水平扩展 |
| **自动分片均衡** | `cluster.routing.rebalance.enable` | 新节点加入自动迁移分片 | 迁移过程占用 IO |
| **跨集群搜索（CCS）** | 多个集群联合搜索 | 扩展超出单集群限制 | 网络延迟，复杂 |

### 4.3 通用实现案例（Elasticsearch 7.x/8.x）
- **分片数设置**：生产环境推荐每个分片 20-40GB，分片数 = 未来最大数据量 / 30GB。例如 3TB 数据，分片数约 100。单个索引分片数建议不超过 1000（元数据压力）。
- **节点角色配置**：
  - Master 候选节点：`node.master: true, node.data: false`（至少 3 个）。
  - 数据节点：`node.master: false, node.data: true`（存储分片）。
  - 协调节点：`node.master: false, node.data: false, node.ingest: false`（无状态，可配置 LB）。
- **负载均衡**：在协调节点前放置代理（HAProxy、Nginx）或云内网 SLB，健康检查端点 `/_cluster/health` 或 `/_nodes/stats`。
- **自动均衡控制**：
  ```
  PUT _cluster/settings
  {
    "persistent": {
      "cluster.routing.rebalance.enable": "none"   // 临时禁用
    }
  }
  ```

### 4.4 生产问题与解决
- **问题1：分片数量过多导致集群状态更新慢**
  - **根因**：单索引分片数 > 1000，或集群总分片数 > 10 万。
  - **解决方案**：使用 rollover 滚动索引，控制单个索引大小；删除无用索引；调整 `cluster.routing.allocation.total_shards_per_node` 限制单节点分片数。
- **问题2：新节点加入后分片迁移导致性能下降**
  - **根因**：迁移抢占 IO 和网络。
  - **解决方案**：限制迁移速度：`indices.recovery.max_bytes_per_sec: "40mb"`；分批加入节点，避免一次性大量迁移。
- **问题3：协调节点成为瓶颈**
  - **根因**：查询聚合计算量大，协调节点 CPU 耗尽。
  - **解决方案**：增加协调节点（水平扩展），或使用异步搜索。

### 4.5 边界条件与风险
- **极值风险**：分片数不足导致单个分片过大（>100GB），重新分片困难（需 reindex）。
- **环境风险**：跨地域扩展时，节点间延迟高影响均衡 → 部署独立集群。
- **异常风险**：重平衡期间如果节点故障，可能导致数据迁移失败 → 使用 `_cluster/reroute?retry_failed=true`。

### 4.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 分片数量 | 扩展粒度 | 每个分片 20-40GB，总分数 ≤ 节点数 × 20 | 监控分片大小和查询延迟 | 创建时确定 |
| 副本数量 | 冗余与扩展 | 生产≥1，大型集群可为每个分片 1 副本 | 模拟节点故障，检查读取路由 | **在线生效** |
| `total_shards_per_node` | 限制单节点分片压力 | 默认无限制，建议 ≤ 1000/节点 | 监控数据节点内存和 CPU | **在线生效** |
| 迁移限速 | 控制迁移对 IO 冲击 | `recovery.max_bytes_per_sec: 40mb` | 观察迁移时段 IO 带宽占用 | **在线生效** |
| 协调节点数量 | 查询处理能力 | 按需 1-3 个（大集群可更多） | 压测查询，监控协调节点 CPU | 静态部署 |

> **时效性提示**：ES 7.x 开始不再建议使用 `index.number_of_shards` 的默认值 5（改为 1），请根据实际规划设置。

### 4.6.1 参数联动清单（扩容操作）
- **场景**：从 3 节点扩展到 10 节点。
- **涉及参数**：`cluster.routing.allocation.enable`、`recovery.max_bytes_per_sec`、`total_shards_per_node`。
- **配置原则**：
  1. 临时禁用分配：`"allocation.enable": "none"`。
  2. 逐个加入节点，恢复分配并限制迁移速度。
  3. 迁移完成后再次均衡副本。
  4. 动态调整 `total_shards_per_node`。
- **未同步调整的风险**：大量分片迁移导致集群不稳定。
- **验证方法**：扩容后观察 `_cat/shards` 分布，确认均衡。

### 4.7 已知反模式检查
- **类别**：分片数不合理
  - **反模式**：为每个用户创建独立索引且分片数过多 → 元数据爆炸。
  - **规避**：使用分片路由或 join 方式，控制总索引数。
- **类别**：节点角色混乱
  - **反模式**：Master 节点同时作为数据节点，重负载下可能导致选举超时。
  - **规避**：严格分离，Master 节点只做选举和集群管理。
- **类别**：协调节点过少
  - **反模式**：仅使用数据节点接收请求，聚合压力影响数据节点稳定性 → 推荐独立协调节点。

## 原则5：安全合规

> **主归属**：X9（安全防御） | **关联域**：SPEC

### 5.1 第一性原理
- **物理/数学约束**：数据泄露风险高，必须保障传输、存储、访问控制。加密会带来性能开销，但不可妥协。
- **推导**：开启 X-Pack 安全功能，配置 TLS 加密，使用基于角色的访问控制（RBAC），审计日志记录关键操作。

### 5.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **认证** | 用户名/密码、API Key、PKI 证书 | 阻止未授权访问 | 配置复杂 |
| **RBAC** | 角色映射到索引和操作权限（read、write、manage） | 精细化权限控制 | 维护角色 |
| **传输加密** | 节点间 TLS + 客户端 TLS | 防窃听 | CPU 10-20% |
| **字段级安全** | 基于角色的字段过滤 | 脱敏敏感字段 | 查询性能轻微下降 |
| **审计日志** | 记录登录、查询、配置变更 | 合规追溯 | 存储开销 |
| **IP 白名单** | 在代理层限制 IP 范围 | 简单网络过滤 | 动态 IP 环境难用 |

### 5.3 通用实现案例（Elasticsearch 7.x/8.x）
- **开启安全功能**（基础版免费）：
  ```yaml
  xpack.security.enabled: true
  xpack.security.authc.api_key.enabled: true
  ```
  首次启动需设置内置用户密码：
  ```
  bin/elasticsearch-setup-passwords interactive
  ```
- **TLS 配置**：生成 CA 和证书，修改 `elasticsearch.yml`：
  ```yaml
  xpack.security.transport.ssl.enabled: true
  xpack.security.transport.ssl.keystore.path: certs/elastic-certificates.p12
  xpack.security.transport.ssl.truststore.path: certs/elastic-certificates.p12
  ```
- **RBAC 示例**：创建只读角色：
  ```
  POST /_security/role/logs_reader
  {
    "indices": [
      { "names": [ "logs-*" ], "privileges": ["read"] }
    ]
  }
  ```
  分配角色给用户。
- **字段级安全**：
  ```json
  {
    "indices": [{
      "names": ["customer"],
      "privileges": ["read"],
      "field_security": { "grant": ["name", "email"], "except": ["ssn"] }
    }]
  }
  ```
- **审计日志**：配置 `xpack.security.audit.enabled: true`，输出到专用索引或文件。

### 5.4 生产问题与解决
- **问题1：开启 TLS 后节点间通信失败**
  - **根因**：证书不信任或节点名称不匹配。
  - **解决方案**：使用相同 CA 签发所有节点证书，设置 `xpack.security.transport.ssl.verification_mode: certificate`（或 `full`）。
- **问题2：忘记设置 API Key 的过期时间**
  - **根因**：默认永不过期，存在泄露风险。
  - **解决方案**：创建时指定 `expiration`，并使用自动轮换机制。

### 5.5 边界条件与风险
- **极值风险**：证书泄露或内部人员滥用权限 → 定期轮换证书，最小权限原则。
- **环境风险**：云环境托管服务（如 Elastic Cloud）已内置安全功能，注意配置网络策略。
- **异常风险**：审计日志索引写满导致集群变黄 → 设置 ILM 自动删除审计索引。

### 5.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 安全开关 | 强制安全 | `xpack.security.enabled: true` | 未认证请求返回 401 | 需重启 |
| TLS 验证模式 | 传输安全性 | `certificate` 或 `full` | 抓包检查是否加密 | 需重启 |
| API Key 有效期 | 临时凭证 | 设置 30 天，定期轮换 | 检查日志是否有过期 key 拒绝 | 动态创建 |
| 审计日志保留 | 合规存储 | ILM 策略保留 90 天 | 监控磁盘使用 | 在线生效 |

> **时效性提示**：不同版本安全特性有差异（8.x 默认开启，且更严格），**请查阅对应版本官方文档**。

### 5.6.1 参数联动（合规加固）
- **场景**：满足 SOC2 或等保要求。
- **配置**：强制 TLS、开启审计、启用 RBAC、设置密码策略（长度、复杂度）、禁止匿名访问。
- **验证**：使用渗透测试工具扫描未授权访问。

### 5.7 已知反模式检查
- **类别**：生产环境禁用安全功能
  - **反模式**：`xpack.security.enabled: false` → 数据裸奔。
  - **规避**：生产强制开启，配置 CI 检查配置文件。
- **类别**：使用默认的 `elastic` 超级用户
  - **反模式**：所有应用共用超级用户 → 权限过大。
  - **规避**：创建专用角色（如 `app_writer`），仅授予必要权限。
- **类别**：审计日志本地文件不轮转
  - **反模式**：写入 `elasticsearch_access.log` 无限增长 → 磁盘爆满。
  - **规避**：使用索引存储审计日志并配置 ILM。

## 原则6：可观测性

> **主归属**：X10（可观测性） | **关联域**：X8（故障检测）、X12（配置演化）

### 6.1 第一性原理
- **物理/数学约束**：集群健康状况、索引性能、节点资源必须通过指标实时可知，否则无法运维。
- **推导**：暴露节点和索引的关键指标（通过监控 API），配置慢日志定位问题，使用集群健康 API 进行自动化运维。

### 6.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **集群健康 API** | `/_cluster/health` 返回绿/黄/红状态 | 快速了解集群状态 | 仅简单状态 |
| **节点统计 API** | `/_nodes/stats` 提供 CPU、内存、磁盘、索引速率 | 精细化监控 | 高频轮询影响性能 |
| **慢查询日志** | 记录超过阈值的搜索和索引请求 | 定位性能瓶颈 | 日志开销 |
| **索引级别指标** | `/_stats` 返回文档数、删除数、存储大小 | 容量规划 | 高频查询对集群有压力 |
| **Prometheus 集成** | 通过 exporter 或自带 Prometheus 端点 | 接入监控告警系统 | 额外开销 |
| **Elastic 自身监控（旧称 Marvel）** | 内置监控收集器 | 方便，集成度高 | 消耗资源 |

### 6.3 通用实现案例（Elasticsearch 7.x/8.x）
- **健康检查**：
  ```
  GET /_cluster/health?pretty
  ```
  返回值 `status` 字段：`green`（所有分片正常）、`yellow`（主分片正常，副本缺失）、`red`（至少一个主分片未分配）。
- **节点统计**：获取关键指标 `_nodes/stats/jvm,os,process,indices,transport,http`。
- **慢日志配置**：
  ```yaml
  index.search.slowlog.threshold.query.warn: 10s
  index.search.slowlog.threshold.fetch.warn: 1s
  index.indexing.slowlog.threshold.index.warn: 10s
  ```
  可在索引 settings 中动态调整。
- **Prometheus 集成**：使用 [elasticsearch_exporter](https://github.com/prometheus-community/elasticsearch_exporter) 或 ES 8.0+ 自带的 `/_prometheus/metrics` 端点。
- **Elastic Agent**：通过 Fleet 部署，监控集群并发送到监控集群（需另建监控集群）。

### 6.4 生产问题与解决
- **问题1：集群状态 Yellow 且持续不恢复**
  - **根因**：副本分片无法分配，可能因节点数不足或磁盘满。
  - **解决方案**：检查 `_cluster/allocation/explain` API 定位原因，增加节点或清理磁盘。
- **问题2：慢日志发现大量慢查询**
  - **根因**：未使用索引过滤、通配符查询、大量聚合。
  - **解决方案**：分析慢日志，优化查询或添加索引。
- **问题3：Prometheus 抓取 /_prometheus/metrics 时集群响应变慢**
  - **根因**：指标聚合计算开销大。
  - **解决方案**：降低抓取频率（30s→60s），或使用 dedicated 监控节点（`node.roles: [ "monitoring" ]`）。

### 6.5 边界条件与风险
- **极值风险**：监控 API 被频繁调用拖垮集群 → 设置代理缓存或限制轮询频率。
- **环境风险**：监控数据索引与业务索引混用可能导致资源争抢 → 使用独立监控集群。
- **异常风险**：慢日志记录参数可能泄露敏感数据 → 在 log4j2 配置中脱敏。

### 6.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 慢日志阈值 | 性能基准 | 搜索 warn=10s，info=1s；索引 warn=10s | 执行慢查询，检查日志输出 | **在线生效** |
| 监控收集间隔 | 平衡监控粒度 | Prometheus 30s；内部监控 10s | 监控 CPU 使用率 | 外部配置 |
| 磁盘水位线 | 防止磁盘满 | 低水位 85%，高水位 90%，只读 95% | 写入接近阈值，检查集群操作 | **在线生效** |
| 健康检查频率 | 自动化决策 | 外部 LB 每 5s 检查一次 | 模拟节点故障，LB 摘除 | 外部配置 |

> **时效性提示**：8.x 中磁盘水位线默认值有所调整，**请查阅官方文档**。

### 6.6.1 联动清单（告警规则）
- **重要告警**：
  - 集群状态为 `red` → 立即处理。
  - 节点磁盘使用率 ≥ 85% → 增加节点或删除旧索引。
  - 节点 JVM GC 时间超过 5s/次 → 检查 heap 配置或内存泄漏。
  - 搜索拒绝率（`search_rejected_total`）>0 → 增加协调节点或优化查询。

### 6.7 已知反模式检查
- **类别**：使用生产集群监控自身
  - **反模式**：在生产集群中存储监控数据，导致循环依赖。
  - **规避**：部署专用的监控集群（小规模），并配置 ILM 保留较短时间。
- **类别**：日志级别调为 DEBUG
  - **反模式**：线上开启 DEBUG 日志，磁盘爆满。
  - **规避**：生产使用 INFO，需要调试时临时开启并用 `/_cluster/settings` 动态关闭。

## 原则7：成本优化

> **主归属**：X13（成本优化） | **关联域**：C1（计算资源）、D1（数据容量）

### 7.1 第一性原理
- **物理/数学约束**：存储和计算有直接成本，通过数据生命周期管理、压缩、冷热分离降低总体拥有成本（TCO）。
- **推导**：热节点使用 SSD，温节点用 HDD，冷节点使用可搜索快照（冻结层）存储到对象存储（S3）。同时启用最佳压缩（`best_compression`）并定期删除旧数据。

### 7.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **热温冷架构** | 按数据新鲜度分节点层 | 热节点高性能，冷节点低成本 | 管理复杂，需要 ILM 策略 |
| **可搜索快照（冻结层）** | 快照到 S3，部分缓存到本地 | 极低成本存储海量历史数据 | 查询延迟高，需预热 |
| **`best_compression`** | 使用 deflate 算法压缩 | 存储节省 30-50% | CPU 压缩/解压开销 |
| **`_forcemerge`** | 合并为 1 个 segment | 减少文件句柄，提升搜索 | 消耗 IO，适用于不变数据 |
| **索引生命周期管理（ILM）** | 自动迁移、删除、冻结 | 无人值守，降低运维成本 | 需配置策略 |
| **使用 HDD 而非 SSD** | 温节点使用机械硬盘 | 存储成本降低 70% | 随机读性能差 |

### 7.3 通用实现案例（Elasticsearch 7.x/8.x）
- **节点角色分层**：`node.attr.temperature: hot/warm/cold`。
- **ILM 策略示例**：
  ```
  PUT _ilm/policy/logs_policy
  {
    "policy": {
      "phases": {
        "hot": {
          "actions": {
            "rollover": { "max_size": "50GB", "max_age": "1d" },
            "set_priority": { "priority": 100 }
          }
        },
        "warm": {
          "min_age": "3d",
          "actions": {
            "allocate": { "require": { "temperature": "warm" } },
            "forcemerge": { "max_num_segments": 1 }
          }
        },
        "cold": {
          "min_age": "30d",
          "actions": {
            "allocate": { "require": { "temperature": "cold" } },
            "freeze": {}
          }
        },
        "delete": {
          "min_age": "90d",
          "actions": { "delete": {} }
        }
      }
    }
  }
  ```
- **启用 best_compression**：
  ```
  PUT /my_index
  {
    "settings": {
      "index.codec": "best_compression"
    }
  }
  ```
  注意：此设置只能在索引创建时指定，不能动态修改。
- **可搜索快照**（8.x+）：先注册快照仓库（S3），然后通过 `_search` 直接查询快照，需指定 `ignore_throttled=false`。

### 7.4 生产问题与解决
- **问题1：ILM 迁移到冷节点后查询变慢**
  - **根因**：冷节点使用 HDD 或冻结层。
  - **解决方案**：对冷数据查询需要接受较高延迟；若业务需要快速查询，可将数据保留在温节点。
- **问题2：best_compression 导致写入 CPU 飙升**
  - **根因**：压缩级别高（默认 6）。
  - **解决方案**：可接受普通压缩（`lz4`）平衡性能；仅对历史索引启用最佳压缩。

### 7.5 边界条件与风险
- **极值风险**：ILM 删除阶段意外删除未迁移的索引 → 使用 `min_age` 并测试策略。
- **环境风险**：S3 存储成本虽然低，但 API 请求次数会产生费用 → 聚合查询尽量避免扫描大量快照。
- **异常风险**：冻结层快照仓库不可用导致搜索失败 → 配置多仓库备份。

### 7.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 索引 codec | 压缩算法 | 热节点 `lz4`，冷节点 `best_compression` | 比较存储大小和 CPU | 创建时设置 |
| ILM 策略 | 自动化成本控制 | 根据数据 SLA 制定 | 模拟时间流转，检查迁移动作 | 在线生效 |
| 冻结层缓存 | 提升查询性能 | `xpack.searchable.snapshot.shared_cache.size: 10%` | 查询命中率监控 | 动态 |
| 分片大小 | 存储与查询平衡 | 20-40GB | 单个分片过大时触发 reindex | 创建时规划 |

> **时效性提示**：可搜索快照在 8.0+ 已稳定，**请查阅官方文档**。

### 6.1/7.7 已知反模式检查
- **类别**：不分层存储
  - **反模式**：所有数据存储在热节点，成本高且性能无益。
  - **规避**：使用 ILM + 节点属性分层，过期数据降级。
- **类别**：忽略压缩
  - **反模式**：使用默认 `lz4` 存储数年历史数据 → 存储成本过高。
  - **规避**：对历史索引创建新索引并指定 `best_compression`，然后 reindex。

## 原则8：平滑升级与配置演化

> **主归属**：X12（配置演化） | **关联域**：X5（分区扩展）、X10（可观测性）

### 8.1 第一性原理
- **物理/数学约束**：ELasticsearch 版本迭代快，需在不影响业务的情况下升级，且保证数据兼容。
- **推导**：采用滚动升级（从非 master 节点开始，最后升级 master），支持集群版本差异（最多一个版本）。同时使用索引 mapping 演变（只允许增加字段，修改类型需 reindex）。

### 8.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **滚动升级** | 一次升级一个节点，摘除流量，重启后加入 | 零停机 | 升级耗时长 |
| **集群版本兼容** | 允许当前版本 +1 的混合版本 | 逐步升级 | 不支持跨大版本升级 |
| **索引 mapping 演化** | 增加字段、修改 `ignore_above` 等 | 动态适应业务变化 | 删除或修改类型需重建索引 |
| **Reindex 重建索引** | 从旧索引拷贝数据到新索引 | 支持 breaking changes | 消耗资源，需要停机时间窗口 |
| **快照备份** | 升级前全量快照 | 可回滚 | 存储和恢复时间 |

### 8.3 通用实现案例（Elasticsearch 7.x/8.x）
- **滚动升级步骤**：
  1. 禁用分片分配（`cluster.routing.allocation.enable: none`）。
  2. 停止非 master 节点，升级软件，启动。
  3. 重新启用分配，等待节点恢复。
  4. 重复直到所有非 master 节点升级。
  5. 最后升级 master 节点（若不止一个 master 候选，一次一个）。
  6. 完成后再启用重新平衡。
- **Mapping 演化**：默认动态 mapping 会添加新字段；若需修改字段类型，需创建新索引，使用 `_reindex`：
  ```
  POST _reindex
  {
    "source": { "index": "old_index" },
    "dest": { "index": "new_index" }
  }
  ```
  并通过别名切换。
- **快照备份**：
  ```
  PUT /_snapshot/backup/snapshot_1
  {
    "indices": "my_index",
    "ignore_unavailable": true,
    "include_global_state": false
  }
  ```

### 8.4 生产问题与解决
- **问题1：滚动升级后分片无法分配**
  - **根因**：新版本数据格式变化，旧版本节点无法读取。
  - **解决方案**：确保所有节点升级完成后再启用分配；或使用兼容 API 降级。
- **问题2：Mapping 添加字段后导致查询异常**
  - **根因**：字段类型冲突（如以前是 `long`，新数据是 `text`）。
  - **解决方案**：显式定义 mapping 的 `dynamic_templates` 或禁用 dynamic。

### 8.5 边界条件与风险
- **极值风险**：跨两个以上大版本升级（如 6.x → 8.x）不支持滚动，需要全量重建。
- **环境风险**：生产环境升级前未做完整验证 → 在预发环境完整演练。
- **异常风险**：快照恢复失败导致数据丢失 → 定期测试恢复演练。

### 8.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 集群升级检查 | 防止不兼容操作 | 升级前运行 `/_migration/deprecations` | 解决所有警告再升级 | N/A |
| 快照版本 | 兼容性 | 快照与目标版本至少兼容（8.x 可恢复 7.x 快照） | 在预发环境恢复验证 | 创建时确定 |
| 分配禁用 | 升级时安全 | 设置为 `none`，升级完成后恢复 `all` | 观察分片分配日志 | **在线生效** |

### 8.6.1 升级前联动清单
- 检查 deprecation API 无 critical 项。
- 全量快照并验证可恢复。
- 至少预留 30% 磁盘空间用于升级期间的 segment 升级。
- 测试集群完整升级流程。

### 8.7 已知反模式检查
- **类别**：跳过版本兼容性检查
  - **反模式**：直接从 5.x 升级到 7.x → 数据损坏。
  - **规避**：逐步升级（5→6→7→8）。
- **类别**：生产环境直接升级
  - **反模式**：不做预演，直接在生产操作 → 导致长时间不可用。
  - **规避**：克隆生产数据到预发环境，完整演练。

## 原则9：文档级并发控制与批量原子性（SPEC）

> **主归属**：SPEC | **关联域**：X1（一致性模型）、X3（并发控制）

### 9.1 第一性原理
- **物理/数学约束**：Elasticsearch 不提供分布式事务，但通过乐观锁提供文档级原子更新，批量操作需业务自行补偿。
- **推导**：使用 `_seq_no` 和 `_primary_term` 实现乐观锁，利用 `_bulk` 的原子性限制在单个分片内保证顺序，整体失败需业务重试或部分回滚。

### 9.2 解决手段与代价

| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| **乐观锁（版本控制）** | 基于 `if_seq_no` 和 `if_primary_term` | 保证单文档并发安全 | 冲突需重试 |
| **脚本更新** | 通过脚本在服务端进行原子操作（如计数器） | 无需客户端重试 | 脚本性能开销 |
| **批量 API** | `_bulk` 将多个操作打包，任一个失败不影响其他 | 减少网络往返 | 需要检查 `errors` 字段 |
| **索引级写锁** | 一个分片同时只能有一个写入线程 | 保证文档顺序 | 高并发下排队 |

### 9.3 通用实现案例（Elasticsearch 7.x/8.x）
- **乐观锁更新**（见原则2）。
- **脚本原子更新**：
  ```
  POST /my_index/_update/1
  {
    "script": {
      "source": "ctx._source.counter += params.increment",
      "params": { "increment": 1 }
    }
  }
  ```
  脚本在分片内部执行，天然串行。
- **批量操作部分失败处理**：
  ```
  POST _bulk
  { "index": { "_index": "test", "_id": "1" } }
  { "field": "value1" }
  { "index": { "_index": "test", "_id": "1" } }  // 重复 id
  { "field": "value2" }
  ```
  响应中 `errors: true`，业务需检查每个 item 状态，决定重试或记录。

### 9.4 生产问题与解决
- **问题1：大量乐观锁冲突导致写入失败**
  - **根因**：热点文档（如商品库存）。
  - **解决方案**：使用脚本更新（原子操作）；或设计为独立文档用 `_bulk` 索引新版本，查询时取最新。
- **问题2：批量操作中部分成功，如何保证业务一致性**
  - **根因**：`_bulk` 不提供全部回滚。
  - **解决方案**：设计幂等操作，重试失败项；或使用队列确保最终一致。

### 9.5 边界条件与风险
- **极值风险**：乐观锁重试无限循环 → 设置最大重试次数和超时。
- **环境风险**：脚本使用 Groovy 可能导致安全漏洞（已默认禁用）→ 使用 Painless 并限制脚本参数。
- **异常风险**：批量大小过大导致部分成功难以追踪 → 每批控制在 5k 文档以内。

### 9.6 参数调优与验证（原则性指引）

| 参数类别 | 核心作用 | 配置原则 | 验证方法 | 动态生效 |
| :--- | :--- | :--- | :--- | :--- |
| 乐观锁重试 | 冲突恢复 | 客户端实现指数退避，最多 3 次 | 高并发压测，监控 409 | SDK |
| 脚本编译缓存 | 提升脚本性能 | `script.max_compilations_rate: "75/5m"` | 监控编译速率限制 | 动态 |
| 批量请求大小 | 原子性粒度 | 根据网络和文档大小调整 | 压测找到最佳值 | 客户端 |

### 9.6.1 联动清单（幂等设计）
- 为每个操作生成幂等 ID，使用 `_doc` 的 `_id` 保证相同 ID 只索引一次。
- 使用 `_update` 的 `doc_as_upsert` 实现“不存在则创建”。

### 9.7 已知反模式检查
- **类别**：依赖 ES 的事务性
  - **反模式**：期望 `_bulk` 全有或全无 → 无此保证。
  - **规避**：业务应用层实现补偿逻辑。
- **类别**：使用脚本做复杂事务
  - **反模式**：在脚本中调用外部服务 → 阻塞线程池。
  - **规避**：脚本只做简单算术和条件判断。

## 全局权衡矩阵

| 原则对 | 冲突点 | 权衡建议 |
| :--- | :--- | :--- |
| 原则1（副本） ↔ 原则3（性能） | 副本越多写入越慢 | 默认副本数 1，重要索引可设 2，但平衡写入延迟 |
| 原则2（一致性） ↔ 原则3（性能） | 同步复制降低性能 | 日志场景用异步；金融场景用同步+高配置硬件 |
| 原则4（扩展性） ↔ 原则1（高可用） | 分片过多影响恢复时间 | 分片数控制在 1000 以内，单分片 20-40GB |
| 原则5（安全） ↔ 原则3（性能） | TLS 增加 CPU | 内网可关闭双向验证，公网必须开启 |
| 原则6（可观测） ↔ 原则7（成本） | 监控消耗资源 | 监控数据存储专用小集群，保留短时间 |
| 原则7（成本） ↔ 原则3（性能） | 冷数据查询慢 | 明确业务要求，冷数据仅用于低频分析 |
| 原则8（可演进） ↔ 原则1（稳定性） | 升级可能破坏数据 | 严格遵循滚动升级，先预演再生产 |
| 原则9（原子性） ↔ 原则3（性能） | 乐观锁重试增加延迟 | 热点文档用脚本更新，避免高冲突 |
