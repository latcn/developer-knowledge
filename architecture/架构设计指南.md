  **核心目标**：控制软件复杂度，提升代码可读性和系统的可维护性，围绕需求变更进行设计

## 第一部分：软件架构基础

### 1.1 软件的类型与开发方法

| 开发方法 | 适用场景 | 特征 |
|----------|----------|------|
| **迭代法** | 商业项目，需求不确定性高，设计复杂，后期更改代价低 | 计划、需求、架构、构建、测试交叉进行 |
| **序列法** | 性命攸关的项目，需求稳定，设计清晰，后期更改代价高 | 稳定的需求逐一执行 |
| **混合法** | 使命攸关的项目 | 介于两者之间 |

### 1.2 软件开发的先决条件

- **问题定义**：确定目标，明确要解决什么问题。
- **需求**：明确需求，避免争论；面向需求变更开发，演进交付。
- **架构**：开闭原则，抽离变化，关注安全、性能、可伸缩、错误处理、容错；避免过度工程；保持概念完整性。

### 1.3 软件设计的核心原则

#### 七大设计原则

| 原则 | 核心定义 | 实践要点 |
|------|----------|----------|
| **开闭原则** | 对修改关闭，对扩展开放 | 抽象约束，封装变化 |
| **里氏替换** | 子类可替换父类而不影响系统行为 | 尽量避免从具体类继承；组合优于继承 |
| **依赖倒置** | 面向接口编程，不面向实现 | 变量声明用接口/抽象类；不从具体类派生；不覆盖已实现方法 |
| **单一职责** | 一个类/方法只负责一项功能 | 高内聚、低耦合 |
| **接口隔离** | 接口应小而专 | 不同调用者依赖不同的接口 |
| **迪米特法则** | 最少知识原则 | 减少对象之间直接交互，通过第三方转发 |
| **合成复用** | 优先使用组合而非继承 | 提高灵活性 |

#### 设计模式本质

> 控制不变部分，将变化部分提取出来，增加代码复用率。多用组合，少用继承；依据接口实现变化的行为，面向接口编程，不对实现编程。

#### 常见模式要点

- **策略模式**：定义算法族，封装起来，使其可相互替换，让算法的变化独立于使用算法的客户。
- **模板方法**：定义算法步骤，允许子类为一个或多个步骤提供实现。

### 1.4 软件设计的质量属性

| 属性 | 目标 | 糟糕设计的标志 |
|------|------|----------------|
| **僵化性** | 易于改动 | 微小改动引起更大改动 |
| **脆弱性** | 改动不引入意外BUG | 微小改动导致莫名奇妙的BUG |
| **牢固性** | 易于拆分和复用 | 无法有效拆分，复用困难 |
| **粘滞性** | 优秀方案更容易实施 | 糟糕代码比优秀方案更容易实施 |
| **晦涩性** | 代码清晰易懂 | 难以理解 |

**最终目标**：清晰、低耦合、可预测、可扩展、可复用。

### 1.5 分布式系统基础理论

#### CAP 定理
分布式系统无法同时保证 **一致性（C）**、**可用性（A）** 和 **分区容错性（P）**，必须三选二。在实际系统中，P 是必选项，因此设计通常在 C 和 A 之间权衡。

#### BASE 理论
- **基本可用（Basically Available）**：允许响应延迟或部分功能不可用。
- **软状态（Soft State）**：系统中存在中间状态，允许不同节点数据副本出现短暂不一致。
- **最终一致性（Eventually Consistent）**：经过一段时间后，所有数据副本最终达到一致。

BASE 是 CAP 在 AP 系统中的工程落地，Seata、RocketMQ 事务消息、本地消息表等均属于 BASE 框架下的具体实现。

## 第三部分：关键架构领域与技术选型

### 3.1 分布式架构

**应对高并发**：垂直伸缩（提升单机性能） vs 水平伸缩（分布式集群）

**技术方案组合**：
- 分布式缓存
- 负载均衡
- 反向代理与CDN
- 分布式消息队列
- 分布式数据库 / NoSQL
- 分布式文件系统
- 搜索引擎
- 微服务
- **云原生基础设施**：容器化（Docker）、编排（Kubernetes）、服务网格（Istio/Linkerd）

### 3.2 缓存架构

#### 类型对比

| 类型 | 工作机制 | 示例 |
|------|----------|------|
| **通读缓存** | 缓存代理数据源，应用无感知 | CDN、反向代理 |
| **旁路缓存** | 应用主动读写缓存 | Redis、Memcached |

#### 脏数据解决

- **过期失效**：设置较短TTL，缓存失效后重新加载（适用于热点数据）
- **失效通知**：更新数据源时发送通知，清除缓存

#### 一致性哈希

- 物理节点虚拟化为多个虚拟节点，放置于哈希环上，解决节点增减时大量数据迁移问题。

#### 选型对比表（修正后）

| 特性 | Redis | Memcached | Caffeine（本地） |
|------|-------|-----------|------------------|
| 数据结构 | 丰富 | 仅string | 仅string/对象 |
| 持久化 | RDB+AOF | 无 | 无 |
| 高可用 | 哨兵/Cluster | 客户端分片 | 无 |
| 性能（参考） | 单节点 **8-15 万 QPS**（4核8万，8核12万，峰值15万） | 多线程更高 | 延迟 **微秒级**，吞吐量比 Guava Cache 高 40%+ |
| 适用 | 复杂结构、需持久化 | 纯缓存、大value | 单机高频读 |

> 注：Redis 6.0+ 支持多线程 I/O（**仅网络读写，命令执行仍为单线程**；默认关闭，需配置 `io-threads` 和 `io-threads-do-reads` 启用）。以上数据为官方基准 + 第三方实测综合参考值。

### 3.3 异步架构（消息队列）

#### 优势

1. 改善写操作响应时间
2. 更容易伸缩（拆分资源消耗大的功能）
3. 削峰填谷
4. 隔离失败
5. 降低耦合

#### 消息队列选型对比

| 特性 | RocketMQ | Kafka | RabbitMQ | Pulsar |
|------|----------|-------|----------|--------|
| 吞吐量 | 单实例约 7 万条/秒，3 Broker 最高 12 万条/秒 | 百万级/s | 万级/s | 高 |
| 延迟（P99） | 3-50ms（优化后可达 3ms 以下） | 默认配置毫秒级；**acks=-1 配置下 P99 可能升至秒级** | 微秒级 | 毫秒级 |
| 事务消息 | **支持（需实现回查接口）** | 不支持（但可幂等） | 弱 | 支持 |
| 顺序消息 | 支持（全局/分区） | 支持（分区内） | 不支持 | 支持 |
| 适用场景 | 金融、电商、事务要求高 | 日志收集、大数据管道、流处理 | 复杂路由、低延迟小消息 | 云原生、多租户、存储计算分离 |

> 数据来源：Apache RocketMQ 官方基准、KIP-618（生产者延迟改进）、各项目官方文档。

### 3.4 负载均衡架构

- **反向代理**：Nginx，七层负载均衡
- **IP负载均衡**：LVS，流量经过负载均衡器
- **数据链路负载均衡**：直接修改MAC地址，应用服务器和负载均衡器共享虚拟IP，响应直接返回客户端
- **典型组合**：LVS + Nginx

### 3.5 数据存储架构

- **数据库主从复制**：读写分离
- **数据库分片**：水平分片 vs 垂直分片

#### 读写分离
通过主库处理写操作，从库处理读操作，可配置强制主库读（避免复制延迟）。常用实现包括 ShardingSphere-JDBC、MySQL Router 等。

#### 分片方案对比

| 方案 | 实现位置 | 跨分片查询 | 事务 | 运维成本 | 典型代表 |
|------|----------|------------|------|----------|----------|
| 应用层分片 | 应用代码 | 困难 | 补偿/XA | 低 | 自定义路由 |
| 中间件 | 代理/JDBC | 支持但降性能 | 柔性事务 | 中 | ShardingSphere |
| 分布式数据库 | 原生 | 原生支持 | 分布式ACID | 高 | **TiDB、OceanBase、CockroachDB、Google Spanner** |

### 3.6 微服务架构

#### 单体困难
- 编译、部署困难
- 代码分支管理困难
- 数据库连接耗尽
- 新增业务困难
- 发布困难

#### SOA与微服务
- Dubbo 借鉴 SOA 架构，采用二进制协议，服务注册中心
- 微服务与业务强相关，需先做好业务模块化设计（低耦合、高内聚）

### 3.7 搜索引擎架构

> **说明**：原文档引用的 GitHub 链接 `https://github.com/itisaid/sokeeper` 已失效，不再推荐。

> - **Elasticsearch**：分布式、RESTful，基于 Lucene，适合日志、全文检索。
> - **Solr**：成熟、强大的全文检索，支持分布式索引。
> - **Meilisearch**：轻量级、开箱即用，适合中小型应用。

### 3.8 高性能架构

**优化路径**（迭代进行）：
1. 数据中心优化（多数据中心）
2. 硬件优化（CPU/网卡/硬盘）
3. 操作系统优化（如透明大页）
4. 虚拟机优化（JVM）
5. 基础组件优化（Web容器、连接池）

### 3.9 高可用架构

- 冗余备份（多台服务，负载均衡）
- 失败隔离（消息队列）
- 限流降级（关闭非核心功能）
- 异地多活（数据冲突避免）
- 自动化测试减少BUG
- 自动化监控、灰度发布
- **可观测性**（见第 3.11 节）

> 分布式系统基础理论（CAP/BASE）见第 1.5 节。

### 3.10 安全性架构（修正后）

| 攻击类型 | 原理 | 防御手段 |
|----------|------|----------|
| **XSS** | 恶意脚本在浏览器执行 | **三层防御**：①输入校验与输出转义（HTML实体编码）；②内容安全策略（CSP）；③HttpOnly Cookie（仅防止会话劫持，不能阻止攻击本身） |
| **CSRF** | 挟持会话发起非本意请求 | HTTP Referer校验；Token（双重提交Cookie或服务端Token） |
| **SQL注入** | 拼接SQL | SQL预编译；参数化查询；ORM框架安全使用 |
| **HTTP劫持** | 运营商劫持 | HTTPS |
| **DNS劫持** | 篡改DNS解析 | DNSSEC；使用可信DNS；DoH/DoT |
| **DDoS** | 大量请求耗尽资源 | 限流、WAF、CDN、云防护 |

#### 密钥管理
- 禁止硬编码密钥、密码、API Token。
- 使用密钥管理服务：HashiCorp Vault、AWS Secrets Manager、Azure Key Vault 或 Kubernetes Secrets + 外部密钥存储（如 External Secrets Operator）。
- 环境变量注入或动态挂载。

#### Web 应用防火墙（WAF）选型

- **开源方案**：**Coraza WAF**（OWASP 主导，兼容 ModSecurity 规则集，是目前推荐的 ModSecurity 继任者）。原 ModSecurity 官网已停止维护，仅接收安全补丁。
- **云原生 WAF**：AWS WAF、Cloudflare WAF、Azure WAF、阿里云 WAF，推荐生产环境使用。

### 3.11 可观测性架构

> **推荐使用 [OpenTelemetry](https://opentelemetry.io/) 作为统一的数据采集和导出标准**，它提供与语言无关的 API、SDK，可生成 metrics/logs/traces，并兼容 Prometheus、Jaeger 等后端。

#### 三大支柱

| 支柱 | 工具示例 | 作用 |
|------|----------|------|
| **Metrics** | Prometheus + Grafana | 收集 CPU、内存、QPS、延迟等指标，设置告警 |
| **Logging** | ELK（Elasticsearch, Logstash, Kibana） / Loki | 集中日志存储、查询、分析 |
| **Tracing** | Jaeger / SkyWalking / Zipkin | 追踪跨服务请求链路，定位性能瓶颈 |

#### AI 辅助架构特有监控点
- AI 生成代码的调用量、异常率、架构违规趋势（如 ArchUnit 测试失败次数热力图）
- 技术债务标记（`// FIXME [TechDebt]`）自动上报，可视化债务分布

#### 服务等级目标（SLO）
- 按服务类型分级定义 SLO（如核心交易接口 P99 < 200ms，可用性 99.99%）
- 定期评估 SLO 达成情况，公示未达标项并跟踪改进

### 3.12 云原生架构设计

#### 容器化与编排
- **Docker**：应用打包为镜像，环境一致、快速部署
- **Kubernetes**：自动伸缩、滚动更新、服务发现、自我修复。当前稳定版本为 **v1.36**（2026 年 4 月发布），推荐使用。
- **服务网格**：Istio **v1.25**（2026 年 5 月发布）、Linkerd，提供无侵入的流量管理、可观测性、安全（mTLS）

#### 镜像与安全
- 镜像分层优化：减少层数、使用轻量基础镜像（Alpine、Distroless）
- 镜像漏洞扫描：Trivy / Grype
- 运行时安全：Pod 安全策略（或 Kyverno）、Seccomp、AppArmor

### 3.13 大数据与AI架构

- **分布式存储**：HDFS
- **分布式计算**：MapReduce、Spark
- **AI 与物联网**：大数据算法发现数据关联关系
- **区块链**：去信任的跨组织合作（生产关系革命）

## 第四部分：高质量代码设计

### 4.1 设计概念与实践

| 原则 | 解释 |
|------|------|
| **最小复杂度** | 简单易于理解，可专注于程序的一部分 |
| **易于维护** | 修改和扩展容易 |
| **松散耦合** | 模块间依赖弱 |
| **可扩展、可重用** | 设计支持未来变化 |
| **高扇入** | 一个类被大量类使用（复用度高） |
| **低扇出** | 一个类使用少量其他类（依赖少） |
| **精简** | 没有多余代码 |
| **层次** | 分层、子系统通信限制、一致抽象、信息隐藏 |

### 4.2 防御式编程

- 检查所有外部输入
- 使用断言捕获内部错误
- 限制错误传播范围
- 使用异常处理（但不要用异常控制正常流程）

### 4.3 伪代码先行

先用自然语言或简单代码描述逻辑，再逐步细化，最后生成实现。这种方法尤其适用于 AI 辅助编程时保持设计意图。

## 第五部分：AI Coding 下的架构设计（生产实践）

### 5.1 核心理念

> AI 是实现的加速器，架构是质量的定盘星。架构决策必须由人做出，AI 只能执行；所有 AI 生成的代码必须通过架构约束自动验证。

### 5.2 前期准备：机器可读的架构规则集

| 工具 | 当前版本（截至 2026‑06） | 作用 | 示例 |
|------|------------------------|------|------|
| **ArchUnit** | v1.4.2 (2026-04) | 检查包、类、依赖 | `noClasses().that().resideInAPackage("..controller..").should().dependOnClassesThat().resideInAPackage("..dal..")` |
| **Checkstyle** | v13.4.1 (2026-04) | 命名、风格 | 可自定义团队规范（如 DTO 包命名） |
| **PMD** | v7.22.0 (2026-02) | 代码静态分析 | 检测空 catch、未使用变量等 |
| **SonarQube** | 2026.1 LTA (2026-01) | 代码质量门禁 | 支持 AI 生成代码专项扫描 |
| **CodeQL** | Bundle v2.23.9 (2026-01) | 安全漏洞扫描 | 检测 SQL 注入、硬编码密钥等 |

**操作步骤**：
1. 列出项目架构分层（如 Controller → Service → Repository → DB）

3. 将架构测试集成到 `mvn verify` / `gradle check` 中，CI 失败则阻断合并

### 5.4 AI 生成权限分级

| 区域 | 权限 | 要求 |
|------|------|------|
| 值对象、DTO、枚举 | ✅ 完全自主 | 符合规范 |
| 简单CRUD | ✅ 自主 | 通过ArchUnit |
| 工具类、转换器 | ✅ 自主 | 同时生成单元测试 |
| 核心业务逻辑 | ⚠️ 仅生成骨架 | 人工填充分支 |
| 事务边界 | ❌ 禁止AI决定 | 人工标注@Transactional |
| 缓存、异步 | ❌ 禁止AI自动添加 | 需设计评审 |
| 第三方集成 | ⚠️ 隔离在Adapter | 安全审查 |

#### 角色说明
- **AI 提示工程师**：**推荐设置**（非可选）。据 Gartner 2025 年报告，58% 的大型企业已设立此岗位；预测到 2027 年，70% 的企业将在软件工程团队中设置 AI 工程相关岗位。

### 5.5 人机协作五步法

1. **人工定义模块边界与接口**（架构师+领域专家）
2. **AI生成模块骨架**（使用提示词模板）
3. **人工补充架构关键决策点**（事务、缓存、安全、异常）
4. **AI生成单元测试与集成测试**
5. **架构验证闭环**（CI自动执行ArchUnit、质量门禁、安全扫描）

### 5.6 推荐的包结构

```
com.company.project
├── module-order
│   ├── api/               # 对外接口（人工）
│   ├── application/       # 应用层（AI生成+人工补事务）
│   ├── domain/            # 领域层（AI生成实体）
│   ├── infrastructure/    # 基础设施（AI生成，需隔离）
│   └── ui/                # 控制器（AI生成+人工加权限）
└── shared/
    ├── arch/              # 架构测试规则
    ├── util/
    └── exception/
```

### 5.7 质量保障

#### 三层审查机制

| 审查层级 | 执行人 | 关注点 | 工具辅助 |
|----------|--------|--------|----------|
| **自动检查** | CI | 架构约束、代码规范、安全漏洞、重复率 | ArchUnit, SonarQube, CodeQL |
| **人工审查** | 同组开发人员 | 业务逻辑正确性、异常处理、性能隐患 | GitHub PR 评论 |
| **架构审查** | 架构师 / Tech Lead | 设计是否匹配 ADR、是否引入不必要的复杂度 | 每周架构评审会 |

#### AI 代码元信息

在文件头部自动添加注释，标明生成工具和时间，便于追溯。

```java
/**
 * @generated-by Cursor (2026-06-08)
 * @reviewed-by [人工审查者姓名] (待填写)
 * @architecture-check ArchUnit passed
 */
```

#### 技术债务标记与自动化追踪（扩展）

- 标记：`// FIXME [TechDebt: 2026-07-30] 当前使用本地缓存，需替换为 Redis 集群`
- 自动化：使用 SonarQube AI 代码专项扫描（2026 LTA 版支持）识别常见 AI 债务，生成债务热力图。
- **常见 AI 技术债类型**：

| 债务类型 | 表现形式 | 检测工具 |
|----------|----------|----------|
| 代码复用率低 | AI 为每个场景生成相似但非复用的代码 | SonarQube 重复率检测 |
| 抽象缺失 | AI 倾向直接实现，不提取接口/抽象类 | ArchUnit 接口覆盖检查 |
| 事务边界模糊 | AI 不理解分布式事务，随意加或不加 @Transactional | 自定义 ArchUnit 事务检查规则 |
| 配置硬编码 | AI 从训练数据中学习硬编码习惯 | CodeQL 配置检测规则 |

### 5.8 风险应对速查

| 风险       | 迹象             | 行动                         |
| -------- | -------------- | -------------------------- |
| **架构侵蚀** | CI 架构测试失败次数增加  | 暂停 AI 合并，修正提示词             |
| **循环依赖** | 修改引发多模块重编译     | 运行 `jdeps`，用 ArchUnit 禁止   |
| **重复代码** | Sonar 重复率 > 5% | 提取公用类，更新提示词                |
| **安全漏洞** | CodeQL 报高危     | 禁止 AI 生成 Statement/反射/eval |
| **过度设计** | 大量单实现接口        | 重构为简单类，增加约束                |

- 不要把解决方案当作问题的定义

- **向上沟通**：用封闭式问题（提供多个方案）

- **彼得定律**：所有职位都被不能胜任的人承担
- **目标型管理**：将问题转化为目标，优于问题驱动或流程驱动
- **力量与温暖平衡**：整合技术、资源、决策力，同时善于聆听

### 附录B：架构设计面试/答辩问答集（精选，含修正要点）

**Q1：如何保证秒杀系统不超卖？**
- 前置校验（CDN、Nginx限流、网关限流）
- 库存预热到 Redis，Lua 原子扣减
- 下单减库存，超时未支付回滚
- 消息队列异步落库
- 事务消息保证最终一致性

**Q2：单体演进微服务的坑？**
- 分布式事务（Seata + 消息补偿）
- 服务发现延迟（调整心跳 + 本地缓存）
- 跨服务查询（CQRS 或聚合服务）
- 链路追踪（SkyWalking）
- 数据库连接爆炸（分库分表）

**Q3：如何设计时序数据平台（IoT）？**
- 接入层：MQTT 集群或 Kafka
- 缓冲：Kafka 按设备 ID 分区
- 处理：Flink 清洗
- 存储：时序数据库（冷热分离）
- 查询：预聚合、元数据路由

**Q4：如何处理分布式最终一致性？**
- 本地消息表 + 定时轮询 MQ
- 事务消息（RocketMQ，需实现回查接口）
- SAGA（Seata）
- 幂等设计（唯一键 + 数据库唯一索引）

**Q5：架构评审最看重的质量指标？**

| 指标 | 度量 | 目标 |
|------|------|------|
| 性能 | P99 延迟、TPS | <200ms, >5000 |
| 可用性 | SLA、MTTR | 99.99%, <15min |
| 可扩展性 | 水平伸缩线性度 | 1倍节点 → 80%+ 吞吐 |
| 可维护性 | 圈复杂度、部署时间 | <10, <5min |
| 安全性 | 漏洞扫描 | 无高危 |
| 可观测性 | 日志/Trace 覆盖率、SLO 达成率 | 核心服务 >95% |

**Q6：如何重构复杂模块？**
- 提取变化部分
- 引入状态/策略模式
- 依赖倒置
- 单一职责
- 效果：新增只需加类，测试覆盖率提升

**Q7：如何避免过度设计？**
- YAGNI 原则
- 先简单实现，第二次出现类似需求再抽象
- 定期技术债评审
- 规则适用于特定场景

### 附录C：学习与成长方法

- **5-20-2 法则**：5分钟了解场景 → 20分钟理解原理 → 2小时深入细节

## 结语

> 技术总是在变，但“清晰、低耦合、可预测、可扩展、可复用”的目标不变。AI Coding 让实现更快，但只有架构纪律能让系统走得更远。本文档覆盖了从基础原则、设计方法、技术选型、AI 辅助架构实施到团队协作的完整体系，可作为团队架构设计的基准与演进起点。
