## 第零章：Sentinel 的设计本质与第一性原理

### 0.1 设计目的
Sentinel 的核心目的是为分布式系统提供**流量控制、熔断降级、系统负载保护**的轻量级组件，解决微服务雪崩效应，保障系统高可用。

### 0.2 解决的根本问题
1. **流量突增**：瞬时洪峰压垮系统 → 限流（QPS/并发线程数）提前拒绝超额请求。
2. **依赖不稳定**：下游服务变慢或错误率飙升 → 熔断降级，快速失败或回退。
3. **系统负载过高**：CPU、Load、RT 等指标异常 → 系统自适应保护，自动调整通过阈值。

### 0.3 适用场景
- API 网关、微服务入口流量控制
- 慢调用、异常比例熔断
- 热点参数限流（防缓存击穿、防刷）
- 集群流控（精确控制集群总 QPS）
- 系统负载保护（防止系统过载）

### 0.4 核心设计矛盾与原则映射
| 矛盾 | 对应原则 |
| :--- | :--- |
| 精确限流 vs 性能 | 原则1（滑动窗口统计） |
| 熔断恢复 vs 错误容忍 | 原则2（熔断器状态机） |
| 规则动态 vs 一致性 | 原则3（规则管理与动态推送） |
| 单机 vs 集群 | 原则4（集群流控） |
| 系统保护 vs 误杀 | 原则5（系统自适应保护） |
| 可观测 vs 开销 | 原则6（指标与监控） |
| 扩展性 vs 复杂性 | 原则7（SPI 扩展点） |

### 0.5 原则规划与推理草稿
基于用户需求（Sentinel、关注全维度），规划以下7个原则域：
1. [N2 通信容错] → 流量控制算法与滑动窗口（性能、高可用）
2. [X8 故障检测] → 熔断降级与状态机（高可用）
3. [X12 配置演化] → 规则管理与动态推送（可演进性、扩展性）
4. [X7 分布式锁] → 集群流控（一致性、扩展性）
5. [C1 计算资源] → 系统自适应保护（高可用、成本）
6. [X10 可观测性] → 指标、日志、监控（可观测）
7. [X12 配置演化] → SPI 扩展机制（扩展性、可演进性）

**推理草稿**：长事务不适用 Sentinel；一致性由集群流控中的 Token Server 保证；成本通过系统自适应保护提升资源利用率体现。

## 原则 1：流量控制与滑动窗口（N2）

### 1.1 第一性原理
- **物理/数学约束**：请求速率不可控，需精确统计 QPS/并发线程数。
- **推导**：滑动窗口计数器（LeapArray）实现高精度、低开销的实时统计。

### 1.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 直接拒绝 | 超过阈值直接拒绝 | 简单 | 可能导致误杀 |
| 匀速排队（漏桶） | 控制请求间间隔 | 削峰填谷 | 请求可能排队超时 |
| Warm Up（令牌桶） | 预热期逐步增加阈值 | 保护刚启动系统 | 参数需压测 |

### 1.3 通用实现案例
- **QPS 限流**：`FlowRule` 设置 `grade = RuleConstant.FLOW_GRADE_QPS`, `count = 100`
- **匀速排队**：`controlBehavior = RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER`

### 1.4 生产问题与解决
- **限流精度不够**：滑动窗口格子数（默认 2）可调大，提高精度。
- **WarmUp 预热时间不足**：JIT 编译、连接池初始化需更长预热时间 → 调大 `warmUpPeriodSec`。
- **匀速排队超时**：`maxQueueingTimeMs` 默认 500ms，过大则线程堆积。

### 1.5 边界条件与风险
- **极值风险**：滑动窗口格子数过多 → 内存膨胀、统计开销增大。
- **冷启动陡升**：WarmUp 使用指数衰减模型，可能无法完全平滑 → 调整 `coldFactor`。

### 1.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `grade` | 限流维度 | QPS / 并发线程数 | 在线 | 压力测试 |
| `count` | 阈值 | 压测确定 | 在线 | 观察限流触发 |
| `warmUpPeriodSec` | 预热时长 | 30-60s | 在线 | 启动后 QPS 曲线 |
| `controlBehavior` | 流控效果 | 快速失败/匀速/预热 | 在线 | 压测延迟 |

### 1.6.1 参数联动清单
- **场景**：匀速排队 + `maxQueueingTimeMs`
- **风险**：队头阻塞，长期占用线程 → 限制 `maxQueueingTimeMs` ≤ 500ms。

### 1.7 已知反模式检查
- **反模式**：QPS 限流阈值设得过低 → 误杀正常流量。
- **规避**：基于压测确定合理阈值，并动态调整。

## 原则 2：熔断降级与状态机（X8）

### 2.1 第一性原理
- **物理/数学约束**：依赖服务故障会扩散。
- **推导**：熔断器三态（关闭→打开→半开），基于错误率/慢调用比例自动切换。

### 2.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 慢调用比例 | RT 大于阈值比例触发 | 防止慢服务拖垮 | 需配置 RT 阈值 |
| 异常比例 | 异常比例触发 | 应对下游异常 | 需区分业务异常 |
| 异常数 | 固定次数触发 | 简单 | 不适用于比例 |

### 2.3 通用实现案例
- **慢调用熔断**：`DegradeRule` 设置 `grade = RuleConstant.DEGRADE_GRADE_RT`, `count = 1000`, `timeWindow = 10`

### 2.4 生产问题与解决
- **熔断后恢复慢**：`timeWindow` 后单请求探测，若成功则关闭；若失败则继续打开。
- **慢调用 RT 阈值过小**：正常调用偶超时 → 误触发熔断。
- **异常比例阈值不合理**：业务异常导致误熔断 → 熔断规则忽略业务异常（需配置）。

### 2.5 边界条件与风险
- **极值风险**：半开探测期间若大量请求涌入，可能瞬间击垮。
- **最小请求数**：`minRequestAmount` 默认 5，小于该值不触发熔断。

### 2.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `grade` | 熔断策略 | RT / 异常比例 / 异常数 | 在线 | 注入故障 |
| `count` | 阈值 | RT（ms）或比例 | 在线 | 观察熔断触发 |
| `timeWindow` | 熔断时长 | 10-60s | 在线 | 恢复时间 |
| `minRequestAmount` | 最小请求数 | 5-10 | 在线 | 模拟小流量 |

### 2.6.1 参数联动清单
- **场景**：慢调用熔断 + 统计窗口 `statIntervalMs`
- **风险**：窗口内请求数不足 `minRequestAmount` 不触发。

### 2.7 已知反模式检查
- **反模式**：熔断后无降级逻辑 → 用户直接看到错误。
- **规避**：配置 `fallback` 或 `blockHandler` 返回默认值。

## 原则 3：规则管理与动态推送（X12）

### 3.1 第一性原理
- **物理/数学约束**：限流熔断规则需频繁调整，不能每次重启。
- **推导**：规则配置中心（Nacos、Apollo、Zookeeper），实时推送更新。

### 3.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 本地文件 | 读取本地 JSON | 简单 | 无动态 |
| Pull 模式 | 客户端定时拉取 | 解耦 | 延迟高 |
| Push 模式 | 配置中心推送 | 实时 | 依赖配置中心 |

### 3.3 通用实现案例
- **Nacos**：`ReadableDataSource` 监听配置变更。

### 3.4 生产问题与解决
- **规则推送延迟**：网络问题导致延迟 → 使用长轮询或 gRPC 流。
- **规则不一致**：不同节点更新顺序不同 → 最终一致可接受。
- **规则失效**：未正确初始化数据源 → 检查日志。

### 3.5 边界条件与风险
- **极值风险**：配置中心全部宕机 → 本地内存规则仍生效，但无法变更。
- **配置格式错误**：解析失败 → 保留原有规则。

### 3.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `dataSource` | 数据源 | Nacos/ZK/Apollo | 在线 | 修改配置测试 |
| `rule-type` | 规则类型 | flow / degrade / system | 在线 | 查看规则列表 |

### 3.6.1 参数联动清单
- **场景**：多规则数据源
- **涉及参数**：不同数据源不能冲突。

### 3.7 已知反模式检查
- **反模式**：生产使用原始模式（内存） → 重启丢规则。
- **规避**：必须使用 Push 模式 + 配置中心持久化。

## 原则 4：集群流控（X7）

### 4.1 第一性原理
- **物理/数学约束**：单机限流无法精确控制集群总 QPS。
- **推导**：Token Server 集中发放令牌，客户端申请。

### 4.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 嵌入模式 | Token Server 与业务应用共用 | 简单 | 资源争抢 |
| 独立部署 | 单独进程 | 隔离性好 | 额外部署成本 |

### 4.3 通用实现案例
- **独立 Token Server**：`<dependency>` `sentinel-cluster-server-envoy`。

### 4.4 生产问题与解决
- **Token Server 单点**：部署多实例，客户端故障转移。
- **网络抖动导致申请失败**：降级为单机限流或快速失败。
- **Token Server 负载高**：扩容节点，一致性哈希分配 namespace。

### 4.5 边界条件与风险
- **极值风险**：Token Server 全挂 → 服务降级策略（`fallbackToLocalWhenFail` 控制）。
- **配额分配不均**：使用负载均衡算法优化。

### 4.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `token-server` | 启动模式 | server / client | 需重启 | 日志确认 |
| `port` | 通信端口 | 默认 18730 | 需重启 | netstat 检查 |
| `fallbackToLocalWhenFail` | 降级策略 | true | 在线 | 模拟 server 宕机 |

### 4.6.1 参数联动清单
- **场景**：多 namespace
- **涉及参数**：namespace 必须一致，否则无法通信。

### 4.7 已知反模式检查
- **反模式**：Token Server 与业务应用混部 → 资源竞争。
- **规避**：生产环境独立部署 Token Server 集群。

## 原则 5：系统自适应保护（C1）

### 5.1 第一性原理
- **物理/数学约束**：系统容量有限，过载会崩溃。
- **推导**：监控系统负载（Load、CPU、RT、入口 QPS、线程数），自动调节通过流量。

### 5.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| Load 保护 | 系统 load1 > 阈值 | 防止系统过载 | 需配置合适阈值 |
| CPU 保护 | CPU > 阈值 | 保护 CPU | 可能过于敏感 |
| RT 保护 | 平均 RT > 阈值 | 保护服务 | 依赖统计 |
| 入口 QPS 保护 | 入口总 QPS 超过阈值 | 整体限流 | 忽略内部链路 |

### 5.3 通用实现案例
- **系统规则**：`SystemRule` 设置 `highestSystemLoad = 3.0`, `avgRt = 1000`

### 5.4 生产问题与解决
- **Load 阈值在容器环境不准确**：应使用 CPU 使用率替代。
- **系统规则误触发**：阈值过于保守 → 根据压测调高。
- **RT 保护与业务 RT 关系**：业务 RT 本就高时需调高阈值。

### 5.5 边界条件与风险
- **极值风险**：Load 采样周期长，响应慢。
- **CPU 保护开启后，瞬间高负载可能来不及反应**：需配合限流。

### 5.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `highestSystemLoad` | Load 阈值 | 根据核数 * 0.8 | 在线 | 压测触发 |
| `avgRt` | 平均响应时间阈值 | 业务 RT * 1.5 | 在线 | 模拟慢调用 |
| `maxThread` | 并发线程数阈值 | 根据线程池大小 | 在线 | 模拟线程堆积 |

### 5.6.1 参数联动清单
- **场景**：容器环境
- **涉及参数**：需使用 CPU 使用率而非 Load。

### 5.7 已知反模式检查
- **反模式**：系统规则阈值设置过高 → 无保护作用。
- **规避**：压测确定系统容量，再设置阈值。

## 原则 6：可观测性（X10）

### 6.1 第一性原理
- **物理/数学约束**：限流熔断效果需量化。
- **推导**：指标（通过 QPS、拒绝 QPS、熔断次数）、日志、链路追踪。

### 6.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| 指标暴露 | Prometheus 导出 | 实时监控 | 存储开销 |
| 事件记录 | 记录触发限流/熔断事件 | 定位问题 | 日志量大 |
| 控制台（Dashboard） | 实时监控、管理规则 | 可视化 | 需部署 |

### 6.3 通用实现案例
- **Prometheus**：`sentinel-datasource-metrics` 导出。
- **Dashboard**：`sentinel-dashboard` 包。

### 6.4 生产问题与解决
- **指标基数爆炸**：按资源名聚合，避免高基数标签。
- **控制台无数据**：检查 transport 端口（8719）是否可达。
- **日志过多**：限频或采样记录。

### 6.5 边界条件与风险
- **极值风险**：大量拒绝事件打爆日志。
- **控制台与客户端版本不匹配**：需同版本。

### 6.6 健康检查最佳实践
Sentinel 本身不提供独立健康端点，但可通过 QPS 或拒绝数判断。K8s 探针建议使用 TCP 端口检测或调用 `/actuator/health`（如果集成 Spring Boot）。

```yaml
livenessProbe:
  tcpSocket:
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
```

### 6.7 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |

## 原则 7：SPI 扩展机制（X12）

### 7.1 第一性原理
- **物理/数学约束**：业务需求多样，需可扩展。
- **推导**：基于 SPI 的插件体系，支持自定义限流算法、数据源、规则解析等。

### 7.2 解决手段与代价
| 手段 | 原理 | 收益 | 代价 |
| :--- | :--- | :--- | :--- |
| `Slot` 链 | 责任链扩展 | 灵活 | 需理解顺序 |
| `Metric` 扩展 | 自定义指标统计 | 适配特殊场景 | 侵入 |
| `Datasource` 扩展 | 自定义配置源 | 对接现有配置中心 | 实现复杂度 |

### 7.3 通用实现案例
- **自定义 Slot**：实现 `ProcessorSlot`，SPI 配置。

### 7.4 生产问题与解决
- **SPI 未加载**：检查 `META-INF/services` 文件。
- **Slot 顺序错误**：注册顺序影响执行逻辑 → 通过 SPI 排序。
- **性能损耗**：自定义 Slot 避免复杂计算。

### 7.5 边界条件与风险
- **极值风险**：过多 Slot 影响性能。
- **版本升级不兼容**：留意 API 变更。

### 7.6 参数调优与验证
| 参数 | 核心作用 | 配置原则 | 动态生效 | 验证方法 |
| :--- | :--- | :--- | :--- | :--- |
| `spi` 文件 | 扩展点声明 | 按规范 | 需重启 | 日志确认加载 |

### 7.7 已知反模式检查
- **反模式**：修改 Sentinel 核心代码 → 升级困难。
- **规避**：通过 SPI 扩展，不修改核心。

- **关联域**：无。
- **预期检查项**：C1,C3,C4,C15。

## 全局权衡矩阵

| 冲突维度 | 涉及原则 | 权衡分析与架构建议 |
| :--- | :--- | :--- |
| 精确统计 vs 性能 | 原则1 | 默认 2 格滑动窗口，高精度可调多格 |
| 熔断恢复 vs 误判 | 原则2 | 异常比例阈值不宜过低，半开探测单请求 |

| 集群流控一致性 vs 可用性 | 原则4 | Token Server 高可用，降级到本地限流 |
| 系统保护 vs 误杀 | 原则5 | 结合压测调优阈值 |
| 可观测 vs 性能开销 | 原则6 | 控制指标粒度，采样日志 |
| 扩展性 vs 复杂性 | 原则7 | 按需扩展，不滥用 SPI |
