## 2. 第一部分：编译原理基础与扫描器

### 2.1 Lua编译器源码的架构评价

Lua的C语言源码（PUC-RIO官方实现）是工业级健壮性与教学级可读性的典范：

| 阶段 | 核心源文件 | 主要职责 |
| :--- | :--- | :--- |
| 编译入口 | `lua.c`, `luac.c` | 提供`luaL_loadstring`等API |
| 词法分析 | `llex.c` | 字符流→Token流 |
| 语法分析 | `lparser.c` | **递归下降法**构建AST |
| 字节码生成 | `lcode.c` | AST→寄存器架构字节码 |
| 虚拟机执行 | `lvm.c` | 高效循环解释执行 |
| 运行时支持 | `lobject.h`, `lstate.h`, `ltable.c`, `lgc.c` | 值、状态、表、垃圾回收 |

### 2.2 递归下降解析的第一性原理

**核心公理**：
- 源代码是线性序列（字符流→Token流）
- 语法语义是层次结构（嵌套）
- 文法的定义是递归的（`表达式 = 表达式 + 表达式`）

**逻辑推导链条**：
- 因为文法是递归的 → 解析算法必须具有递归性质
- 因为函数调用自带返回地址 → 直接用C函数调用栈匹配嵌套结构
- 因为Lua语法设计是LL(1) → 只看当前Token即可决策，无需回溯

**本质**：递归下降法是**利用编程语言的运行时机制（函数调用栈）去映射目标语言（Lua）的语法树结构**。

### 2.3 解释执行的两种模型

| 维度 | 类型一：基线解释器 | 类型二：JIT编译执行 |
| :--- | :--- | :--- |
| 工作机制 | 顺序遍历AST/字节码，立即执行 | 记录执行信息（热点），优化编译 |
| 遇到函数调用 | 压栈/弹栈，无记忆 | 可能内联展开，有类型反馈 |
| 特征 | 无预热，无记忆 | 有预热，有自适应优化 |
| 代表 | Python CPython, Lua 5.1, jlox | Java HotSpot, V8, LuaJIT |

### 2.4 扫描器（Scanning）的第一性原理

**三大公理**：
1. 计算机只能逐字符线性读取源代码
2. 编程语言由有意义的语义单元（Token）构成
3. 同一字符在不同上下文中可能代表不同含义

**五条推论**：
1. 扫描器必须循环遍历每个字符，在恰当边界切分Token
2. 扫描器必须能往前看（Lookahead）判断当前字符属于哪种Token
3. 扫描逻辑按Token类型分支：单字符直接匹配，多字符需要试探性消费
4. 每识别完一个Token，存入Token列表供后续使用
5. 遇到空格/注释跳过，遇到非法字符报告错误但继续扫描

**最长匹配原则（Maximal Munch）**：能匹配更长的lexeme就优先匹配更长的。

### 2.5 关键概念澄清：词法非正则

Python（缩进管理）和Haskell（嵌套注释、布局规则）的词法**不是正则的**：

- 正则文法（3型）无法处理`a^n b^n`这种需要计数的结构
- 它们需要**下推自动机**（带栈），属于上下文无关文法（2型）
- 工程上必须**手写词法分析器**，不能用`Lex/Flex`生成器

### 2.6 扫描器的职责边界

**扫描器做**：模式识别、Token切分、行号记录、基于字符类别的贪婪循环

**扫描器不做**：语义理解、类型判断、数学变换、统计次数、后续解析凭证

**修正后的三要点**：
1. 纯字符流读取：循环遍历，丢弃空格/注释，记录行号
2. 贪婪分类匹配：基于首字符类型进入对应子程序，吃尽连续同类字符
3. 无状态输出列表：生成Token对象，追加到列表，扫描完即失忆

## 3. 第二部分：语法树、访问者模式与表达式问题

### 3.1 抽象语法树（AST）vs 解析树（Parse Tree）

- **解析树**：完整保留所有文法细节（包括括号、优先级辅助符号）
- **AST**：只保留结构本质，丢弃冗余信息

**Lox选择AST**：`1 + (2 * 3)` 和 `1 + 2 * 3` 生成同样的AST（`Binary(1, Binary(2, 3))`），括号信息被结构隐含。

### 3.2 Representing Code的核心推论

1. 语法递归嵌套 → 必须用**树形结构**表示
2. 节点类型对应文法产生式（Literal, Unary, Binary, Grouping）
3. 操作会持续增长 → 需要解耦操作与数据结构
4. 解耦工具：**访问者模式（Visitor Pattern）**
5. 避免手写样板代码 → 使用**元编程/代码生成**

### 3.3 访问者模式的代价分析

**新增节点类（横向扩展）的代价**：
- 必须修改Visitor接口，添加新方法
- 所有现有Visitor实现类全部编译报错
- 必须逐个实现新方法

**新增操作（纵向扩展）的代价**：
- 只需新建一个Visitor实现类
- 完全不用碰已有节点类和已有操作

**结论**：访问者模式把“低频痛苦”（新增语法类）与“高频舒适”（新增操作）进行了对调。这是**表达式问题（Expression Problem）**的工程化取舍。

### 3.4 表达式问题（Expression Problem）详解

**定义**（Philip Wadler, 1998）：
> 我们希望使用一种类型系统，使得：
> 1. 新增数据类型（行扩展）时，无需修改现有操作代码
> 2. 新增操作（列扩展）时，无需修改现有数据类型代码
> 3. 同时编译器能保持类型安全

**三种范式对比**：

| 需求 | 标准OOP（虚方法） | 访问者模式（Visitor） | 模式匹配（ADT+Switch） |
| :--- | :--- | :--- | :--- |
| 新增数据类型（行） | ✅ 极简 | ❌ 灾难 | ⚠️ 中等 |
| 新增操作（列） | ❌ 灾难 | ✅ 极简 | ✅ 极简 |
| 编译期安全性 | ✅ 强 | ✅ 强 | ✅ 强 |
| 代码耦合度 | 高 | 高 | 低 |

**关键洞察**：表达式问题**没有完美解**，只有**代价转移**。

### 3.5 表达式（Expr）与语句（Stmt）的分离

| 维度 | 表达式（Expression） | 语句（Statement） |
| :--- | :--- | :--- |
| 核心使命 | 求值（产生值） | 执行（产生副作用） |
| 能否嵌套 | 可以无限嵌套 | 不能作为值嵌套在表达式里 |
| 是否必须产生值 | 是 | 否（void） |
| 返回类型 | Object（有值） | Void（无值） |

**`break`的归属**：`break`没有返回值，且不能出现在需要值的上下文中，因此属于`Stmt`而非`Expr`。

**表达式语句（Expression Statement）**：把表达式装进语句的壳里，使其能独立成行（如`1 + 2;`）。

### 3.6 `return` 的穿透实现

Lox使用**Java异常机制**实现`return`的非局部控制流转移：
```java
class Return extends RuntimeException {
    final Object value;
    Return(Object value) { this.value = value; }
}
```
顶层调用用`try-catch`包裹，捕获异常取出返回值。

## 4. 第三部分：表达式文法与上下文无关文法

### 4.1 Lox表达式文法

```
expression  → literal
            | unary
            | binary
            | grouping ;

literal     → NUMBER | STRING | "true" | "false" | "nil" ;
grouping    → "(" expression ")" ;
unary       → ( "-" | "!" ) expression ;
binary      → expression operator expression ;
operator    → "==" | "!=" | "<" | "<=" | ">" | ">="
            | "+"  | "-"  | "*" | "/" ;
```

### 4.2 文法到AST的映射

每条产生式对应一个Java类：

| 文法规则 | 对应的AST类 | 字段 |
| :--- | :--- | :--- |
| `literal → NUMBER \| STRING \| ...` | `Literal` | `Object value` |
| `unary → operator expression` | `Unary` | `Token operator; Expr right` |
| `binary → expression operator expression` | `Binary` | `Expr left; Token operator; Expr right` |
| `grouping → "(" expression ")"` | `Grouping` | `Expr expression` |

### 4.3 上下文无关文法（CFG）的第一性原理

**定义**：每个产生式的左边是一个**单独的非终结符**，推导规则**不依赖邻居符号**。

**正则文法的致命缺陷**：无记忆，不能处理`(`和`)`的配对、不能处理嵌套。

**CFG的能力**：
- 递归表达：`Expr → Expr + Expr`允许无限嵌套
- 匹配配对：天生支持括号、花括号的配对逻辑
- 解析确定性：可通过优先级和结合性消除歧义

### 4.4 为什么解析一定终止？

**数学证明**：解析器每一步操作要么消耗一个Token，要么结束当前层级的递归。

- 递归下降：每次调用要么匹配Token，要么调用子规则解析更小的部分
- 因为总Token数`N`有限，函数调用栈深度被`N`限制
- 执行步骤数严格正比于Token数量（O(N)）

**关键防火墙**：
- **解析（Parser）** = 线性读取器，基于有限输入长度，保证终止
- **运行（Interpreter）** = 交互式状态机，基于可变的堆内存状态，可能无限循环

### 4.5 图灵完备性的三个必要条件

1. **顺序执行**：能逐条推进指令
2. **分支（条件选择）**：能根据条件跳转（`if`）
3. **循环或递归**：能反复执行（`while`或函数调用）
4. **状态存储与修改**：能记住中间结果（`var`赋值）

（注：第4点在原始图灵机定义中对应“纸带+写入”，是隐含前提）

## 5. 第四部分：语法分析与解析器设计

### 5.1 运算符优先级与结合性的处理

**文法的二义性**：`1 + 2 * 3`可以解析为`(1+2)*3`或`1+(2*3)`。

**解决方案**：**分层文法 + Pratt解析（优先级攀升）**
- 将`binary`拆分为多层（`addition`、`multiplication`、`comparison`）
- 每个层级对应一个优先级
- 解析器通过传入`minPrecedence`参数控制递归深度

### 5.2 Pratt解析核心逻辑

```java
private Expr parseExpression(int minPrecedence) {
    Expr left = parsePrefix();  // 解析基础表达式（数字、括号等）
    while (true) {
        Token op = peek();
        int precedence = getPrecedence(op);
        if (precedence < minPrecedence) break;
        consume(op);
        Expr right = parseExpression(precedence + 1);
        left = new Binary(left, op, right);
    }
    return left;
}
```

**原理**：
- 每个运算符有优先级数值
- 解析右侧表达式时传入`precedence + 1`，确保只有更高优先级的运算符才能被纳入右侧
- 同一优先级通过循环处理左结合

### 5.3 左递归问题的消除

原始文法：`expression → expression + term`（左递归，会导致无限递归）

**解决方案**：改写为右递归或使用Pratt解析的循环结构

```java
// Pratt方式：用while循环替代左递归
while (nextOperatorHasHigherPrecedence(minPrecedence)) {
    // 吃运算符，递归解析右侧
}
```

## 6. 第五部分：环境、作用域与闭包

### 6.1 环境（Environment）的三个公理

1. 变量名是地址，环境是“电话簿”（Key→Value映射）
2. 作用域是嵌套的上下文（内部可见外部，反之不然）
3. 声明（`var`）与赋值（`=`）是两种截然不同的行为

### 6.2 环境链的实现

```java
class Environment {
    private final Map<String, Object> values = new HashMap<>();
    final Environment enclosing;  // 指向父作用域的链
    
    void define(String name, Object value) {
        values.put(name, value);  // 仅当前环境插入
    }
    
    Object get(Token name) {
        if (values.containsKey(name.lexeme)) return values.get(name.lexeme);
        if (enclosing != null) return enclosing.get(name);
        throw new RuntimeError("Undefined variable");
    }
    
    void assign(Token name, Object value) {
        if (values.containsKey(name.lexeme)) {
            values.put(name.lexeme, value); return;
        }
        if (enclosing != null) { enclosing.assign(name, value); return; }
        throw new RuntimeError("Undefined variable");
    }
}
```

### 6.3 块级作用域的实现

```java
@Override
public Void visitBlockStmt(Stmt.Block stmt) {
    Environment previous = this.environment;
    this.environment = new Environment(previous);  // 创建子环境
    try {
        for (Stmt s : stmt.statements) execute(s);
    } finally {
        this.environment = previous;  // 恢复父环境
    }
    return null;
}
```

### 6.4 闭包的底层机制——Upvalue

**闭包（Closure）** = 函数 + 捕获的自由变量环境

**自由变量（Free Variable）**：
- 在函数体内被引用
- 不在该函数的参数列表中声明
- 不在函数体内的任何局部声明语句中声明

**捕获（Capturing）**：
- 当闭包创建时，被引用的外部变量从栈转移到堆（Upvalue）
- 多个闭包可共享同一个Upvalue
- 捕获的是**存储地址**，而不是值

**Lua的Upvalue机制**：
- **开放（Open）**：变量还在栈上，Upvalue指针直接指向栈位置
- **闭合（Closed）**：外函数执行完毕，将变量拷贝到堆，更新指针

### 6.5 闭包中的变量修改语义

**关键区分**：

| 操作 | 底层含义 | 闭包内是否变化 |
| :--- | :--- | :--- |
| `x = new_object`（重新赋值） | 改变变量指向的地址 | ❌ 不变（闭包仍指旧地址） |
| `x.field = new_value`（修改内部） | 改变对象内部属性 | ✅ 变化（地址未变） |
| 外部`return x`（值类型） | 复制值 | ❌ 与闭包无关 |
| 外部`return x`（引用类型） | 复制引用（钥匙） | ✅ 闭包和外部指向同一对象 |

**核心原理**：闭包捕获的是**变量盒子（地址）**，不是值。外部同名变量和闭包Upvalue是**不同的物理存储位置**，除非显式通过setter修改。

### 6.6 变量解析的优化方向

- **AST解释器阶段**：沿环境链线性查找（O(深度)），教学清晰但效率低
- **工业级实现**：在编译/解析阶段计算**栈槽位索引（Slot Index）**，运行时O(1)访问

## 7. 第六部分：计算理论基础——图灵机、λ演算与停机问题

### 7.1 图灵停机问题

**问题定义**：是否存在通用算法`H(P, I)`，能在有限时间内判断程序`P`在输入`I`上是否停机？

**答案**：不存在。

**归谬证明**（自指悖论）：
1. 假设存在`H(P, I)`返回`true`（停机）或`false`（不停机）
2. 构造捣蛋程序`D(X)`：若`H(X, X)`返回`true`，则`D`执行死循环；否则立即返回
3. 问：`D(D)`会怎样？
   - 若`H(D, D)`=true → D死循环 → H判错
   - 若`H(D, D)`=false → D立即返回 → H判错
4. 矛盾 → `H`不存在

**对编译器的启示**：
- 静态分析的极限：不可能完美预测程序运行时行为
- 死代码消除、循环展开等优化必须保守处理
- 停机问题的不可判定性定义了**可计算性的终极边界**

### 7.2 λ演算（Lambda Calculus）

**阿隆佐·邱奇（Alonzo Church）** 提出，1930年代。

**三条核心规则**：
1. 变量：`x`, `y`
2. 函数抽象：`λx.M`（接受参数`x`，返回表达式`M`）
3. 函数应用：`(M N)`（把函数`M`应用到参数`N`）

**β-归约（Beta-reduction）**：`(λx.M) N → M[x := N]`（把`M`中的`x`替换为`N`）

**与图灵机的关系**：
- 图灵机 = 物理机器视角（读写头、纸带、状态）
- λ演算 = 纯数学替换视角（函数抽象、参数代入）
- **邱奇-图灵论题**：两者表达能力等价

### 7.3 邱奇编码（Church Encoding）

λ演算中没有数字、布尔值、循环，只有函数。邱奇用函数表示一切：

**邱奇数**：
- `0 = λf.λx.x`（应用0次）
- `1 = λf.λx.f x`（应用1次）
- `2 = λf.λx.f (f x)`（应用2次）

**邱奇布尔值**：
- `true = λx.λy.x`（返回第一个参数）
- `false = λx.λy.y`（返回第二个参数）

**if-else的演化**：`if condition then A else B ≡ condition(A)(B)`
- `true(A)(B) → A`
- `false(A)(B) → B`

**逻辑运算**：
- `and = λa.λb. a b false`
- `or = λa.λb. a true b`

### 7.4 柯里-霍华德同构（Curry-Howard Isomorphism）

**发展历程**：
- 1934年（萌芽）：柯里观察到组合子类型对应逻辑公理
- 1958年（雏形）：柯里明确类型化组合子逻辑与演绎系统的对应
- 1969年（确立）：霍华德发现自然演绎证明与λ演算程序的对应

**核心对应**：
- 程序 = 证明
- 类型 = 逻辑命题
- β-归约 = 逻辑化简/证明规约

## 8. 第七部分：数字逻辑与硬件计算原理

### 8.1 布尔代数的完备性定理

**任意布尔函数都可以写成“最小项之和”的标准形式**

**最小项（Minterm）**：锁定唯一输入组合的“与”表达式
- 输入`(1,0)` → 最小项为`x · \bar{y}`

**推导过程**：
1. 列出真值表中所有输出为1的行
2. 每行构造对应的最小项
3. 用“或”连接所有最小项

**结论**：任何复杂的逻辑计算，在数学上都可以通过“与、或、非”三种门实现。

### 8.2 NAND门的完备性

**与非门（NAND）**单种门即可构成完备集：

- `NOT(A) = A NAND A`
- `AND(A,B) = (A NAND B) NAND (A NAND B)`
- `OR(A,B) = (A NAND A) NAND (B NAND B)`

**半导体意义**：NAND门在硅片上只需4个晶体管，是最基本的物理实现单元。

### 8.3 加法器的硬件实现

**半加器（Half Adder）**：
- `Sum = A XOR B`
- `Carry = A AND B`

**全加器（Full Adder）**：半加器 + 半加器 + 或门

**乘法器**：
- 移位 + 加法并行（华莱士树）
- 或循环累加（慢但简单）

**除法器**：
- 恢复余数法/不恢复余数法（SRT算法）
- 本质：减法试探 + 移位并行

### 8.4 分支即计算（算术化）

**三元运算的布尔代数表达**：
```
Result = (A & Mask) | (B & ~Mask)
```
其中`Mask`是条件生成的位掩码（全0或全1）。

**CPU指令支持**：
- ARM: `CSEL Xd, Xn, Xm, cond`
- x86: `CMOVcc reg, reg/mem`
- RISC-V: `czero.eqz`, `BPICK`

**好处**：避免分支预测失败（Branch Misprediction）的性能惩罚。

### 8.5 CPU中的计算单元

| 单元 | 职责 | 特点 |
| :--- | :--- | :--- |
| ALU（算术逻辑单元） | 整数运算、逻辑运算 | 简单指令1周期完成 |
| FPU（浮点运算单元） | 浮点数加减乘除、平方根 | 支持FMA（融合乘加） |
| SFU（专用功能单元） | 三角函数、指数、对数 | 硬件加速，精度可能略低 |
| LD/ST（加载存储单元） | 搬运数据 | 包含AGU（地址生成单元） |
| AGU（地址生成单元） | 计算内存访问地址 | 支持基地址+偏移量 |

### 8.6 从1+1到电压变化的完整链条

```
Lox代码: 1 + 1;
    ↓
AST: Binary(Literal(1), Plus, Literal(1))
    ↓
字节码/机器码: ADD R1, R2
    ↓
二进制: 0001 + 0001
    ↓
半加器逻辑:
    Carry = 1 AND 1 = 1
    Sum = (1 OR 1) AND NOT(1 AND 1) = 0
    ↓
物理硅片: 电子流过NAND门网络
    ↓
输出: 0010 (十进制2)
```

## 9. 第八部分：数学计算的精确性与计算机极限

### 9.1 数值的精确性分类

| 数类 | 能否在有限硬件中精确表示 | 例子 |
| :--- | :--- | :--- |
| 整数 | ✅ 完全精确 | 1, 2, 3 |
| 有理数（有限小数） | ✅ 完全精确 | 0.5, 0.125 |
| 有理数（无限循环） | ❌ 只能近似 | 1/3 = 0.333... |
| 代数数（如√2） | ❌ 只能近似 | 无理数，无限不循环 |
| 超越数（π, e） | ❌ 只能近似 | 无限不循环，无代数闭式 |

### 9.2 精确计算CPU的理论可行性

**有理数精确计算**：✅ 完全可行
- 存储：分子+分母（分数存储法）
- 需要：超大整数乘法器 + GCD加速器（欧几里得算法流水线）
- 代价：极慢，数百至数千时钟周期

**代数数精确计算**：⚠️ 理论上可行，硬件极复杂
- 存储：最小多项式（符号表达式）
- 需要：模式匹配单元 + 多项式因数分解单元
- 本质上：计算机代数系统（CAS）的硬件加速版

**超越数精确计算**：❌ 物理上不可能
- π的信息量是无限的（无限不循环数字串）
- 有限物理世界（有限原子）无法存储无限信息

### 9.3 超越函数的计算方法

**泰勒级数**（无线项展开）：
```
e^x = 1 + x + x²/2! + x³/3! + ...
sin(x) = x - x³/3! + x⁵/5! - ...
```

**关键洞察**：只要项数有限，结果就是近似值。绝对精确需要无限多项，在现实世界中永远做不完。

### 9.4 数学中无法转换为四则运算的问题

**A. 存在性问题**（无法构造）：
- `π + e`是否是有理数？
- 哥德巴赫猜想的判定
- 这类问题需要逻辑推理，无法通过建立有限次四则运算求解

**B. 不可判定问题**（图灵机极限）：
- 希尔伯特第十问题（判断整数多项式方程是否有整数解）
- 1970年证明：**不存在**有限算法回答“有解/无解”

### 9.5 第一性原理边界

**有限vs无限的冲突**：
- 计算机：有限状态、有限存储、有限步骤
- 数学：包含无限集合、无穷级数、无限循环
- 计算机永远是对数学的**有限逼近**，而非绝对精确实现

## 10. 第九部分：非冯·诺依曼架构与未来计算

### 10.1 量子计算机

**优势**：
- Shor算法：大整数质因数分解指数级加速
- Grover算法：数据库搜索平方根加速
- 量子模拟：高效模拟分子和材料

**精确性分析**：
- 代数数：可以精确表示（量子态振幅）
- 超越数：**无法精确表示**（振幅本质是复数，天生含无理数）
- 输出：概率性的，需要多次测量，带统计误差

### 10.2 神经形态计算

**核心思想**：“固化数学理论”
- 数学运算是通过**物理系统的固有响应**完成的（电流流过特定电路产生自然结果）
- 计算本质是**物理场的演化**，而非逻辑门的离散操作

**输出机制**：
1. 脉冲时空模式（Spike Pattern）作为标识（Token/Label）
2. 模数转换器（ADC）将模拟量转为数字
3. 数字后端校准器输出近似值

**精度特征**：
- 相对精确（受物理噪声、温度漂移影响）
- 精度受ADC分辨率限制

### 10.3 存算一体（Compute-in-Memory）

- 计算逻辑嵌入存储单元
- 数字式：精度无损
- 模拟式：精度受限，但能效高

### 10.4 光子计算机/光学计算

- 用光子代替电子
- 适合解偏微分方程等特定问题
- 精度目前约90%，不及传统计算机

### 10.5 计算架构的演进图谱

```
通用CPU (冯·诺依曼)
    ├── 追求确定性，灵活
    ├── 串行/有限并行
    └── 精确(离散)计算

GPU/TPU/NPU (专用加速)
    ├── 追求吞吐量
    ├── 大规模并行
    └── 单精度/半精度为主

神经形态/模拟计算
    ├── 追求能效比
    ├── 物理场直接映射
    └── 相对精确(物理逼近)

量子计算
    ├── 追求特定问题加速
    ├── 量子态叠加/纠缠
    └── 概率性输出
```

## 11. 终章：宇宙、信息与计算的本体论

### 11.1 邱奇-图灵论题的扩展视角

**“程序不过是一堆数据，区别在于怎么去解析”**

- 程序的结构：有限的原子（变量、抽象、应用）
- 解析动作：字符流→结构化数据（AST）
- 执行本质：按照固定规则（β-归约）将一种结构化数据重写为另一种

**有限结构产生无限可能**：
- 周期结构：`while(true)`（有限状态循环）
- 非周期无限：Y组合子、康威生命游戏（简单规则产生永不重复的模式）

### 11.2 计算机的“第一推动力”

| 层面 | 计算机 | 宇宙 |
| :--- | :--- | :--- |
| 初始条件 | 开机地址（BIOS/UEFI硬连线） | 大爆炸初始奇点 |
| 演化规则 | 时钟驱动 + 逻辑门延迟 | 薛定谔方程 + 广义相对论 |
| 信息编码 | 二进制（电压高低） | 质量/电荷/自旋 |
| 结构 | AST + 环境链 + 硬件状态机 | 费米子 + 玻色子 + 时空流形 |

### 11.3 “It from Bit”（万物源于比特）

**John Wheeler（惠勒）的洞见**：
- 宇宙最底层可能不是物质和能量，而是**信息**
- 物理定律 = 解析器，宇宙状态 = 数据流
- 粒子、场、时空都是信息的表象

### 11.4 计算的终极边界

**物理世界=近似计算的巨型模拟器**：

1. 有理数是唯一能在物理世界中完全精确表示的数
2. 代数数（如√2）理论上可精确，但代价巨大
3. 超越数（如π）无法在有限物理资源中精确表示
4. 因此：**任何基于有限物理资源的计算机，本质上都是近似计算器**

### 11.5 计算机 vs 宇宙的非对称性

**核心差异**：
- 计算机有“外部使用者”（按开机键）
- 宇宙（若封闭）没有外部环境
- 宇宙的“第一推动力”在逻辑上比计算机的开机键更神秘

**共同点**：
- 有限规则产生无限演化
- 信息是底层实在
- 计算是物理过程的数学投影
