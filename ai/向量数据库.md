
## 一、pgvector HNSW 索引参数调优

### 1. 三大核心参数

| 参数 | 类型 | 默认值 | 建议范围 | 主要影响 |
|------|------|--------|----------|----------|
| **`m`** | 构建时 | 16 | 8–64 | 图连通度：越大内存占用和构建时间越高，但图越稠密，搜索路径越多 |
| **`ef_construction`** | 构建时 | 64 | 64–512 | 构建质量：值越大构建越慢，索引质量越高，后续查询召回率越好，必须 ≥ 2×`m` |
| **`ef_search`** | 运行时 | 40 | 40–500 | 查询动态候选列表大小：**零成本调优首选**，直接影响每次查询的延迟与召回率 |

### 2. 分场景调优建议

- **通用 RAG（检索增强生成）**  
  使用默认 `m=16, ef_construction=64`，查询时稍增大 `ef_search`（如 100）。
  ```sql
  CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
  SET hnsw.ef_search = 100;
  ```

- **高精度场景（风控、医疗）**  
  提高 `m` 到 32，`ef_construction` 到 256，配合较高 `ef_search`（如 400）。
  ```sql
  CREATE INDEX ... WITH (m = 32, ef_construction = 256);
  SET hnsw.ef_search = 400;
  ```

- **高吞吐低延迟场景（热点推荐）**  
  适当降低 `m`（如 12），使用较小的 `ef_search`（如 80），牺牲少量精度换取极高 QPS。
  ```sql
  CREATE INDEX ... WITH (m = 12, ef_construction = 100);
  SET hnsw.ef_search = 80;
  ```

### 3. `ef_search` 的三种设置方式
- **会话级**：`SET hnsw.ef_search = 200;`
- **事务级**：`SET LOCAL hnsw.ef_search = 400;`（仅在事务内生效）
- **全局持久化**（需超级用户）：
  ```sql
  ALTER SYSTEM SET hnsw.ef_search = 120;
  SELECT pg_reload_conf();
  ```

### 4. 构建环境优化
- 为索引构建预留大内存：`SET maintenance_work_mem = '2GB';`
- 确保服务器物理内存能完全容纳 HNSW 索引（例如 1536 维、100 万条数据约需 6 GB）
- 强烈建议升级至 pgvector 0.6+ 以获得更快的构建速度

### 5. 调优流程
1. 从默认值开始（`m=16, ef_construction=64, ef_search=40`）
2. 若召回率不足，**优先调大 `ef_search`**（无需重建索引）
3. 若延迟无法接受或精度仍不达标，才重建索引，小幅提高 `m` 和 `ef_construction`
4. 重建后再次调优 `ef_search`，找到新平衡点

### 6. 监控召回率
通过比对近似搜索与精确搜索（暴力扫描）的结果计算召回率：
```sql
-- 精确搜索基准
SELECT id FROM items ORDER BY embedding <=> query_embedding LIMIT 10;
-- 近似搜索
SET hnsw.ef_search = 100;
SELECT id FROM items ORDER BY embedding <=> query_embedding LIMIT 10;
-- 计算：重叠数量 / 10
```
通常 **99% 召回率** 为生产可接受水平。

## 二、pgvector 常见查询模式

以下查询均以 `embedding` 列为 `vector(1536)` 为例，并假定存在对应距离操作符的索引。

### 1. 精确 / 近似最近邻搜索（KNN / ANN）
```sql
SELECT id, content
FROM items
ORDER BY embedding <-> '[0.1,0.2,...]'   -- L2 距离
LIMIT 10;
```
- 距离操作符：`<->` L2, `<#>` 负内积, `<=>` 余弦距离
- 若有 HNSW 索引，查询前记得设置 `ef_search`

### 2. 范围搜索（距离过滤）
```sql
SELECT id, content, embedding <-> query_embedding AS distance
FROM items
WHERE embedding <-> query_embedding < 0.8;
```

### 3. 混合过滤（向量 + 结构化条件）
```sql
SELECT id, content
FROM items
WHERE category = '科技' AND publish_date > '2024-01-01'
ORDER BY embedding <=> query_embedding
LIMIT 5;
```
- 若过滤条件选择性高，可配合 B-Tree 索引或部分索引优化性能。

### 4. 纯距离计算
```sql
SELECT a.id, b.id, a.embedding <=> b.embedding AS cosine_distance
FROM items a, items b
WHERE a.id = 1 AND b.id = 2;
```

### 5. 自连接查找相似对（聚类/去重分析）
```sql
SELECT a.id, b.id, a.embedding <=> b.embedding AS dist
FROM items a
JOIN items b ON a.id < b.id
WHERE a.embedding <=> b.embedding < 0.2
ORDER BY dist;
```
- 计算量极大，仅适合离线分析或小数据量。

### 6. 分组/聚合 Top‑K（每个组取最相似的前 K 条）

**方法一：窗口函数**
```sql
SELECT id, category, content, dist
FROM (
  SELECT *,
         embedding <=> query_embedding AS dist,
         ROW_NUMBER() OVER (PARTITION BY category ORDER BY embedding <=> query_embedding) AS rn
  FROM items
) sub
WHERE rn <= 3;
```

**方法二：LATERAL 子查询（通常能更好利用索引）**
```sql
SELECT cats.category, top_n.id, top_n.dist
FROM (SELECT DISTINCT category FROM items) cats
LEFT JOIN LATERAL (
  SELECT id, embedding <=> query_embedding AS dist
  FROM items
  WHERE category = cats.category
  ORDER BY dist
  LIMIT 3
) top_n ON true;
```

### 7. 多向量批量查询（一次 SQL 为多个查询向量返回 Top‑K）
```sql
SELECT q.query_id, i.id, i.content
FROM queries q
CROSS JOIN LATERAL (
  SELECT id, content
  FROM items
  ORDER BY embedding <=> q.query_embedding
  LIMIT 5
) i;
```
- `queries` 表存储多个查询向量，每个向量独立搜索 Top‑K，显著减少网络往返。

## 三、分组 Top‑K 中具体向量值的含义 ≠ 自动聚类

我们澄清了一个常见误区：  
`embedding <=> '[0.1,0.2,...]'` 中的向量是**外部传入的查询向量**（如用户搜索词 embedding），而不是从数据内部自动生成的聚类中心。

“自动聚类”是**无监督**的，pgvector 未内置 K‑Means 等算法。若需要自动聚类，可采用：
1. **应用层聚类**：用 Python sklearn 等计算聚类中心，再用 SQL 取每簇 Top‑K 成员。
2. **自连接发现相似群落**（适合小数据量）：通过 `WHERE a.embedding <=> b.embedding < 阈值` 找到相似记录对。
3. **数据库内扩展**：如 `pg_similarity` 或 PL/Python 自定义函数，但实施成本高。

## 四、普通数据中用 LEFT JOIN 实现分组 Top‑K（不使用窗口函数）

以“每个科目分数最高的前 3 名学生”为例，展示了经典的**自连接 + 计数**技巧：

```sql
SELECT s1.subject, s1.student_name, s1.score
FROM scores s1
LEFT JOIN scores s2
  ON s1.subject = s2.subject
  AND s1.score < s2.score          -- 找出同科目比 s1 分数高的所有记录
GROUP BY s1.id, s1.subject, s1.student_name, s1.score
HAVING COUNT(s2.id) < 3            -- 比自己高的人数 < 3 即为前 3
ORDER BY s1.subject, s1.score DESC;
```

**原理**：通过自连接统计“比自己高的行数”，若小于 K 则入选。  
- 优点：兼容所有 SQL 数据库（无需窗口函数）。  
- 缺点：大表时性能差，且对并列分数的处理可能超出 K 值（视需求选择 `ROW_NUMBER` 还是 `RANK` 语义）。  
- **现代 PostgreSQL 推荐直接使用窗口函数**。

## 五、LATERAL 关键字全面解析

### 1. 功能本质
`LATERAL` 允许子查询引用其**左边（前面）表的列**，并且子查询会**为左表的每一行执行一次**，实现“参数化子查询”。

### 2. 向量批量查询中的应用
```sql
CROSS JOIN LATERAL (
  SELECT ... FROM items ORDER BY embedding <=> q.query_embedding LIMIT 5
) i
```
- 遍历 `queries` 表每一行（每个查询向量）
- 以当前行的 `query_embedding` 作为输入，在 `items` 表中进行相似度排序
- 返回该查询向量的前 5 条结果，与当前 `query_id` 组合输出

### 3. 为什么必须用 LATERAL？
标准 SQL 中，`FROM` 子句的子查询默认**不能引用同级其他表的列**。`LATERAL` 打破此限制，使其合法。

### 4. 与其他数据库的兼容性
- **PostgreSQL**：`LATERAL` 关键字（9.3+）
- **MySQL**：`LATERAL` 关键字（8.0.14+），语法与 PG 一致
- **Oracle**：`LATERAL` (12c+)，也支持 `CROSS APPLY` / `OUTER APPLY`
- **SQL Server**：无 `LATERAL` 关键字，但 `CROSS APPLY` / `OUTER APPLY` 功能等价
- **SQLite**：不支持
- **DB2**：支持 `LATERAL`

### 5. 在普通数据查询中的优势（例：每部门薪资 Top‑3）
```sql
SELECT d.dept, top3.name, top3.salary
FROM (SELECT DISTINCT dept FROM employees) d
CROSS JOIN LATERAL (
  SELECT name, salary
  FROM employees e
  WHERE e.dept = d.dept
  ORDER BY e.salary DESC
  LIMIT 3
) top3;
```
利用 `(dept, salary)` 索引可避免全表扫描，性能常优于窗口函数（视数据分布而定）。

### 6. CROSS JOIN LATERAL vs LEFT JOIN LATERAL
- `CROSS JOIN LATERAL (...)`：若子查询返回 0 行，则左表该行被丢弃（笛卡尔积乘 0）。
- `LEFT JOIN LATERAL (...) ON true`：子查询返回 0 行时保留左表行，右表列填 NULL。  
向量搜索通常都有结果，故 `CROSS JOIN` 更简洁。

## 六、CROSS JOIN 与其他 JOIN 的区别（重点澄清 FULL JOIN 行数误区）

### 1. 各类 JOIN 对比

| JOIN 类型 | 是否需要 ON 条件 | 结果行数 | 说明 |
|-----------|------------------|----------|------|
| `CROSS JOIN` | **无** | **m × n** | 无条件笛卡尔积，用于组合或配合 LATERAL |
| `INNER JOIN` | 必须 | 0 ~ m×n | 只保留匹配行 |
| `LEFT JOIN` | 必须 | m ~ m×n | 保留左表全部行，右表无匹配填 NULL |
| `RIGHT JOIN` | 必须 | n ~ m×n | 保留右表全部行 |
| `FULL JOIN` | 必须 | **MAX(m,n) ~ m+n** | 保留两表全部行，无匹配填 NULL；**绝不会是 m×n** |

### 2. FULL JOIN 行数详解
- **最少**：当两表所有行都能一一匹配时，结果为 `MAX(m, n)`
- **最多**：当两表无任何匹配时，结果为 `m + n`（左表全行 + 右表全行，均为 NULL 补充）
- **永远不可能**达到 `m × n`，因为它不会产生笛卡尔积式的组合。

### 3. 示例
表 A（3 行），表 B（4 行）：
- `FULL JOIN ... ON A.id = B.id` 结果行数在 4 到 7 之间，不会到 12。
- `CROSS JOIN` 结果固定为 12 行。

> 这是对话中重点纠正的一个常见记忆混淆。

## 一、向量检索基础（入门）

### 1. 核心概念
- **向量嵌入**：通过模型将非结构化数据（文本、图片）映射为固定维度（64~8192）的稠密向量，空间距离表示语义相似度。
- **相似度度量**：
  - **余弦相似度**：衡量方向，归一化后等价于内积，适合文本。
  - **内积（IP）**：适合归一化向量，推荐系统常用。
  - **欧氏距离（L2）**：衡量绝对距离，适合图像、语音。
- **KNN vs ANN**：
  - KNN：暴力计算，100%召回，亿级数据延迟达秒级。
  - ANN：用索引牺牲微小召回换取指数级加速，主流场景可做到99%召回 + 毫秒级延迟。

### 2. pgvector 与 Milvus 设计哲学对比
| 维度 | pgvector | Milvus |
|------|----------|--------|
| 本质 | PostgreSQL扩展插件 | 专为向量打造的分布式数据库 |
| 数据规模 | ≤500万条 | 千万~百亿级 |
| 运维 | 极低 | 较高 |
| 适用场景 | 已有PG的中小项目 | 大规模高性能AI应用 |

## 二、核心索引算法（进阶）

### 1. Flat（暴力搜索）
- 100% 召回，适合 <10万 数据或性能基线。

### 2. IVF（倒排文件索引）
- **原理**：k-means 聚类将空间划分为 `nlist` 个簇，查询只搜 `nprobe` 个最近簇。
- **构建**：训练质心 → 建立倒排表 → 可选压缩（SQ8 / PQ）。
- **关键参数**：`nlist`（建议 ≈ √N），`nprobe`（查询时调节精度/延迟）。

### 3. HNSW（分层可导航小世界图）
- 多层图结构，查询从上层粗粒度图开始向下搜索，对数复杂度。
- **特点**：查询快，内存占用高，构建长，支持增量更新。
- **关键参数**：`M`（每层连接数，经验值 ≈ log₂(N)），`ef_construction`（构建候选集大小），`ef_search`（查询候选集）。

### 4. PQ（乘积量化）
- 将向量切分为子空间，每子空间用码本编码，实现极高压压缩（如128维float32 → 8字节）。
- 在 Milvus 中为 `IVF_PQ`，参数 `m`（子空间数）、`nbits`（每子空间编码位数）。

## 三、pgvector 详解（进阶 & 专家）

### 1. 实现方式
- 在 PG 内实现 `vector` 数据类型，通过索引接口集成 IVFFlat 和 HNSW。
- **限制**：无法多核并行扫描，无 GPU 加速。

### 2. 索引创建与调优
**IVFFlat**：
```sql
CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops) WITH (lists = 1000);
-- 查询时动态调整
SET ivfflat.probes = 10;
```

**HNSW**：
```sql
CREATE INDEX ON items USING hnsw (embedding vector_l2_ops) WITH (m = 16, ef_construction = 200);
-- 事务级动态调整
SET LOCAL hnsw.ef_search = 100;
```

**参数建议**：
- 百万级内优先用 HNSW，十亿级结合分区表（热数据 HNSW，冷数据 IVFFlat）。
- 过滤查询需创建过滤列索引 + 启用 `hnsw.iterative_scan = strict_order`。
- 归一化向量用内积 `<#>` 比 L2 快约 30%。
- 批量查询用 `unnest` 减少网络往返。

### 3. 存储与压缩
- **halfvec**：16位浮点，存储减半，索引构建更快。
- **pgvectorscale 扩展**：
  - **StreamingDiskANN**：磁盘图索引，突破内存限制，参数 `num_neighbors`、`search_list_size`、`query_rescore`。
  - **SBQ**：统计二值量化，每维 1 bit，配合 DiskANN 使用。

### 4. 版本演进
- pgvector 0.8：HNSW 构建提速 40%，支持 `halfvec` 和 RaBitQ（1-bit 压缩，32倍空间缩减）。

## 四、Milvus 详解（进阶 & 专家）

### 1. 建表（Collection）
```python
from pymilvus import MilvusClient, DataType
client = MilvusClient(uri="http://localhost:19530")
schema = client.create_schema(auto_id=False, enable_dynamic_field=True)
schema.add_field(field_name="id", datatype=DataType.INT64, is_primary=True)
schema.add_field(field_name="embedding", datatype=DataType.FLOAT_VECTOR, dim=128)
schema.add_field(field_name="title", datatype=DataType.VARCHAR, max_length=512)
client.create_collection(collection_name="my_books", schema=schema)
```

### 2. 索引
- 支持 10+ 种索引：`FLAT`、`IVF_FLAT`、`IVF_SQ8`、`IVF_PQ`、`HNSW`、`DiskANN`、`GPU_CAGRA` 等。
- 创建示例：
```python
index_params = client.prepare_index_params()
index_params.add_index(field_name="embedding", index_type="IVF_FLAT", 
                        metric_type="COSINE", params={"nlist": 128})
index_params.add_index(field_name="title", index_type="Trie")  # 标量索引
client.create_index("my_books", index_params)
client.load_collection("my_books")
```

### 3. 查询
```python
search_params = {"metric_type": "COSINE", "params": {"nprobe": 16}}
results = client.search(
    collection_name="my_books",
    data=[query_embedding],
    anns_field="embedding",
    param=search_params,
    limit=10,
    filter='title not like "%Old%"',
    output_fields=["title"]
)
```
- `nprobe` / `ef` 控制精度与延迟。
- 高级查询：混合搜索（多向量+重排序）、分组搜索。

### 4. 优化策略
- **分区（Partition）**：按业务维度划分，单集合分区不超过 1000 个。
- **分片（Shard）**：建议单分片数据量 1000万~1亿，大数据量时增加 `shards_num`。
- **批量插入**：每次 1000~5000 条。
- **索引选型**：
  - <10万：FLAT
  - 百万级：IVF_FLAT，`nlist ≈ √N`
  - 千万级：HNSW，`M ≈ log₂(N)`，`efConstruction` 影响构建质量
  - 亿级以上：DiskANN 或 IVF_PQ
- **冷热分层**：Milvus 2.6 可使数据集加载从 25 分钟降至 45 秒。

## 五、向量压缩编码：float32 → 8-bit（SQ8）

### 1. 原理
- 对每一维度统计全局 `min_j`、`max_j`。
- 编码公式：`code_j = round(255 * (x_j - min_j) / (max_j - min_j))`，存储为 `uint8`。
- 解码：`x_j ≈ min_j + code_j * (max_j - min_j) / 255`。
- 查询时采用非对称量化（查询向量保持 float32，数据库向量为 uint8），使用查找表或整数 SIMD 加速。

### 2. 手工实现（Python）
```python
class ScalarQuantizer8bit:
    def train(self, vectors): # 计算每维 min/max
    def encode(self, x):      # 映射至0~255 uint8
    def decode(self, codes):  # 还原近似浮点
```
压缩比 4:1（如 128维 512字节 → 128字节）。

### 3. 在 Milvus 中使用
直接指定索引类型 `IVF_SQ8`，内部自动训练、编码和近似距离计算。
```python
index_params.add_index(field_name="embedding", index_type="IVF_SQ8",
                        metric_type="L2", params={"nlist": 128})
```
适当增大 `nprobe` 补偿量化损失。

### 4. pgvector 等效方案
- `halfvec` (float16) ：2字节/维，存储减半，索引可用。
- 手工 SQ8 存储为 `bytea` 但无法利用向量索引。
- pgvectorscale 的 SBQ（1-bit）更极致。

### 5. 进一步压缩：乘积量化（PQ）
- `IVF_PQ` 参数：`m` (子空间数)，`nbits` (每子空间编码位数)。
- 典型配置 `m=16, nbits=8` 得到 16 字节/向量（128维），压缩比 32 倍。

  - SQ8：内存缩减75%，精度较高。
  - PQ：4~32倍压缩，适合内存受限场景。
  - RaBitQ/SBQ：1-bit 压缩，十亿级存储优化。

## 七、技术趋势总结
- **pgvector**：通过 StreamingDiskANN、RaBitQ、混合搜索向十亿级规模延伸。
- **Milvus**：强化 GPU-CPU 混合索引（GPU_CAGRA）、稀疏向量 BM25、JSON 过滤加速、实体级多向量检索，深耕百亿级性能。
- **共同方向**：融合标量与向量、全文与语义，降低运维复杂度，在 PostgreSQL 和专用库之间选择渐趋多元。
