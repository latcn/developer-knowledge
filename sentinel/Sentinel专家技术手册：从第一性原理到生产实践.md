## 1. 第一性原理：分布式系统稳定性的根基

我们从一个简单的事实出发：**软件运行在有限的硬件上，而请求的到达却不可预测。** 这就是一切问题的原点。

### 1.1 从“服务雪崩”到流量控制

设想一个服务A依赖服务B。B因为某些原因变慢了，导致A的线程池全被等待B的响应占满。A因此无法处理新请求，而调用A的上游C也开始堆积线程……就像多米诺骨牌一样，整个链路因为一个点的延迟而全线崩溃。这就是**服务雪崩**。

**第一性原理追问**：雪崩的根本原因是什么？  
—— 是“过载传播”：一个组件过载后，非但没有拒绝多余的请求，反而让这些请求继续消耗稀缺资源（线程、连接、内存），从而拖垮调用方。  
因此，**必须有一种机制，在过载发生时就阻断请求，保护自己和上游**。这就是**流量控制**（限流）的最根本动机。不是“为了限流而限流”，而是为了**避免系统进入它无法承受的状态**。

### 1.2 从“资源耗尽”到熔断降级

上面的场景中，B变慢了但还没死。如果B已经彻底不可用（例如持续抛出异常），A的每次调用都会立即失败。此时继续重试或调用，除了白白消耗A自身的资源（网络、CPU），没有任何意义。  

**第一性原理追问**：当依赖已经确认不可用时，最理性的做法是什么？  
—— 是“快速失败”，暂时不去调用它，把资源留给还能正常工作的逻辑。这就是**熔断**（断路器）。它不是“惩罚”依赖，而是“止损”。

### 1.3 直觉模型：水龙头—蓄水池—保险丝

- **流量控制**像给水龙头加一个**限流器**：不管你多大水流涌来，我这里每秒只通过固定水量。
- **排队等待**像在龙头下放一个**蓄水池**，让瞬时洪峰在池子里排队，以恒定速率流出。
- **熔断降级**像电路里的**保险丝**：一旦电流过大（错误太多），立即熔断切断电路，保护电器；过一段时间尝试恢复（半开），若仍有故障则再次熔断。

**一句话总结**：一切的防护措施，本质上都是在“资源有限、请求无限”的前提下，做出的**快速拒绝**或**优雅等待**的决策。

**自问自答**：  
问：“如果没有流量控制，高并发下会出现什么问题？”  
答：线程池饱和、响应变慢、超时重试加剧负载，最终整个服务不可用，并可能传播到上游。

## 2. 架构设计全景

Sentinel 不是单一的服务，而是由 **客户端（核心库）** 和 **控制台（Dashboard）** 组成的双核心体系。

### 2.1 客户端与控制台的职责边界

- **客户端 (sentinel-core)**：嵌入应用进程，负责所有流控、熔断、降级逻辑的实际执行。它直接拦截调用，采集指标，判断规则，极其轻量，不依赖外部服务也能独立工作。
- **控制台 (sentinel-dashboard)**：一个独立的Spring Boot应用，提供规则管理、监控查看、动态下发的能力。它不与客户端做“实时”强制交互，而是充当管理入口。

**第一性原理推导**：为什么不做成一个中心化的实时决策服务？  
因为如果每个请求都要调用远程服务决策，该服务本身就是单点和性能瓶颈，违背了高可用的初衷。Sentinel 选择把**决策逻辑放在本地**，控制台只负责规则的管理和推送，这就是“规则推送，本地执行”的架构哲学。

### 2.2 规则下发与持久化模式

规则要想动态生效，就必须解决“控制台如何把规则交给客户端”的问题。Sentinel 支持三种模式：

| 模式 | 原理 | 一致性/实时性 | 适用场景 |
|------|------|---------------|----------|
| **原始模式** | 规则保存在客户端内存，控制台通过API直接推送到客户端。控制台重启或客户端重启都会丢失规则。 | 实时高，但无持久化 | 本地开发测试 |
| **Pull模式** | 客户端定时从配置中心拉取规则（如本地文件、Consul）。 | 有延迟，依赖拉取间隔 | 简单生产，可接受秒级延迟 |
| **Push模式** | 控制台将规则写入配置中心（Nacos、ZooKeeper、Apollo），配置中心通知所有客户端更新。 | 近实时，持久化，强一致保障 | **生产推荐**：规则持久化，客户端动态监听 |

**第一性原理分析**：为什么Push模式是生产首选？  
因为 “规则数据”是配置，不是临时状态。配置应具备**持久化**和**变更通知**能力，这正是配置中心擅长的。Sentinel控制台不应自己承担存储和消息推送职责，而是委托给成熟中间件，遵循“单一职责”原则。

### 2.3 扩展点与SPI机制：责任链（Slot Chain）

Sentinel 的强大灵活性来自于它的**责任链模式**。所有对资源的访问都经过一个ProcessorSlot链，每个Slot负责一项职能，通过SPI可自定义编排。

**【修正】** 核心Slot及顺序（基于 Sentinel 1.8.x 源码 `DefaultSlotChainBuilder` 的 SPI 加载顺序）：
```
NodeSelectorSlot → ClusterBuilderSlot → LogSlot → StatisticSlot → AuthoritySlot → SystemSlot → ParamFlowSlot → FlowSlot → DegradeSlot
```
- **NodeSelectorSlot**：构建资源调用路径树节点。
- **ClusterBuilderSlot**：构建集群节点统计信息。
- **LogSlot**：记录请求日志。
- **StatisticSlot**：统计各种指标（RT、QPS、异常数等）。
- **AuthoritySlot**：黑白名单授权。
- **SystemSlot**：系统自适应保护。
- **ParamFlowSlot**：热点参数限流。
- **FlowSlot**：基于规则做流控。
- **DegradeSlot**：熔断降级。

**一句话总结**：Slot Chain是Sentinel的“脊柱”，任何请求都要穿过这条链，每个链节只做一件事，并可以通过SPI插入自定义链节。

**自问自答**：  
问：“如果我想在流控之前先检查一个自定义头，应该插入哪个Slot之后？”  
答：可以自定义Slot放在`AuthoritySlot`和`SystemSlot`之间，不影响核心指标统计。

### 2.4 集群限流架构

单机限流无法精确控制整个集群的总QPS（比如整个集群总QPS限制为1000）。集群限流需要一个外部“计数器”来统一分配许可。

- **Token Server**：**【修正】** Token Server 可以是独立部署的进程（独立模式），也可以是嵌入在业务应用中的一个节点（嵌入模式）。它维护精确的总令牌桶，处理所有客户端的许可请求。
- **Token Client**：嵌入应用，向Token Server异步申请令牌。支持两种模式：
  - 独立模式：Token Server单独部署。
  - 嵌入模式：在集群中选取一个节点作为Server。
- **通信与控制**：基于Netty，使用长连接，并配备降级策略：当Server不可用时，自动降级为单机限流。

## 3. 核心原理与算法深度剖析

这是我们深入“呼吸”的部分。每个算法，我们都会从“为什么需要它”开始推导。

### 3.1 流量控制算法

#### 3.1.1 滑动窗口计数器：LeapArray的实现细节

**第一性原理**：我们想限制QPS，就需要知道“过去1秒内有多少请求”。最简单的是固定窗口（例如每秒清空一次计数器）。但固定窗口有个致命缺陷：如果在第0.9秒到第1.1秒之间涌入100个请求，在0-1秒窗口和1-2秒窗口各计50个，都不会超限，但实际上0.2秒内承载了全量，造成**边界突发**。

**推导**：要解决这个问题，需要把1秒切分成更细的粒度，并让窗口随时间平滑滑动，不再有硬边界。  
Sentinel 使用**LeapArray**实现**滑动窗口**。它将统计周期（如1秒）分成N个桶（例如2个500ms桶），每个桶维护自己的计数器。每经过一个桶的时间，滑动窗口丢弃最老的桶，加入新桶。计算当前QPS时，将所有有效桶的计数相加除以窗口长度。

关键数据结构和并发控制：LeapArray使用`AtomicReferenceArray`存储桶。获取当前桶的`currentWindow(time)`逻辑如下：
- 如果桶不存在，通过CAS创建新桶。
- 如果桶已存在但窗口开始时间已过时，需要滑动窗口。为保证窗口重置的原子性，Sentinel使用了**ReentrantLock**。**【修正】** 获得锁后，才执行旧桶重置为新窗口的操作。若并发竞争锁失败，线程会阻塞（通过`ReentrantLock`的排队机制）直至获取锁，从而保证窗口重置的原子性。

这样设计既利用CAS快速创建新桶，又通过细粒度锁保证滑动时数据一致性，在极高并发下仍能保持正确性和高性能。

**一句话总结**：滑动窗口就是把时间轴切成小片，统计时只看最近N片，消除了固定窗口的“边界漏洞”。Sentinel的实现结合CAS与锁，兼顾了性能与正确性。

**自问自答**：  
问：“如果窗口长度1秒，分成2个桶，边界突发影响能降低多少？”  
答：突发持续时间最多是一个桶的长度（500ms），概率大大降低。

#### 3.1.2 令牌桶与漏桶在Sentinel中的体现

Sentinel 并非直接实现标准令牌桶，而是抽象出三种**流控效果**，对应于不同的算法思想：

- **直接拒绝（快速失败）**：当QPS超过阈值，直接抛出`FlowException`。对应滑动窗口计数，发现已达阈值就拒绝。
- **WarmUp（预热）**：系统启动时允许的QPS从低逐渐升到阈值。实现自`WarmUpController`，其内部模型是**预热令牌桶**。
- **排队等待**：匀速通过请求，超过阈值后不直接拒绝，而是让请求排队等待一段时间，若超时则失败。类似于**漏桶**算法。

##### 深入WarmUp：冷却因子与警戒令牌数

`WarmUpController`的核心思想是：系统冷状态时令牌消耗速率要慢（即许可发放慢），随着时间推移速率逐渐增加，直到稳定在阈值QPS。它有几个关键参数：
- `coldFactor`（冷却因子，默认3）：决定冷状态的速率降低程度。
- `warmUpPeriodSec`（预热时长）：从冷态到稳定态所需时间。
- `warningToken`（警戒令牌数）：令牌桶中的令牌数超过此值时进入预热冷态，速率降低。
- `maxToken`（最大令牌数）：桶容量。

**准确的计算公式**（源自`WarmUpController`源码）：
```
warningToken = (int)(warmUpPeriodInSec * count) / (coldFactor - 1);
maxToken = warningToken + (int)(2 * warmUpPeriodInSec * count / (1.0 + coldFactor));
```
其中`count`是阈值QPS。  
**【修正】** 冷状态下，许可发放的初始间隔是 `coldInterval`（即 `stableInterval * coldFactor`），随着系统预热（令牌被消耗），间隔逐渐线性减小，当令牌数降至 `warningToken` 时恢复为 `stableInterval`。`stableInterval` = 1/count，`coldInterval` = `stableInterval * coldFactor`。

**冷却因子3**的直观理解：冷启动时允许的瞬时速率只有阈值的1/3，系统有一个缓慢爬升的过程。

**一句话总结**：WarmUp不是不让你通过，而是让你“慢慢热起来”，防止冷系统被瞬间打垮。

**自问自答**：  
问：“冷却因子设成3代表什么数学含义？”  
答：冷状态时，许可证发放间隔是稳定间隔的3倍，即允许通过的速率只有正常阈值的1/3。

##### 排队等待：漏桶的匀速控制

`RateLimiterController`使用`latestPassedTime`记录上一个通过请求的时间。新请求到来时，计算期望通过时间 `expected = latestPassedTime + costTime`（costTime = 1/QPS）。如果当前时间小于期望时间，则需要等待 `waitTime = expected - now`。如果等待时间超过超时时间（由`maxQueueingTimeMs`设置），则拒绝；否则等待。

这就实现了匀速通过，相当于漏桶。

#### 3.1.3 三种流控效果对比

| 效果 | 算法本质 | 场景 | 突刺容忍度 |
|------|----------|------|------------|
| 快速失败 | 滑动窗口计数器 | 保护系统不被突发流量冲垮 | 零容忍 |
| WarmUp | 预热令牌桶 | 缓存预热、刚启动的服务 | 逐渐上升 |
| 排队等待 | 漏桶（严格队列） | 消息队列削峰、需要恒定速率的场景 | 允许等待 |

### 3.2 熔断降级算法

**第一性原理追问**：限流是“量”的控制，而熔断是“质”的控制。当依赖服务质量下降到不可接受，我们应该**快速失败而不是继续忍受慢和错误**。

Sentinel 熔断器（DegradeSlot）定义三种不稳定的标准：
1. **慢调用比例**：RT大于阈值（如500ms）的请求占比超过设定比例。
2. **异常比例**：抛出异常的请求占比超过阈值。
3. **异常数**：一分钟内异常请求的绝对数量。

#### 3.2.1 断路器状态机

- **关闭(Closed)**：正常统计，当指标达到熔断阈值，转变为打开。
- **打开(Open)**：拒绝所有请求，直接抛出`DegradeException`。经过一个可配置的`timeWindow`（如10秒）后，转为半开。
- **半开(Half-Open)**：允许少量请求通过（探测），如果这些探测请求成功（不再满足熔断条件），则断路器关闭；如果仍有失败，再次打开。

**第一性原理分析**：为什么需要半开状态？  
完全自动打开后，如果永远不尝试恢复，依赖可能已经好了但我们不知道，这等于永久降级。半开用最小的代价（一个或几个请求）去探测，是“乐观试探，悲观保护”。

#### 3.2.2 统计窗口：秒级滑动窗口（默认1秒）

熔断统计窗口由`statIntervalMs`控制，**默认值为1000ms（即1秒）**。滑动窗口类似流控，但默认粒度为1秒。慢调用比例、异常比例都是基于这个窗口内的数据。对于RT的判断，Sentinel并非计算精确p99，而是统计超过阈值RT的次数，近似反映慢调用比重。

#### 3.2.3 如何选择统计窗口长度

默认1秒窗口能够快速响应依赖恶化，但在某些场景可能过于敏感——短暂的网络毛刺或GC停顿可能导致慢调用比例瞬间达标，触发不必要的熔断。此时可增大`statIntervalMs`（如设为60000毫秒，即1分钟），利用更长时间窗口平滑瞬态抖动，让熔断决策更稳重。但代价是故障发现速度变慢，需要根据业务容忍度权衡。

**一句话总结**：熔断就是“你不好，我先把你关掉，等会儿再试试看”，是面向依赖的智能开关。

**自问自答**：  
问：“如果半开状态下发的一个探测请求很慢但没有超时，熔断器会怎么反应？”  
答：该慢请求会被统计，如果导致慢调用比例再次达标，断路器会再次打开。  
问：“为什么默认1秒窗口可能导致误熔断？如何优化？”  
答：瞬时的网络延迟可能使慢调用比例短暂超标，造成误熔断。可增大统计窗口到分钟级以平滑波动，但需接受更慢的故障恢复。

### 3.3 系统自适应保护

**第一性原理**：之前的规则都需要人工设定阈值。能不能让系统自己知道“我快不行了”，然后主动拒绝请求？  
这需要一个系统整体的“负荷”指标。Sentinel 从**五个维度**定义系统自适应规则：

- **Load**：操作系统1分钟平均负载，超过阈值。
- **CPU使用率**：当前CPU usage。
- **平均RT**：所有入口资源的平均响应时间。
- **并发线程数**：所有入口资源的并发执行线程数。
- **入口QPS**：所有入口流量的总QPS。

当任何一个指标超过阈值，SystemSlot会触发保护，拒绝所有入口流量。这借鉴了TCP BBR拥塞控制的思想：不断探测系统容量，一旦逼近极限就主动限流。

**一句话总结**：系统保护是最后的“安全气囊”，不看具体服务，只看整个进程的健康。

### 3.4 热点参数限流

**第一性原理**：有时候QPS总量正常，但某个热点用户或商品ID被频繁请求导致局部过热，比如秒杀商品。我们需要对**参数值**进行精细控制。

Sentinel 使用 **ParamFlowSlot** 实现。核心是一个 LRU 缓存（默认容量4000），缓存每个参数值的统计窗口。当某个参数值QPS超过阈值，仅对该参数值限流，不影响其他参数。

**推导**：如果为每个参数都维护一个全量窗口，内存会爆炸。但大多数场景只有少量热点参数，所以用LRU保留最频繁的那些，冷门参数自动淘汰。这正是资源有限下的折中。

**一句话总结**：热点限流是“枪打出头鸟”，针对最热的key进行精准打击。

**自问自答**：  
问：“如果一个冷门参数偶尔超过阈值，会被限流吗？”  
答：可能不会，因为LRU中可能还没有它的统计，或者统计窗口不完整。热点限流主要面向频繁出现的参数。

## 4. 主要功能详解与场景化指南

### 4.1 功能全景及选型

| 功能 | 场景举例 | 规则关键配置 |
|------|----------|--------------|
| 流量控制 | 保护核心API每秒处理能力 | 资源名、阈值类型(QPS/线程数)、流控效果 |
| 熔断降级 | 第三方支付接口超时频繁 | 降级策略(慢调用/异常)、比例/数值、熔断时长 |
| 热点参数限流 | 秒杀商品详情页，限制单个商品QPS | 参数索引、阈值、统计窗口、参数例外项 |
| 系统保护 | 服务整体负载高时自动限流 | 阈值类型(LOAD/CPU/RT/线程数/入口QPS) |
| 授权规则 | 只允许内部服务调用，拒绝外网IP | 黑白名单、来源应用 |
| 集群流控 | 全网QPS精确限制到集群 | 集群模式、Token Server配置 |
| 网关流控 | API网关针对路由、API分组限流 | 路由模式、参数提取、网关专用API |

### 4.2 降级处理最佳范式

资源定义粒度：建议使用`@SentinelResource`注解，并指定`blockHandler`和`fallback`方法。

```java
@SentinelResource(value = "getOrder", blockHandler = "handleBlock", fallback = "handleFallback")
public Order getOrder(String orderId) {
    // 业务逻辑
}
```

- `blockHandler`：处理被Sentinel流控/熔断的`BlockException`。
- `fallback`：处理业务异常。

配合 `UrlCleaner` 可对资源URL进行清洗聚合，比如`/order/123`和`/order/456`聚合为`/order/*`。

**一句话总结**：资源定义的精细度决定了控制的灵活度，但过细则管理复杂，遵循“按服务接口聚合，必要时参数精细化”原则。

## 5. 生产问题分类与解决方案（决策树）

当出现问题时，按以下决策树排查：

```
问题现象
│
├── 规则不生效
│   ├── 检查资源名是否与规则完全匹配（注意 URL 清洗）
│   ├── 检查控制台规则是否成功推送到客户端（查看日志/端点）
│   ├── 如果是集群限流，检查Token Server状态
│   └── 确认规则启动时间（是否在应用启动前就配置）
│
├── 熔断频繁切换/不恢复
│   ├── 检查统计窗口是否有突发流量导致比例瞬间超标
│   ├── 降低熔断阈值比例或增加统计窗口长度（如调整为分钟级）
│   ├── 检查半开探测的超时/等待时间是否合理
│   └── 查看是否有网络抖动，考虑增加RT阈值
│
├── 控制台无监控数据
│   ├── 检查客户端是否引入了sentinel-transport模块
│   ├── 检查端口是否正确（默认8719），网络互通
│   ├── 检查应用是否有流量产生（没有流量无数据）
│   └── 检查控制台日志是否报错
│
├── 规则持久化失败（Push模式）
│   ├── 检查配置中心（Nacos等）是否正常
│   ├── 查看控制台推送日志，确认配置写入配置中心成功
│   ├── 检查客户端监听的namespace/group正确性
│   └── 确认配置中心中规则数据格式正确
│
├── 集群限流脑裂/Token Server不可用
│   ├── Token Server部署为独立高可用，避免单点
│   ├── 客户端必须配置降级为单机限流
│   ├── 检查Token Server与客户端通信的网络和序列化
│   └── 脑裂时，适当调整lease时长
│
├── 引入Sentinel后性能下降
│   ├── 检查Slot Chain中是否有自定义Slot耗时严重
│   ├── 是否有大量热点参数导致LRU频繁失效
│   ├── 如果使用排队等待模式，检查maxQueueingTimeMs是否过大导致线程堆积
│   └── 检查是否有过多的规则（千级以上）
│
└── 网关集成问题
    ├── 确认使用了对应网关适配模块（spring-cloud-gateway等）
    ├── 注意路由ID与资源名的映射规则
    ├── 网关限流可基于Route或自定义API分组
    └── 检查过滤器顺序，SentinelGatewayFilter需在反应式链中执行
```

典型问题详细剖析示例：

**问题**：配置了QPS限流1000，实际在800时就开始拒绝。  
**根因**：滑动窗口统计是估算值，如果窗口分割较粗（如1秒2桶），可能出现局部超限。也可能是线程数限流规则同时生效。  
**解决**：检查是否有其他规则叠加，调整窗口桶数（增大平滑度），确认限流阈值类型。

## 6. 使用优化与最佳实践

### 6.1 资源名称规范与埋点优化

- 使用类名+方法名，如`com.example.OrderService.getOrder`。
- 避免将资源细化到用户ID级别，除非有强需求，用热点限流代替。
- 对于频繁调用的方法，使用`SphU.entry()`手动定义资源时，务必在`finally`块中`entry.exit()`。

### 6.2 动静分离：规则托管配置中心

生产环境采用Push模式，将规则托管到Nacos/Apollo等。控制台仅作为规则编辑界面，配置中心作为规则存储和下发中枢。这样控制台挂掉不影响已下发规则。

### 6.3 监控集成

- 将Sentinel Metric暴露给Prometheus：通过`sentinel-metric-prometheus`模块直接暴露端点。
- 日志记录：配置`BlockException`处理逻辑，将限流、熔断事件记录到业务日志，用于后续分析。
- 事件监听：实现`SentinelEvent`监听器，可对熔断状态变化等事件进行告警。

### 6.4 压测调优

- **WarmUp参数设置**：根据服务启动后到能满载处理的时间来设定预热时长（秒）。一般Java应用JIT编译需要几十秒，可设60秒预热期。冷却因子保持默认3即可，除非有特定需求。
- **排队超时设定**：`maxQueueingTimeMs`不宜过大，超过通常的请求超时时间没意义，建议200-500ms。
- **熔断窗口**：`timeWindow`（熔断打开持续时间）不要太短（如3秒），容易抖动，建议10-30秒。`statIntervalMs`默认1秒，若因抖动导致误熔断可调大。
- 使用`Jmeter`或`wrk`压测，观察RT分布，确定合理的QPS阈值和线程数阈值。

### 6.5 大促场景策略模板

1. **容量规划**：通过压测确定服务的单机极限QPS，设定总集群限流为该极限的80%。
2. **规则预演**：在预发环境将所有规则推送到配置中心，验证规则加载和生效。
3. **灰度上线**：先对部分实例下发规则观察。
4. **快速回滚**：规则全部托管在配置中心，一旦限流导致异常，可直接在配置中心调整阈值或禁用规则，无需重启应用。

### 6.6 框架适配注意点

- **Dubbo**：引入`sentinel-apache-dubbo-adapter`，自动将Dubbo接口方法作为资源，支持流控和降级。注意fallback配置。
- **Spring Cloud**：使用`@SentinelRestTemplate`或`@FeignClient`降级。确保sentinel启动顺序早于feign。
- **gRPC**：使用对应拦截器，埋点资源和追踪。

## 7. 费曼学习法终极检验

### 7.1 向应届生解释什么是Sentinel（200字内）

你可以这样讲：

> Sentinel就像你家的智能电网系统。家里有很多电器（服务），但入户总功率有限（系统容量）。当你同时开很多电器，电流过大，保险丝就会熔断（熔断），防止烧毁线路。水龙头的水流也是，水厂压力有限，水龙头有个限流器让水不会哗哗流得太猛（限流）。Sentinel就是给软件系统装上了这样的限流器和保险丝，让请求平稳过来，遇到坏掉的电器立刻切断，不让一个坏掉的电器影响全家用电。

### 7.2 15个自测问题（含答案要点）

1. **滑动窗口如何解决固定窗口的边界突发问题？**  
   答：将时间轴切分为多个小桶，统计总请求时只看最近几个桶的和，没有硬边界，无法利用边界间隔穿透。

2. **WarmUp流控效果中冷却因子设成3代表什么数学含义？**  
   答：冷启动时许可证发放间隔是稳定间隔的3倍，即允许的初始速率仅为阈值的1/3，随着令牌消耗速率线性恢复。

3. **半开状态如何判断是否恢复？如果半开期间仍有少量慢调用会发生什么？**  
   答：半开状态下允许探测请求通过，实时统计这些请求的慢调用/异常比例，一旦再次达到阈值，断路器立刻回到打开状态。

4. **Sentinel的Slot Chain中，StatisticSlot放在FlowSlot前面有什么好处？**  
   答：先统计后限流，保证限流判断基于当前窗口的准确统计，同时限流失败的请求也会被统计，可反映被拒流量。

5. **为什么集群限流需要独立Token Server而不是直接选取集群内一个节点？**  
   答：避免单点性能瓶颈和复杂的选主逻辑，独立Server可以水平扩展，职责单一，并且避免了与业务混合部署的资源竞争。（注：嵌入模式也是一种选择，但独立模式更常用）

6. **Push模式相比Pull模式在生产环境有哪些核心优势？**  
   答：规则变更实时推送，无需等待轮询间隔；规则持久化在配置中心，不会因为控制台重启丢失。

7. **解释`maxQueueingTimeMs`在排队等待流控中的作用。**  
   答：定义请求允许的最长排队等待时间，超过则拒绝，防止请求无限排队导致连接耗尽。

8. **为什么熔断统计窗口默认1秒可能过于敏感？如何解决？**  
   答：默认1秒窗口容易因瞬时网络抖动或GC引发误熔断。可将`statIntervalMs`调大（如60000）平滑波动，但需权衡故障发现的延迟。

9. **如果规则不生效，可能有哪些原因？（列出至少三个）**  
   答：资源名不匹配；客户端与控制台网络不通且无本地规则；规则推送失败；规则不在生效状态（如规则被禁用）；集群限流Token Server未启动。

10. **系统自适应保护中，为什么使用操作系统Load而不是进程CPU？**  
    答：操作系统Load能更全面反映I/O等待等整体资源压力，当Load高时CPU可能不高但线程都在等磁盘，同样需要保护。此外还支持入口QPS等维度。

11. **热点参数限流中的LRU缓存有什么作用？**  
    答：限制内存中统计的参数数量，只保留最热参数，丢弃冷参数，以固定成本处理大多数热点。

12. **如何设计一个防止规则持久化丢失的方案？**  
    答：使用配置中心（如Nacos）存储规则，控制台与配置中心交互，客户端监听配置中心，即使控制台宕机规则依然存在并可下发。

13. **在引入Sentinel后发现应用线程数增加，可能的原因是什么？**  
    答：流控效果使用排队等待模式时，请求线程会sleep等待，如果并发量大，会导致线程堆积。建议评估是否改为快速失败或缩小超时时间。

14. **Sentinel与Hystrix的区别体现在设计思想上是什么？**  
    答：Sentinel更侧重流量控制和系统保护，规则动态配置灵活；Hystrix侧重隔离和降级（线程池/信号量），设计较重。Sentinel采用责任链和槽位扩展，更易定制。

15. **描述大促前Sentinel的完整准备流程。**  
    答：压测确定阈值 -> 编写限流降级规则 -> 推到配置中心 -> 预发验证 -> 生产灰度部分实例 -> 全量发布 -> 监控告警系统就位，准备应急回滚。
