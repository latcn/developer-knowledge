## 第一部分：核心概念与认证机制

### 1. 基础概念

| 术语 | 定义 |
|------|------|
| **认证（Authentication）** | 确认“你是谁”。例如用户名/密码、扫码、生物识别。 |
| **授权（Authorization）** | 决定“你能做什么”。例如角色是否有权限访问某 API。 |
| **凭证（Credential）** | 证明身份的信息，如密码、令牌、证书。 |
| **访问控制（Access Control）** | 具体授权策略模型：ACL、RBAC、ABAC 等。 |

### 2. 常见认证机制

#### 2.1 HMAC-SHA256 签名认证（API 签名）

用于 API 请求防篡改和身份验证（如 AWS、阿里云）。

**步骤**：
1. 客户端获取 `AccessKeyId`（公开）和 `SecretAccessKey`（机密）。
2. 构造待签名字符串：`HTTP Method + "\n" + Path + "\n" + QueryString + "\n" + Body(可选) + "\n" + Timestamp + "\n" + Nonce`，按字典序排序。
3. 使用 `SecretAccessKey` 对字符串进行 HMAC-SHA256 签名，得到 `Signature`。
4. 请求头中携带 `AccessKeyId`、`Signature`、`Timestamp`、`Nonce`。
5. 服务端重算签名并比对，同时校验时间戳与 Nonce 防重放。

**安全要点**：
- `SecretAccessKey` **绝不通过网络传输**（仅用于本地签名）。
- 强制使用 HTTPS。
- Nonce 保证一次有效，服务端需缓存已用 Nonce。

#### 2.2 TOTP（基于时间的一次性密码）

用于两步验证（如 Google Authenticator）。

- **原理**：客户端与服务端共享密钥（Base32），以当前时间窗口（通常 30 秒）为计数器，通过 HMAC 生成 6-8 位数字。
- **算法**：RFC 6238 定义支持 HMAC-SHA1（最常用）、HMAC-SHA256、HMAC-SHA512。部分服务因 SHA1 安全性考虑已迁移至 SHA256。
- **特点**：无需网络，双方独立计算。

### 3. JWT（JSON Web Token）

#### 3.1 结构

`header.payload.signature`

- **Header**：`{"alg":"HS256","typ":"JWT"}`
- **Payload**：包含声明（`iss`、`exp`、`sub`、`aud` 等）及自定义字段。
- **Signature**：对 `header.payload` 进行签名（HMAC 或 RSA）。

#### 3.2 安全注意事项

| 问题 | 说明 |
|------|------|
| Payload 不加密 | 仅 base64 编码，**严禁存放敏感信息**（如身份证、密码）。如需加密，使用 JWE（RFC 7516）。 |
| 签名算法漏洞 | 防止 `alg: none` 攻击。**真实案例**：CVE-2025-61152（python‑jose ≤3.3.0）、CVE-2026-28802（Authlib 1.6.0‑1.6.5）表明 2025‑2026 年仍有库受此影响。服务端必须强制校验算法白名单（仅接受 HS256/RS256/ES256），并启用 `kid` 白名单以防止算法混淆攻击。 |
| 无法主动撤销 | 可通过**短生命周期（5~15 分钟）+ Refresh Token 轮换**或**黑名单（Redis 存储 `jti`）** 实现类撤销。 |
| 校验所有标准声明 | 必须校验 `exp`（过期）、`nbf`（生效时间）、`iss`（签发者）、`aud`（受众）等。 |

#### 3.3 最佳实践

- 使用强签名算法，禁用 `none`。
- 设置合理的过期时间（Access Token 建议 ≤15 分钟）。
- 使用 Refresh Token 机制（长期凭证，需绑定客户端并启用轮换）。
- 黑名单方案：授权服务器维护撤销列表，资源服务器可调用 introspection 端点查询（牺牲无状态性）。

### 4. 访问控制策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| **RBAC** | 用户 → 角色 → 权限 | 权限相对稳定，如企业内部系统。 |
| **ABAC** | 基于属性（用户、资源、环境）动态计算 | 复杂业务规则，如“仅限本人查看自己的订单”。 |
| **ACL** | 直接为每个资源绑定用户/组权限 | 文件系统、共享文档。 |

> 现代系统常混合使用：**粗粒度用 RBAC（角色），细粒度用 ABAC（属性）**。此外，外部策略引擎（如 OPA）也可作为独立的授权层。

### 5. Spring Security 核心组件（6.x / 7.x 现代架构）

| 组件 | 职责 |
|------|------|
| `SecurityFilterChain` | 定义过滤器链，匹配路径的安全规则。 |
| `AuthenticationManager` | 认证流程管理器。 |
| `ProviderManager` | 委托给多个 `AuthenticationProvider`。 |
| `DaoAuthenticationProvider` | 配合 `UserDetailsService` 完成用户名/密码认证。 |
| `AuthorizationManager` | 授权决策管理器（**替代旧版 `AccessDecisionManager` 和 `AccessDecisionVoter`**）。旧 API 已标记废弃，Spring Security 7 中将移至独立模块 `spring-security-access`。 |

### 6. Apache Shiro 概要

- **核心组件**：`Subject`（当前用户）、`SecurityManager`（调度中心）、`Realm`（数据源）。
- **特点**：配置简单，但 OAuth2/OIDC 集成较弱。
- **安全提醒**：Apache Shiro 2.x 存在认证绕过漏洞（CVE-2026-23903 等），攻击者可利用大小写不敏感文件系统绕过静态文件认证。务必升级到 **2.0.7 或更高版本**。

### 7. 安全最佳实践汇总

| 实践 | 说明 |
|------|------|
| 强制 HTTPS | 所有令牌、凭证必须在 TLS 信道中传输。 |
| Access Token 不放在 URL 中 | 应使用 `Authorization: Bearer` 头。 |
| Refresh Token 绑定客户端凭证 | 验证 client_id + client_secret。 |
| **Refresh Token 轮换** | **每次刷新时颁发新 Refresh Token，并使旧令牌立即失效，防止重放攻击。** 需处理并发刷新冲突（乐观锁或原子操作），并遵循 OAuth 2.0 Security BCP (RFC 6819) 建议。 |
| JWT 强制校验算法 | 防止 `alg: none` 和 `kid` 注入攻击。建议启用 `kid` 白名单。 |
| 短期 Access Token + 长期 Refresh Token | Access Token 有效期 5~15 分钟。 |
| 防重放 | 使用 Nonce + 时间戳缓存或 TOTP。 |
| 密钥轮换 | 定期更换 HMAC 或 RSA 密钥。 |
| CSRF 防护 | 使用 cookie 存储 token 时需启用 CSRF Token；Bearer Token 方式免疫。 |
| 速率限制 | 防止暴力破解和滥用。 |
| 审计日志 | 记录认证、授权失败等关键事件。 |

## 第二部分：OAuth 2.1 草案 / OIDC 实战与第三方登录

> **规范状态声明**：OAuth 2.1 目前是 IETF 互联网草案 **draft-ietf-oauth-v2-1-15**（2026‑03‑02 发布，2026‑09‑03 到期），尚未成为正式 RFC。但其核心安全改进（PKCE 强制要求、移除隐式授权/密码授权、Refresh Token 轮换等）已被主流授权服务器和身份提供商广泛采纳，代表下一代 OAuth 的演进方向。

### 1. OAuth 2.1 核心概念

#### 1.1 角色

| 角色 | 说明 |
|------|------|
| **资源所有者** | 用户本人。 |
| **客户端** | 第三方应用。 |
| **授权服务器** | 认证用户、颁发令牌。 |
| **资源服务器** | 存储用户数据，校验令牌。 |

#### 1.2 授权模式（OAuth 2.1 保留）

| 模式 | 适用场景 | 要求 |
|------|----------|------|
| **授权码模式** | 有后端服务的 Web 应用，为用户参与的交互场景。 | **强制使用 PKCE**。授权服务器必须拒绝缺少 `code_challenge` 和 `code_challenge_method=S256` 的请求。 |
| **客户端凭证模式** | 机器对机器（M2M），无用户参与。 | 不涉及用户授权，是服务端调用的推荐模式。 |
| **刷新令牌** | 辅助获取新的访问令牌。 | 必须实现轮换（见 1.3 节）。 |

> ❌ **OAuth 2.1 已完全移除**：隐式授权（Implicit）、资源所有者密码模式（Password）。这些模式不再属于 OAuth 2.1 规范。

#### 1.3 令牌类型与安全要求

- **Access Token**：短期（分钟~小时），发给资源服务器。前端存储需谨慎（建议内存或 session storage）。
- **Refresh Token**：长期（天~月），**仅在客户端与授权服务器之间传输**，必须绑定客户端凭证（client_id + client_secret）。
- **Refresh Token 轮换（Rotation）**：  
  每次客户端使用 Refresh Token 换取新的 Access Token 时，授权服务器**必须颁发一个新的 Refresh Token**，并使旧的 Refresh Token 立即失效。  
  这可以防止令牌被窃取后攻击者长期使用同一 Refresh Token 刷新会话。如果授权服务器检测到同一个 Refresh Token 被多次使用（可能是重放攻击），应撤销该用户的所有令牌。  
  > **可靠性权衡**：轮换机制在网络偶发丢失时可能导致客户端收不到新令牌，建议实现幂等重试、持久队列或原子操作（如乐观锁）来处理并发刷新冲突。此建议符合 OAuth 2.0 安全最佳实践（RFC 6819）。

#### 1.4 验证 Access Token 的方式

| 方式 | 原理 | 优缺点 |
|------|------|--------|
| **Introspection** | 资源服务器调用授权服务器的 `/introspect` 端点。 | 实时撤销，但有网络开销和单点依赖。 |
| **JWT** | 授权服务器用私钥签发 JWT，资源服务器用公钥校验签名。 | 无状态、高性能，但撤销需额外机制（短过期+黑名单）。 |

### 2. OpenID Connect (OIDC)

- **解决的问题**：OAuth 2.0 只授权，不提供用户身份信息。
- **OIDC 扩展**：在授权码流程中额外返回 **ID Token**（JWT 格式），包含 `sub`（用户唯一标识）、`email`、`name` 等。
- **典型流程**：客户端获取 access_token 的同时获得 ID token，通过验证 ID token 完成用户认证。

### 3. 第三方登录实战（以 GitHub 为例）

#### 3.1 回调 URL 配置

- **GitHub OAuth App**：只允许配置**一个**精确回调 URL（完全匹配：协议、域名、端口、路径、大小写、末尾斜杠）。
- **GitHub Apps**：支持配置多个回调 URL。
- **本地开发**：可用 `http://localhost:端口/路径`，生产必须 `https`。

**匹配规则示例**：
```
注册：https://yourapp.com/login/oauth2/code/github
请求中必须完全一致，否则返回 redirect_uri_mismatch。
```

#### 3.2 授权码流程（标准）

1. 客户端携带 `client_id`、`redirect_uri`、`state`、`code_challenge`（PKCE）跳转 GitHub 授权页。
2. 用户授权后，GitHub 重定向到回调 URL，附带 `code` 和 `state`。
3. 客户端（后端）用 `code` + `client_secret` + `code_verifier` 向 GitHub 换取 `access_token`。
4. 用 `access_token` 调用 GitHub API 获取用户信息。

#### 3.3 `state` 参数：防御 CSRF（账户绑定攻击）

**作用**：
- 防止攻击者利用自己生成的授权码，诱骗已登录用户完成账户绑定。
- 可携带业务状态（如登录前页面地址）。

**实现**：
1. 服务端生成随机字符串（如 UUID），存入当前用户 Session 或临时缓存。
2. 授权请求中附带 `state` 参数。
3. 回调时比对：若不一致则拒绝（CSRF 攻击）。

> **注意**：`state` 无法防御 XSS（如攻击者能在你网站执行脚本，可读取 `state`）。XSS 需通过 CSP、输入过滤、HttpOnly Cookie 等防御。

#### 3.4 PKCE（代码交换证明密钥）详解

##### 为什么需要 PKCE？

- **公开客户端**（纯前端 SPA、移动 App）无法安全保存 `client_secret`，原授权码流程存在拦截风险。
- **OAuth 2.1 强制要求**所有使用授权码流的客户端必须使用 PKCE（包括机密客户端，作为深度防御）。

##### 核心组件

| 组件 | 说明 |
|------|------|
| **`code_verifier`** | 高熵随机字符串（43~128 字符），客户端本地生成，**仅在与授权服务器交换 token 时发送**。 |
| **`code_challenge`** | `code_verifier` 的 SHA-256 哈希后 Base64URL 编码，**在授权请求中发送**。 |

##### 流程

1. 客户端生成 `code_verifier`，计算 `code_challenge = Base64URL(SHA256(verifier))`。
2. 授权请求携带 `code_challenge` 和 `code_challenge_method=S256`。
3. 授权服务器存储 `code_challenge` 并返回 `code`。
4. 客户端用 `code` + `code_verifier` 请求 `/token` 端点。
5. 授权服务器重算 `code_challenge`，比对存储值，通过则颁发 token。

**安全效果**：即使攻击者截获 `code` 和 `code_challenge`，也无法提供 `code_verifier`，因而无法换取 token。

**强制要求**：根据 OAuth 2.1 草案，授权服务器必须拒绝任何缺少 `code_challenge` 或 `code_challenge_method` 的授权请求，并且 `code_challenge_method` 必须为 `S256`（不允许 `plain`）。

##### GitHub 支持

- **GitHub 推荐使用 PKCE**，但非强制要求。对于公开客户端（SPA、移动应用），强烈建议启用。GitHub 要求 `code_challenge_method` 必须为 `S256`。
- 注：设备授权流程（Device Flow）和安装令牌（Installation Token）不受 PKCE 影响，无需使用 PKCE。
- 如果你使用 Spring Security 等框架，设置 `client-authentication-method: none` 会自动启用 PKCE。

### 4. 授权决策模式对比

| 模式 | 决策位置 | 权限粒度 | 优点 | 缺点 | 适用场景 |
|------|----------|----------|------|------|----------|
| **集中式** | 授权服务器 | 粗（scope/角色） | 管理集中、资源服务器无状态 | 难以表达复杂规则 | 第三方 API 接入，微服务 |
| **资源自主** | 资源服务器 | 细（ABAC） | 表达力强、实时变更 | 权限分散、重复实现 | 复杂业务逻辑，遗留系统 |
| **混合模式** | 两者结合 | 粗+细 | 兼顾集中与灵活 | 设计稍复杂 | 大多数生产系统 |
| **外部策略引擎** | 独立授权引擎（OPA） | 细（ABAC） | 集中规则，动态决策 | 额外组件和延迟 | 大规模复杂策略环境 |

**推荐混合模式**：
- 授权服务器颁发 `scope` 控制 API 级访问（如 `read:orders`）。
- 资源服务器在方法内用 `@PreAuthorize` 进一步判断行级权限（如用户只能看自己的订单）。

> ⚠️ **安全提醒**：务必在授权服务器端实现 **Refresh Token 轮换**。这是 OAuth 2.0 安全最佳实践的核心要求，可有效防御令牌窃取后的持续滥用。

> - Spring Security 7.0.0 已于 2025‑11‑17 GA，7.0.5 于 2026‑04‑20 发布。代码示例在 6.x 和 7.x 下均可运行（主体 API 兼容）。

#### 1.2 基础安全配置（基于 `SecurityFilterChain`）

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**", "/error").permitAll()
                .anyRequest().authenticated()
            )
            .formLogin(form -> form
                .loginPage("/login")
                .permitAll()
            )
            .logout(logout -> logout.permitAll());
        return http.build();
    }
}
```

#### 1.3 JWT 资源服务器配置

```java
@Configuration
@EnableWebSecurity
public class ResourceServerConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers("/api/orders/**").hasAuthority("SCOPE_read_orders")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt());
        return http.build();
    }
}
```

配合 `application.yml`：

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://your-auth-server.com
          jwk-set-uri: https://your-auth-server.com/oauth2/jwks
```

#### 1.4 GitHub 第三方登录配置（含 PKCE 启用）

对于**公开客户端**（纯前端 SPA 或无法安全保管 `client_secret` 的应用），**必须启用 PKCE**。Spring Security 通过设置 `client-authentication-method: none` 自动启用 PKCE。

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          github:
            client-id: ${GITHUB_CLIENT_ID}
            client-secret: ${GITHUB_CLIENT_SECRET}   # 公开客户端可不配置，但 GitHub 要求必须有占位符
            client-authentication-method: none       # 关键：标记为公开客户端，自动启用 PKCE
            authorization-grant-type: authorization_code
            scope:
              - user:email
              - read:user
            redirect-uri: "{baseUrl}/login/oauth2/code/github"
        provider:
          github:
            authorization-uri: https://github.com/login/oauth/authorize
            token-uri: https://github.com/login/oauth/access_token
            user-info-uri: https://api.github.com/user
            user-name-attribute: login
```

> **说明**：设置 `client-authentication-method: none` 后，Spring Security 会自动生成 `code_verifier` 和 `code_challenge`，并在授权请求中传递 `code_challenge=S256`，在 token 请求中传递 `code_verifier`。无需手动编码。

对于**机密客户端**（有后端，能安全保存 `client_secret`），虽然 OAuth 2.1 建议也启用 PKCE，但 Spring Security 默认不自动启用。如需启用，可以自定义 `OAuth2AuthorizationRequestResolver` 或使用 `AuthorizationRequestCustomizer`。下面是一个强制启用 PKCE 的配置示例：

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .oauth2Login(oauth2 -> oauth2
            .authorizationEndpoint(endpoint -> endpoint
                .authorizationRequestResolver(
                    new DefaultOAuth2AuthorizationRequestResolver(
                        clientRegistrationRepository,
                        "/oauth2/authorization"
                    ) {{
                        setAuthorizationRequestCustomizer(
                            OAuth2AuthorizationRequestCustomizers.withPkce()
                        );
                    }}
                )
            )
        );
    return http.build();
}
```

#### 1.5 通用 OAuth2 客户端 + PKCE（自定义授权服务器）

当对接任意支持 PKCE 的授权服务器（如 Keycloak、Auth0、Okta）时，可以在 `application.yml` 中配置并强制使用 PKCE：

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          my-auth-server:
            client-id: my-client
            client-secret: my-secret   # 即使有 secret，也可启用 PKCE
            client-authentication-method: client_secret_basic
            authorization-grant-type: authorization_code
            scope: openid,profile,email
            redirect-uri: "{baseUrl}/login/oauth2/code/my-auth-server"
        provider:
          my-auth-server:
            issuer-uri: https://my-auth-server.com
```

然后在代码中强制要求 PKCE（通过自定义 `OAuth2AuthorizationRequestResolver` 或 `AuthorizationRequestCustomizer` 添加 `code_challenge` 参数），推荐使用 `OAuth2AuthorizationRequestCustomizers.withPkce()`。

### 2. Spring Authorization Server 快速示例（含 PKCE 要求）

#### 2.1 依赖

```xml
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-oauth2-authorization-server</artifactId>
    <version>1.5.7</version>
</dependency>
```

#### 2.2 配置授权服务器（支持 PKCE）

Spring Authorization Server 默认**自动支持 PKCE**，无需额外配置。但你可以强制要求客户端使用 PKCE（通过 `requireProofKey`）。

```java
@Configuration
@EnableWebSecurity
public class AuthorizationServerConfig {

    @Bean
    @Order(1)
    public SecurityFilterChain authorizationServerSecurityFilterChain(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/oauth2/**")
            .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt());
        return http.build();
    }

    @Bean
    @Order(2)
    public SecurityFilterChain standardSecurityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
            )
            .formLogin(Customizer.withDefaults());
        return http.build();
    }

    @Bean
    public RegisteredClientRepository registeredClientRepository() {
        RegisteredClient registeredClient = RegisteredClient.withId(UUID.randomUUID().toString())
            .clientId("pkce-client")
            // 对于公开客户端，可以不设置 clientSecret
            .clientAuthenticationMethod(ClientAuthenticationMethod.NONE)   // 公开客户端
            .authorizationGrantType(AuthorizationGrantType.AUTHORIZATION_CODE)
            .authorizationGrantType(AuthorizationGrantType.REFRESH_TOKEN)
            .redirectUri("https://yourapp.com/login/oauth2/code/custom")
            .scope("read_orders")
            .scope("write_orders")
            // 强制要求 PKCE（客户端必须提供 code_challenge）
            .clientSettings(ClientSettings.builder()
                .requireProofKey(true)   // 关键：强制 PKCE
                .build())
            .tokenSettings(TokenSettings.builder()
                .accessTokenTimeToLive(Duration.ofMinutes(5))
                .refreshTokenTimeToLive(Duration.ofDays(1))
                .reuseRefreshTokens(false)   // Refresh Token 轮换
                .build())
            .build();

        return new InMemoryRegisteredClientRepository(registeredClient);
    }

    @Bean
    public JWKSource<SecurityContext> jwkSource() {
        RSAKey rsaKey = Jwks.generateRsa();
        JWKSet jwkSet = new JWKSet(rsaKey);
        return (jwkSelector, context) -> jwkSelector.select(jwkSet);
    }
}
```

> **说明**：
> - `clientSettings.requireProofKey(true)` 强制要求客户端在授权请求中携带 `code_challenge` 且 `code_challenge_method=S256`，否则授权请求会被拒绝（HTTP 400）。
> - 对于公开客户端（无 `client_secret`），必须使用 PKCE；对于机密客户端，也可要求 PKCE 作为额外安全层。
> - `reuseRefreshTokens(false)` 启用 Refresh Token 轮换，每次刷新颁发新令牌。
> - 授权服务器应实现 `code_verifier` 校验失败时的明确错误处理（如返回 `invalid_grant`）。

#### 3.3 Java 代码示例

```java
import org.apache.shiro.SecurityUtils;
import org.apache.shiro.authc.UsernamePasswordToken;
import org.apache.shiro.subject.Subject;

public class ShiroDemo {
    public static void main(String[] args) {
        Subject currentUser = SecurityUtils.getSubject();
        if (!currentUser.isAuthenticated()) {
            UsernamePasswordToken token = new UsernamePasswordToken("admin", "secret");
            token.setRememberMe(true);
            currentUser.login(token);
        }
        // 检查角色
        if (currentUser.hasRole("admin")) {
            System.out.println("Welcome admin!");
        }
        // 检查权限
        if (currentUser.isPermitted("read")) {
            System.out.println("Can read.");
        }
        currentUser.logout();
    }
}
```

> **注意**：Shiro 本身不提供 OAuth2 客户端功能，需要结合第三方库（如 `shiro-oauth2`）或自行实现。PKCE 支持通常由 OAuth2 客户端库处理，Shiro 仅负责认证后的 Subject 管理。务必升级 Shiro 至 **2.0.7 或更高版本** 以修复 CVE-2026-23903 等漏洞。

#### 4.3 手动生成与验证 JWT（Java）

```java
// 生成
String secret = "your-256-bit-secret";
String jwt = Jwts.builder()
    .setSubject("user123")
    .claim("scope", "read_orders")
    .setIssuedAt(new Date())
    .setExpiration(new Date(System.currentTimeMillis() + 300_000)) // 5分钟
    .signWith(SignatureAlgorithm.HS256, secret)
```

#### 4.4 在客户端中手动实现 PKCE（Java 原生）

如果不想依赖 Spring Security 的自动 PKCE，可以手动生成并存储 `code_verifier`：

```java
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Base64;

public class PkceUtil {

    public static String generateCodeVerifier() {
        SecureRandom sr = new SecureRandom();
        byte[] code = new byte[32];
        sr.nextBytes(code);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(code);
    }

    public static String generateCodeChallenge(String verifier) throws Exception {
        byte[] bytes = verifier.getBytes("US-ASCII");
        MessageDigest md = MessageDigest.getInstance("SHA-256");
        md.update(bytes);
        byte[] digest = md.digest();
        return Base64.getUrlEncoder().withoutPadding().encodeToString(digest);
    }
}
```

然后在构建授权 URL 时添加 `code_challenge` 和 `code_challenge_method=S256`，并在换取 token 时附带 `code_verifier`。
