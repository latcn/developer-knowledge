
## 第一章 Nacos 是什么？——定位、问题域与根本权衡

### 1.1 没有 Nacos 的世界

微服务 A 调用微服务 B，需要在配置文件中硬编码 B 的 IP 和端口。当 B 重启、扩容、缩容或宕机后，IP 会变，A 必须修改配置并重启，完全不可行。同时，配置项（开关、阈值）的变更也需要重启。

🔍 **第一性原理推导起点**  
1. **寻址**：服务如何动态获得另一服务的网络位置？  
2. **一致性**：所有调用方看到的服务列表必须强一致吗？允许多大延迟？  
3. **可用性**：注册中心自身故障时，调用能否继续？  
4. **动态性**：变更发生后，依赖方需要多快感知到？

**如果没有 Nacos**，可能用 DNS（无健康检查）、ZooKeeper（CP 系统，失去可用性）、数据库轮询（延迟高）。Nacos 的设计目标是**一站式解决服务发现与配置管理，并在 CAP 中做出灵活权衡**。

📣 **费曼解释**：Nacos 是超级管家。所有服务把地址报给它，向它查询别人地址，配置也存它那，一有变动主动通知。管家自己生病（故障）时，备用管家能顶上。

### 1.2 CAP 权衡：不是单选，而是多选

- **临时实例**（ephemeral）：基于心跳，使用自研 **Distro 协议**，保证 AP。
- **持久化实例**（persistent）：基于 Raft，保证 CP。健康检查采用**服务端主动探测**（TCP/HTTP/MySQL），不健康实例仅标记状态，**永远不会从服务列表中删除**，服务发现默认只返回健康实例。
- **配置中心**：依赖外部数据库 + Raft 同步事件，天然 CP。
- **3.0 MCP / A2A** 服务：MCP Registry 自 3.0 起提供，A2A Registry 自 3.1.0 起提供，均可自由选择 AP 或 CP。
- **3.2 Skills Registry**：企业级私有化 Skill 管理中心，在 Agent 与 Skill 之间构建「验证后信任」的治理层。


## 第二章 整体架构设计

### 2.1 逻辑分层

- **接入层**：HTTP/OpenAPI、gRPC 双向流（2.0+）、Console、SDK
- **服务层**：服务管理、配置管理、元数据/权限、一致性协议（Distro / Raft）
- **存储层**：内嵌 Derby（单机）、MySQL（集群），临时实例不落库
- **插件层**：鉴权、加密、健康检查（HTTP/TCP）

### 2.2 端口矩阵（2.x / 3.x）

| 端口 | 与主端口偏移 | 作用 | 备注 |
|------|-------------|------|------|
| 8848 | 0 | HTTP 主端口（OpenAPI + 服务注册发现） | 必开，兼容老 SDK |
| 8080 | 独立配置 | Nacos 控制台 Web 访问端口 | 3.0+ 新增，`nacos.console.port` 配置，不耦合主端口 |
| 9848 | +1000 | gRPC 客户端请求 | 新 SDK 使用，VIP/nginx 需 TCP 转发 |
| 9849 | +1001 | gRPC 集群节点间通信 | 集群内全互联 |
| 7848 | -1000 | JRaft 请求端口 | 集群同步，可通过 `nacos.raft.port` 修改。Nacos 端口以 8848 为基准，加上或减去偏移，因此一旦修改 8848 端口，其他端口也会随之变化 |

> ℹ️ **Nacos 3.0 端口独立说明**：Nacos 自 3.0 开始新增控制台的网络访问端口（默认 8080），不再与主端口（server.port，默认 8848）耦合。2.x/3.0 客户端仍然保留着和 2.x 客户端相同的计算逻辑：配置主端口（默认 8848），通过相同的偏移量 **+1000** 和 **+1001** 计算对应 gRPC 端口。
>
> 🔒 **安全暴露建议**：7848 端口主要用于 JRaft 协议的通信，这是集群间处理 Raft 相关请求的端口，并不直接服务于客户端请求。该端口不应对外开放，以减少潜在的安全风险。建议对外暴露时仅暴露控制台端口（8080）和 gRPC 端口（9848），按需暴露主端口（8848），内部通信端口（7848、9849）请勿暴露至公网。

## 第三章 核心原理与算法深度剖析

### 3.1 服务注册与发现（临时实例，AP）

#### 3.1.1 注册流程

1. 客户端向任一节点发注册请求。
2. 节点通过**一致性哈希**（虚拟节点数 **1000**，常量 `VIRTUAL_NODE_COUNT`，参数 `sync.consistent.hash.replicas`）找到该服务的 owner。若自己不是 owner，**转发**给 owner。
3. Owner 将实例存入内存注册表（`ephemeral=true`），触发 **Distro 协议**异步同步给其他节点，并启动健康检查。

#### 3.1.2 Distro 协议原理

- 基于一致性哈希，每个节点负责一部分服务（只写权，数据全量存储）。
- Owner 定期开启延迟任务（默认 1s~2s，参数 `nacos.distro.task.dispatch.delay`），将所管服务的全量实例列表 checksum 发给其他节点。
- 其他节点对比，不一致时**全量拉取**差异服务的实例列表，本地替换合并。
- 最终一致性窗口约 2~3s，写入毫秒级。

🔍 **第一性原理推导**：服务发现容忍短暂不一致，换极高写性能和可用性，避免共识开销拖垮注册中心。

#### 3.1.3 数据分片与宕机切换

- **分片粒度**：服务名（serviceName），通过一致性哈希环分配 owner。
- **全量存储**：每个节点内存中均有全量实例数据，读取直接本地响应。
- **宕机切换**：故障节点从哈希环移除，其负责的服务顺时针找到新 owner。新 owner 通过全量同步已持有全局数据（可能存在毫秒级窗口），立即接管写入，丢失仅末同步的极少量变更（<3s 窗口）。

📣 **费曼解释**：图书馆管理员每人记得全部书的位置，但每本书只指定一个人负责登记借还。管理员请假，下一个顺位立刻接替，不用重新盘点。

#### 3.1.4 健康检查与保护阈值

**临时实例（AP）** ：gRPC 长连接模式下，服务端双重判定 —— **gRPC 内置 Keepalive** + **客户端心跳上报**（间隔 5s）。连接级保活：gRPC 内置 Keepalive，连接断开（网络分区、进程崩溃）服务端立即感知，无需等待 15s/30s，实时性大幅提升。15s 未收到心跳且连接断开则标记不健康，30s 剔除。

**持久化实例（CP）** ：服务端主动探测（**HTTP、TCP、MySQL** 三种内置协议）。注册中心在持久化服务初始化时根据客户端选择的协议类型注册探活的定时任务，不断探测服务健康状态。不健康实例仅标记状态，**永远不会被剔除**。服务发现默认只返回健康实例（除非触发保护阈值）。

**保护阈值**：参数 `nacos.naming.protect.threshold`，**默认 0（关闭）**。该阈值**仅作用于临时实例（AP）**，对持久化实例无效。触发条件：`健康临时实例数 / 总临时实例数 ≤ 阈值`。触发后，返回**所有临时实例（健康+不健康）**，并停止主动剔除。生产建议设为 0.85~0.95（需显式配置）。

📣 **费曼解释**：挂号签到，晚半小时自动取消。候诊区空座超 15% 停叫号，防止大家集体去厕所被误取消。

### 3.2 配置管理（CP）

#### 3.2.1 通信机制

- **1.x**：HTTP 长轮询。核心原理为 **MD5 对比**：服务端 hold 请求期间，等待配置变更事件通知或超时后，对比客户端请求中携带的配置 MD5 值与服务端当前缓存中的 MD5 值，若不一致则返回变更内容。
  - 客户端超时默认 30s，服务端 hold 请求 29.5s（在客户端超时基础上减 500ms），防止客户端 SocketTimeoutException。最后 0.5s 检查变更并返回；若无变更则返回空响应，客户端立即发起下一次请求。
  - 可通过 `nacos.config.long-polling-timeout` 自定义超时时间。
- **2.x+**：优先 gRPC 双向流，配置变更时通过已建立的 gRPC 流直接推送，延迟从秒级降至**毫秒级**；保留长轮询兼容。

#### 3.2.2 变更流程

1. 管理员发布配置 → 持久化到 MySQL/Derby。
2. 节点通过 **JRaft** 广播配置变更事件（**仅含 dataId、group、tenant 等元数据，不含配置内容**）给集群所有节点。
3. 各节点收到 Raft 事件后，**通过 DumpService 刷新本地 JVM 缓存**，缓存刷新完成后发出 **LocalDataChangeEvent** 本地数据变更事件。
4. 监听了 LocalDataChangeEvent 的组件触发客户端通知，通过 gRPC 流或长轮询推送变更。客户端收到通知后拉取新配置。

> 🔍 **两阶段事件模式**：配置变更采用 `ConfigDataChangeEvent`（触发缓存刷新）→ `LocalDataChangeEvent`（触发客户端通知）的两阶段模式，将数据库写入与客户端通知解耦，确保本地缓存更新后再通知客户端。

#### 3.2.3 灰度发布

- **开源版本**：仅支持**基于请求来源 IP 匹配**。同一 DataID 存 Beta 内容，按 IP 白名单路由。需代理透传 `X-Forwarded-For`。
- **企业版（MSE）** ：支持标签灰度（如 `version=gray`）和流量比例放量，以及推空保护、推送轨迹等高级特性。
- **一键转正**：灰度验证通过后可全量推送。

#### 3.2.4 Raft 持久化与快照机制

- **日志路径**：Raft 日志和快照存储于 `${nacos.home}/data/protocol/raft/`，包含 `entries/`（未压缩日志）和 `snapshot/`（数据快照）。
- **快照机制**：快照是系统在特定时间点的完整状态记录，用于压缩日志存储和加速新节点启动。当已提交的 Raft 日志条目数达到阈值时，自动触发快照创建。

#### 3.2.5 客户端缓存快照说明

- **服务发现客户端**：本地缓存快照**无过期时间**，服务端不主动推送变更时，客户端会一直使用本地缓存。仅当服务端推送新数据后才会更新。
- **配置客户端**：本地快照**默认过期时间为 30 天**（可通过 `nacos.config.cache.expire` 配置），过期后需要从服务端重新拉取。

### 3.3 Distro vs Raft

| 维度 | Distro (AP) | Raft (CP) |
|------|------------|-----------|
| 应用 | 临时实例 | 持久化实例、配置事件、集群元数据 |
| 数据 | 纯内存 | 日志同步，最终数据在 DB |
| 一致性 | 最终一致（2~3s） | 线性一致（多数确认） |
| 冲突解决 | 时间戳最新者胜 | 日志顺序绝对一致 |
| 健康检查 | 客户端心跳 + gRPC Keepalive | 服务端主动探测（HTTP/TCP/MySQL） |
| 持久化 | 不落库 | Raft 日志 + 快照 + DB |

### 3.4 集群节点间通信：全互联 gRPC

- n 个节点通过 gRPC 全互联，连接数 n×(n-1)/2。
- 每条流承载 Distro checksum、Raft 消息、心跳等，复用连接。
- 基于 **grpc-netty**，Nacos 定制了连接管理、线程隔离、反压、重连等。

📣 **费曼解释**：大家互相打专线电话（全互联），所有事都走这条线，不用每次都拨号。

## 第五章 关键时序与容灾

### 5.1 gRPC 注册时序
Client → Nacos1: 建流 → 注册 → 心跳；Nacos1 (owner) → Nacos2: Distro checksum → 全量拉取。

### 5.2 客户端全宕机容灾

- SDK 本地缓存服务列表快照到磁盘文件：服务发现快照**无过期时间**，配置快照**默认 30 天过期**。全集群宕机后，服务发现可继续使用本地快照，但无法感知实例变更，已下线实例的调用失败率会随时间上升，必须配合重试/熔断/故障转移。
- 配置可继续使用当前快照，但无法获取更新；若快照过期，则无法使用。
- **Raft 快照加速恢复**：新节点加入集群时，可从快照快速加载状态，避免从零同步所有日志，显著降低恢复时间。


## 第六章 常见问题与排查

| 类别 | 问题 | 排查方向 |
|------|------|----------|
| 注册发现 | 注册后消失 | 心跳是否成功，端口 8848/9848 是否通，namespace/group 是否匹配 |
| 注册发现 | 发现列表为空 | 核对命名空间，检查保护阈值是否误保留已宕机实例 |
| 配置 | 修改不更新 | @RefreshScope 缺失，gRPC 流中断，手动 /actuator/refresh 测试 |
| 配置 | Beta 不生效 | 客户端 IP 未匹配，代理丢失源 IP |
| 配置 | 发布失败 | 数据库连接，Raft 选举情况，节点数奇数 |
| 性能 | OOM | 堆内存不足（建议 ≥4G），gRPC 连接数过多，定时清理僵尸实例 |
| 集成 | K8s Pod IP 错 | 显式指定 `spring.cloud.nacos.discovery.ip` |
| 3.x | MCP/Skill 不可见 | category 未正确设置，元数据格式错误 |

## 第八章 最佳实践

### 8.1 命名规范
- Namespace 按环境，Service 按 `业务域-功能-服务`，Group 分版本/灰度。

### 8.2 安全
- 开启鉴权，更换 `secret.key`；最小化端口白名单；配置加密。

### 8.3 优雅上下线
```bash
# 先注销实例
curl -X DELETE 'http://nacos:8848/nacos/v1/ns/instance?serviceName=xxx&ip=xx&port=xx'
# 等待 Distro 同步（建议等待 30 秒，可与应用优雅下线宽限期对齐）
# 使用自适应等待机制：轮询查询服务列表确认该实例已消失，或结合健康检查主动探测实例状态
sleep 30
# 再停止容器
```
搭配 K8s `preStop` hook。业界实践建议：下线前的最大等待时间默认 **30 秒**。Kubernetes 的优雅终止宽限期默认为 **30 秒**，可与 Nacos 注销时间对齐，确保实例下线完全。

### 8.4 多数据中心
- **不跨 WAN 直接组集群**。可使用 **Nacos-Sync** 进行集群间服务/配置同步（⚠️ 社区文档更新及讨论持续存在，但组件本身更新频率降低，生产使用前需充分验证），或结合服务网格/定制同步逻辑。
- 跨地域部署需注意网络延迟对 Distro 同步、心跳判定的影响，建议做韧性测试。

### 8.5 版本升级
- 新系统直上 2.x 或 3.x；1.x 逐步升级至 2.x，客户端统一升级以启用 gRPC。

### 8.6 3.x AI 服务治理
- MCP/A2A/Skill 服务独立命名空间，利用 Beta 灰度测试工具，配置加密存储 API Key。


## 第九章 Nacos 3.x 与 AI 服务治理

### 9.1 MCP / A2A 注册发现

MCP Server 注册 `category=mcp`（自 3.0 起支持），元数据示例：
```json
{
  "category": "mcp",
  "metadata": {
    "mcp.protocol": "jsonrpc",
    "mcp.tools": "[\"get_weather\",\"calculate\"]"
  }
}
```
A2A Agent 注册 `category=a2a`（自 3.1.0 起支持），元数据携带 `a2a.agentCard` 和 `agent endpoint`。消费者通过分类过滤发现，控制台新增 AI 服务视图。

### 9.2 Skill Registry（Nacos 3.2+）

Nacos 3.2 推出的私有化 **Skill Registry**，面向企业生产场景，在 Agent 与 Skill 之间构建「验证后信任」的治理层，将 Skill 的审核、管理、分发与追溯统一纳管。

核心能力：
- **安全审核流水线**：内置开箱即用的安全审核插件，覆盖 10+ 项常用风险扫描。
- **多版本管理与灰度分发**：支持草稿（DRAFT）、审核中、灰度（GRAY）、正式（FORMAL）、下线等完整生命周期，通过 dev/latest/stable 等标签精准控制分发范围。
- **异常快速回滚**：灰度阶段发现问题，切换标签映射即可实现秒级回滚，无需重新发版。
- **权限模型与多层隔离**：支持命名空间级别的资源隔离和细粒度访问控制。

Skill 作为一种 AI Resource，可注册、管理，拥有版本、标签，可以处于 draft、reviewing、online 等状态，并通过 label 分发给不同运行时。

### 9.3 Spring AI 负载均衡调用 MCP

使用 `spring-cloud-starter-alibaba-nacos-discovery` + `LoadBalancerClient` 选择 MCP 实例，构建 `McpClient`。支持权重、灰度路由。

### 9.4 AI Agent 频繁扩缩容与保护阈值

AI Agent 常基于 K8s HPA/KEDA/Job 自动扩缩，实例数频繁剧变。传统保护阈值假设实例总数稳定，频繁扩缩导致健康比例剧烈波动，会误触发保护。建议：
- **关闭或大幅降低保护阈值**（如 0.3 或 0）。
- 依赖客户端预热、断路器、元数据标记（`warmup=true`）保障调用质量。

📣 **费曼解释**：保护阈值假设人员稳定，突然涌进 200 个体检新人，候诊区空座太多，停叫号会导致真正病好的人也走不了。频繁扩缩的环境下，更适合靠每个人自己的判断（客户端容错）来工作。

## 第十一章 自检思考题（专家级）

1. **画出 Nacos 服务注册的完整链路，标注不一致窗口。**  
   答案要点：客户端发起注册 → 目标节点通过一致性哈希找到 Owner → Owner 写入内存注册表（标记 ephemeral=true） → Owner 触发 Distro 协议异步同步 → 其他节点全量拉取差异服务实例列表。**不一致窗口为 2~3s**。

2. **Distro 如何解决同一实例在分区的冲突？**  
   答案要点：Distro 采用**时间戳比较**策略，最新时间戳的实例数据获胜；数据全量存储于各节点内存，冲突解决窗口约 2~3s。

3. **配置中心为何用长轮询而非 WebSocket？gRPC 解决了什么？**  
   答案要点：长轮询实现简单、兼容性好且资源消耗可控；gRPC 双向流降低延迟至毫秒级，同时减少连接资源消耗。

4. **全集群宕机后客户端缓存能撑多久？有哪些配套措施？**  
   答案要点：服务发现客户端缓存无过期时间，可无限期使用，但无法感知实例变更，需配合重试/熔断/故障转移；配置客户端缓存默认 30 天过期，需定期刷新。配套措施：本地缓存快照、重试机制、断路器、故障转移。

5. **多数据中心部署有哪几种模式？各优缺点？**  
   （开放问题，典型模式：独立集群 + Nacos-Sync 同步、服务网格多集群、DNS 加权轮询）

6. **3 节点集群为何支持 30 万实例？扩容到 5 节点读吞吐量能提升多少？写呢？**  
   答案要点：3 节点支持 30 万实例得益于全量存储 + 本地读取；扩容到 5 节点**读吞吐量提升约 66%**（读能力线性扩展），**写能力基本不变**（仍由 Owner 节点处理，受一致性哈希分片限制）。

7. **AI Agent 频繁扩缩时，保护阈值为何不适用？应如何设计容错？**  
   答案要点：保护阈值假设实例总数稳定，频繁扩缩导致健康比例剧烈波动，易误触发。应关闭阈值并依赖客户端重试/熔断/预热机制。

8. **Spring AI 如何利用 Nacos 实现 MCP 工具的负载均衡？**  
   答案要点：使用 `spring-cloud-starter-alibaba-nacos-discovery` 注册 MCP 服务（category=mcp），消费者通过 `LoadBalancerClient` 选择实例，构建 `McpClient` 进行调用。
