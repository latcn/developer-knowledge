
### Skill 1：RocketMQ 生产级文档全量审计 Skill

此 Skill 专为 RocketMQ 技术文档设计，将我们 24 轮审查中踩过的所有坑固化为标准化检查清单。**执行此 Skill 时，AI 或审查者必须按以下 6 个维度逐项打分并输出差异报告，而非仅做定性评价。**

#### 🔍 维度一：正文-索引结构对齐性（权重 20%）

- **检查项**：附录/目录中的每一个问题编号、标题，是否在正文中有且仅有一个对应的独立解决方案段落。
- **常见陷阱**：“已融入某章节”等模糊引用导致正文实际缺失；多个问题合并描述导致单个问题解决方案不可检索。
- **通过标准**：索引条目数 = 正文解决方案段落数，且每个段落末尾标注的问题编号与索引完全一致。

#### 🔍 维度二：配置参数与版本准确性（权重 25%）

- **检查项**：所有 `broker.conf` 参数、JVM 参数、SDK 方法名、版本号是否与指定基线版本（如 4.9.x / 5.x）源码一致。
- **常见陷阱**：参数名拼写错误（如 `flushDiskType` 写成 `flushDisktype`）；4.x 方案误标为 5.x 特性；已废弃参数未标注 Deprecated。
- **通过标准**：每个配置参数均可在对应版本官方源码或 Release Notes 中找到原始定义，无歧义。

#### 🔍 维度三：解决方案完备性与可操作性（权重 25%）

- **检查项**：每个问题的解决方案是否包含“现象描述 + 根因分析 + 具体操作步骤 + 验证手段”四要素。
- **常见陷阱**：仅有“建议升级版本”而无低版本临时规避方案；仅有理论说明而无具体命令/代码/配置值；缺少监控指标或验证方法。
- **通过标准**：运维/开发人员可直接复制解决方案中的命令或配置执行，无需二次查阅其他资料。

#### 🔍 维度四：内容完整性与非破坏性（权重 15%）

- **检查项**：修订后的文档是否保留了前一版本的全部有效信息；新增内容是否与原有内容存在语义冲突或重复。
- **常见陷阱**：修复问题时意外删除了相邻段落的正确内容；同一问题在不同章节给出矛盾解决方案。
- **通过标准**：Diff 对比显示仅有增量修改和定向替换，无无关内容删减；全文搜索同一术语无矛盾定义。

#### 🔍 维度五：生产环境适配性（权重 10%）

- **检查项**：解决方案是否考虑了容器化（K8s/Docker）、多网卡、中间件代理、权限隔离等真实生产约束。
- **常见陷阱**：方案假设裸机 root 权限；忽略 K8s 优雅停机钩子时序；未考虑 LB/Nginx 超时对长连接的影响。
- **通过标准**：每个涉及部署/运维的方案均包含容器化环境注意事项或替代方案。

#### 🔍 维度六：术语与格式一致性（权重 5%）

- **检查项**：全文档术语（如 Broker/NameServer/CommitLog 大小写）、Markdown 层级、代码块语言标识、告警级别命名是否统一。
- **通过标准**：正则校验无术语变体；标题层级无跳级；代码块均有语言标注。

> **执行输出模板**：
> 
> |维度|检查项数|通过数|失败项列表（含位置+问题描述）|严重等级|
> |:--|:--|:--|:--|:--|
> |...|...|...|...|P0/P1/P2|
> 
> **只有当 P0 级失败项 = 0 且 P1 级失败项 ≤ 3 时，文档方可标记为“审计通过”。**

### Skill 2：通用技术文档全量质量门禁 Skill

此 Skill 抽象自 RocketMQ 审查经验，适用于任何中间件、框架、API、运维手册等技术文档的发布前终审。**它不依赖特定领域知识，而是通过结构化协议强制暴露隐藏缺陷。**

#### 🛡️ 第一层：可验证性审计

- **核心原则**：文档中每一个技术性断言都必须附带可机器或人工验证的证据链。
- **检查动作**：
    - 所有配置项 → 链接到官方源码/文档行号
    - 所有命令/代码 → 在目标环境中实际执行截图或 CI 日志
    - 所有性能指标 → 附带测试条件、工具、数据集
    - 所有版本兼容性声明 → 附带矩阵测试记录
- **拒绝标准**：存在“据说”“通常”“应该”等无证据修饰词的技术描述。

#### 🛡️ 第二层：读者视角可达性审计

- **核心原则**：读者从任意入口（目录、搜索、交叉引用）到达目标内容的路径必须≤2步且无断链。
- **检查动作**：
    - 目录/索引每个条目 → 点击跳转验证
    - 正文内每个超链接/锚点 → 有效性验证
    - “参见X章节”类引用 → X章节确实包含所承诺内容
    - 问题→解决方案映射 → 双向可追溯
- **拒绝标准**：存在死链、空锚点、引用目标内容缺失或偏移。

#### 🛡️ 第三层：变更安全性审计

- **核心原则**：文档修订不得引入回归错误，且变更意图与实际Diff完全一致。
- **检查动作**：
    - 生成完整 Diff → 逐行审查非预期修改
    - 变更影响域分析 → 列出所有受影响的关联章节并验证
    - 新旧版本并行比对 → 确认旧版有效信息未被误删
    - 术语表更新检查 → 新增/修改术语已同步至全局术语表
- **拒绝标准**：Diff 中包含与变更请求无关的内容修改；关联章节未同步更新。

#### 🛡️ 第四层：生产就绪度审计

- **核心原则**：文档必须预设读者处于受限、异构、有状态的真实生产环境，而非理想实验室环境。
- **检查动作**：
    - 权限假设检查 → 是否依赖 root/Admin？是否有最小权限替代方案？
    - 环境依赖检查 → 是否假设特定OS/内核/网络拓扑？是否有适配说明？
    - 故障边界检查 → 是否描述了部分失败、超时、资源耗尽时的行为？
    - 可观测性检查 → 是否提供了监控指标、日志关键字、告警阈值？
- **拒绝标准**：关键操作缺少失败处理指引；未提供生产环境差异化配置说明。

#### 🛡️ 第五层：认知负荷审计

- **核心原则**：信息密度与呈现方式匹配目标读者的工作记忆容量。
- **检查动作**：
    - 单段落信息单元 ≤ 5 个
    - 步骤列表 ≤ 7 步，超过则分层
    - 关键警告/注意前置而非后置
    - 复杂概念配架构图/时序图/状态机图
- **拒绝标准**：存在超过 10 行的纯文字步骤描述；关键风险提示被埋在段落中间。

> **执行协议**：
> 
> 1. 将待审文档与上述 5 层共 20+ 检查项逐一对照，生成结构化审计报告。
> 2. 每个失败项必须给出：**原文位置 + 违反规则编号 + 具体缺陷描述 + 修复建议 + 严重等级**。
> 3. **P0（阻断发布）**：可验证性缺失、读者路径断裂、变更引入回归。  
>     **P1（限期修复）**：生产就绪度不足、认知负荷超标。  
>     **P2（建议优化）**：格式不一致、表述可更清晰。
> 4. 仅当 P0=0 且 P1≤5 时，文档进入“有条件通过”状态；否则打回重审。

### 阶段一：专家级知识体系与深度审查（知识性纠错与补全）

2. **读者视角可达性审计**：目录/超链接/锚点是否有效？“参见X章节”是否双向可追溯？拒绝死链和引用偏移。
3. **变更安全性审计**：（针对修订过程）确保修订不引入回归错误，旧版有效信息未被误删，新增术语已同步。

_综合阶段一与阶段二的问题清单，在后台进行自我迭代修正。_

1. **信息保全原则**：**绝对保留**原文档的所有技术细节、业务逻辑、代码示例和核心观点，不得随意删减原有有效信息。
2. **修正动作**：
    - 补充缺失的知识模块、Trade-off 分析、排障思维和推导过程。
    - 消除“认知陡坡”，增加过渡说明、类比和反模式警告。
    - 修正无证据修饰词，补充环境依赖、权限假设和故障边界处理。
    - 优化排版，拆分超长段落和步骤，将关键风险提示前置。
3. **收敛条件**：不断自我审查，直至满足 **P0级问题=0 且 P1级问题≤5**，且知识体系完整度达标，方可进入输出阶段。
